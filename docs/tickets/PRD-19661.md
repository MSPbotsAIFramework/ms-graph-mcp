## Requirement understanding

In one sentence: the reporter wants Graph send email to support sending emails with attachments, because the capability can currently only send plain-text/HTML bodies and cannot carry attachments, which blocks attachment-dependent email workflows.

David Hu raised this request via Teams: the existing `graph_send_mail` can only send emails without attachments, David / Toby need it to send emails with file attachments, and there is currently no alternative ("No workaround"). The reporter marked it urgent; the Minimal Viable Slice is "support common file attachments first", and the success criterion is "can successfully send one or more attachments". After completion, David and Toby must be notified in Teams.

## Product design

### Goals / non-goals

**Goal**: `graph_send_mail` supports attaching one or more file attachments when sending an email (the ticket's "minimal viable slice": support common file attachments first); the attachments are delivered together with the email, and the recipient can see and download them.

**Non-goals** (not done in this change):
- Files exceeding this tool's inline limits (500 KB per file after decoding, 700 KB total) -- larger files would require server-side file fetching (referencing a SharePoint/OneDrive driveItem) or Graph's resumable upload session flow, which would turn the "one-shot sendMail" into a three-step "create draft + chunked upload + send draft" call. That is a clearly larger change and is not done here (see Open Questions and Tech design §3 option C).
- Referencing attachments by link from external storage such as SharePoint/OneDrive (the reference-style usage like "send that file as an attachment for me") -- the ticket asks for "include the file content when sending", not "file reference resolution".
- Inline images (`isInline`), S/MIME-signed attachments, and forwarding another message as an attachment (`itemAttachment`) -- the ticket only says "attachments" and does not mention these more complex subtypes.

### Solution (user-visible behavior)

#### Main flow
When calling `graph_send_mail`, the caller (agent) provides, in addition to the existing parameters such as recipients/subject/body, one or more attachments (file name + file content + optional file type). The tool sends the email as usual, and this email additionally carries those attachments. The recipient can see and download the attachments in their own mailbox; the file names, types, and contents match what the caller provided.

#### UI and interaction changes
Not applicable: this is a capability of the MCP tool layer (called by agents) and involves no UI changes directly facing end users. What the recipient sees in their own mail client is the standard attachment display, not a new UI introduced by this change.

#### Boundaries and exceptions
- No attachments provided: the email is sent as usual, with behavior exactly the same as before the change (backward compatible).
- Attachment content unrecognizable/corrupt: the email is not sent, and the caller receives an error that clearly states which file has the problem, instead of an email that "looks normal but whose attachment cannot be opened".
- Attachments too large (a single one or the total exceeds the limits set by this design) or too many attachments: the email is not sent, and the caller receives a clear over-limit explanation (whether size or count was exceeded) and is advised to use a smaller file or split into multiple emails.
- Attachment missing required information (for example, no file name given): the email is not sent, and the error message states what is missing.
- If any of the above validations fails, partial success such as "email sent first, attachment lost" is not allowed -- either it is sent completely or not sent at all.

#### Permissions and multi-tenancy
No new permission dimension is introduced: the caller's own Graph access token (`Mail.Send`) still determines who the email can be sent as and to which mailbox, and attachment content does not change this authorization model. Each call is independent; the attachment content provided in one call will never appear in the result of another call (even the very next call in the same process) -- this is not a "newly added isolation mechanism", but a consequence of the tool being stateless by design (each request's token and parameters are fully determined by that request, with no cross-request caching). This change introduces no mutable state shared across requests, so it does not break this property.

### Impact

- Affected parties: all agents/workflows that call `graph_send_mail` of `ms-graph-mcp`.
- Existing behavior unchanged: for callers that do not pass the new parameter, the request/response shapes are byte-for-byte identical to before the change.
- No migration needed: no existing data is involved (the service itself has no database).
- No announcement needed: this is a purely additive capability, old usage is unaffected, and new usage requires callers to know how to pass the new parameter (the README will be updated with the tool description).

### Acceptance criteria AC1..ACn

- **AC1**: Given the caller passes `graph_send_mail` `to_recipients`/`subject`/`body` and 1 attachment (file name, optional type, base64 content, decoded <=500 KB), When the tool is called, Then the email is sent to the recipient's mailbox, and carries 1 attachment whose file name/type match the input and whose content bytes are identical.
- **AC2**: Given `attachments` contains 2-5 files, each <=500 KB and totaling <=700 KB, When called, Then all attachments appear in the email, with file names/types/contents each matching the input.
- **AC3**: Given `attachments` is not passed (parameter omitted, or `null`/empty list), When called, Then behavior is exactly the same as before the change -- the email is sent normally with no attachments.
- **AC4**: Given an attachment's `content_base64` is not valid base64, When called, Then the tool returns an `invalid_argument` error that clearly states which file name could not be decoded, and the email is not sent.
- **AC5**: Given a single attachment decodes to more than 500 KB, or all attachments together decode to more than 700 KB, or there are more than 5 attachments, When called, Then the tool returns an `invalid_argument` error stating exactly which limit was exceeded (single size / total size / count), and the email is not sent.
- **AC6**: Given an item in `attachments` is missing one of the two required fields `filename` or `content_base64`, When called, Then an `invalid_argument` error is returned that names the specific missing field, and the email is not sent.
- **AC7 (multi-tenancy/isolation)**: Given two consecutive calls using different access tokens/different recipient mailboxes, each with different attachment content, When called in sequence, Then the second call's request does not contain the first call's attachment content, and the two calls do not affect each other -- that is, the tool is stateless, with no attachment content left over or crossing between calls.

- [confirmed 2026-09-30, David Hu / Toby Huang] Attachment content is passed by the caller (agent) as base64 directly in this tool call's parameters; Toby confirmed the actual files are tens of KB and no more than 500 KB. Original assumption: content is passed directly rather than "upload the file elsewhere and pass only a reference link here" -- because the ticket's wording is "support sending emails with attachments", and because this is consistent with the existing "content passed as a single tool-call parameter" pattern in `sites.py` in the repo. If this assumption does not hold (for example, what is actually expected is "send a SharePoint file by reference"), the interface contract in Tech design section 5 would need to be redone as a two-step "reference first, resolve later" flow.
- [non-blocking] When `content_type` is omitted it is treated as `application/octet-stream`, with no automatic type inference based on the file name extension -- friendlier type detection can be added later on demand.

## Tech design

### Conclusion

Add an optional parameter `attachments` to the `graph_send_mail` tool of `ms-graph-mcp` (`src/graph_mcp/tools/mail.py:67`), where each item contains `filename`/`content_base64`/optional `content_type`; when sending, convert it into a Microsoft Graph `fileAttachment` array and put it into the `message.attachments` field of the existing one-shot `POST {base}/sendMail` request body. No new tool, no change to existing required parameters, no new dependency, no change to authentication (still `Mail.Send`). The limits are 500 KB per file, 700 KB total, at most 5 attachments (see "Decision log" for the rationale); scenarios with larger files are not done in this change and are listed as a follow-up iteration.

### Locating the existing implementation

- `src/graph_mcp/tools/mail.py:62-128` -- `graph_send_mail` inside `register()`: the current signature has only `to_recipients`/`subject`/`body`/`sender_id`/`body_content_type`/`cc_recipients`/`bcc_recipients`/`save_to_sent_items`; the `message` dict is assembled at `:106-114`; `:122` decides the send path `/me/sendMail` or `/users/{id}/sendMail`; `:125` sends it in one shot with `client.post(path, payload)`.
- `src/graph_mcp/tools/mail.py:280-337` (the `include_attachments` branch of `graph_get_message`) -- the only code in the repo that handles the "attachment" concept, but it reads metadata only, never reads `contentBytes`, and has no base64 encode/decode logic that can be reused directly; what is added now is encoding/decoding for the opposite direction (write/send).
- `src/graph_mcp/api_client.py:89-92` (`GraphClient.post`) -- no change needed; `sendMail` goes through exactly this method, and `attachments` is just one more field in the payload.
- `src/graph_mcp/tools/sites.py:32-42` (`_MAX_READ_BYTES`/`_MAX_WRITE_BYTES` and their comments) -- an adjacent constraint of the same kind: when the caller passes content as inline parameters, the limit is set at a magnitude that "the caller's own context/a single tool-call parameter can still handle", rather than Graph's own hard limit; the attachment size limit in this change follows this precedent (see the non-functional section).
- `tests/test_tools.py:16-55` (the `EXPECTED_TOOLS` full-set snapshot), `:39` (the `required` set of `graph_send_mail`), `:99` (the tool count `<=32` cap) -- adding an optional parameter does not change the `required` set and adds no tool, so these two existing assertions are unaffected.
- `README.md:85` (the `graph_send_mail` row in the tool table) -- needs the addition "supports inline attachments"; the Scope column is unchanged (the Permissions table of the Microsoft Graph official documentation `user: sendMail` lists only `Mail.Send`, v1.0, checked 2026-09-30; attachments need no extra permission).

### Data and interface contract

**MCP tool contract** (`graph_send_mail`, other existing parameters unchanged):

Example of the new request field:
```json
{
  "attachments": [
    {"filename": "quote.pdf", "content_type": "application/pdf", "content_base64": "JVBERi0xLj..."},
    {"filename": "notes.txt", "content_base64": "SGVsbG8h"}
  ]
}
```
- `filename`: required, string.
- `content_base64`: required, standard base64 (with padding); once decoded it represents the file's raw bytes.
- `content_type`: optional, defaults to `"application/octet-stream"`.
- Omitted / `null` / `[]` -> behavior is the same as before the change (no attachments).

Success return: unchanged, still `{"status": "sent"}` (wrapped by `dump_json_capped`).

Failure returns (new validation branches, all `error_envelope("invalid_argument", <message>, False)`, i.e. no retry):
- Missing `filename` or `content_base64` -> `"attachments[<i>] missing required field 'filename'/'content_base64'"`
- `content_base64` cannot be decoded -> `"attachments[<i>] ('<filename>') is not valid base64: <original exception message>"`
- Single attachment over the limit -> `"attachment '<filename>' is <N> bytes decoded, exceeds the 500,000-byte (500 KB) per-file limit for inline attachments — compress the file or share a link instead"`
- Total over the limit -> `"attachments total <N> bytes decoded, exceeds the 700,000-byte (700 KB) combined limit; send in multiple emails or fewer/smaller attachments"`
- Over the count limit -> `"5 attachments max per call, got <N>"`

**Microsoft Graph layer call** (only this one extra field downstream, everything else unchanged): `POST /me/sendMail` (or `/users/{id}/sendMail`), with `message.attachments` array elements shaped like `{"@odata.type": "#microsoft.graph.fileAttachment", "name": "quote.pdf", "contentType": "application/pdf", "contentBytes": "JVBERi0xLj..."}` (Microsoft Graph `user: sendMail` API documentation, Example 3, v1.0, checked 2026-09-30).

**DB**: none -- this service has no database (gateway mode, stateless forwarding).

**Backward compatibility**: when existing callers do not pass `attachments`, the request/response shapes are byte-for-byte identical to before the change; the unchanged `required` assertion at `tests/test_tools.py:39` is the machine verification of this.

### Key flow sequence

```
caller (agent) -> graph_send_mail(..., attachments=[...])
  -> _build_attachments(): validate required fields per item -> base64 decode -> validate per-item/total/count limits
      +- any item fails -> immediately return error_envelope(invalid_argument), no Graph request is made
  -> all pass -> message["attachments"] = built
  -> GraphClient.post("/me/sendMail" or "/users/{id}/sendMail", payload)
      +- Graph-side 4xx (cases local validation did not cover) -> GraphError -> error_envelope (per the existing _classify rules)
      +- success -> 202 Accepted -> dump_json_capped({"status": "sent"})
```
(This follows the existing try/except GraphError structure of `mail.py`; attachment validation is a new gate placed "before making the HTTP request".)

### Non-functional

- **Idempotency/concurrency**: `graph_send_mail` itself is not idempotent (sending an email cannot be undone, as the existing docstring at `:93-97` already states), and this change does not alter that; the new validation logic is a pure function with no shared mutable state and introduces no concurrency issue.
- **Performance**: base64 decoding is a pure CPU/memory operation; under the 700 KB limit the cost of a single decode is negligible; no extra network round trips are introduced (still a single `POST`). This change has no performance-related acceptance criteria (the ticket states no concurrency/load requirements), so no performance test cases are produced.
- **Security**: no new authentication surface -- the `Mail.Send` token held by the caller still determines which mailbox can be sent to; attachment content is provided entirely by the caller, and this tool does no content scanning (consistent with the existing boundary of write-type tools such as `graph_write_file_text`, neither tightened nor loosened). Validation error messages echo the `filename` provided by the caller, which is consistent with the existing pattern in other tools of the repo (such as the `received_after` validation error of `graph_list_messages`) of echoing caller input, and is not a newly introduced risk.
- **Multi-tenant isolation**: `GraphClient` holds the token per request (`api_client.py:69-77`) and caches nothing across requests; the `attachments` parameter, like the other parameters, is a local variable of a single call, so it naturally does not leak across tenants/requests -- corresponds to AC7.
- **Observability**: no new logging (`mail.py` currently has no explicit logging calls; this is an existing convention and this change does not introduce a new one); the failure reason is returned to the caller through the `message` field of `error_envelope`, which is enough to locate which file and which rule triggered.

### Rollout and rollback

- No feature flag and no gradual-rollout mechanism (the repo currently has no such infrastructure; `grep -rn "feature_flag" src/` has no hits) -- the new parameter is optional with default `None`, so it is naturally backward compatible, equivalent to "safe to roll out out of the box".
- Release order: single-repo change (`ms-graph-mcp` is the only one), no cross-repo dependency, released directly through the existing `docker compose up --build` / CI flow.
- Rollback: `git revert` the change's commit -- the parameter is a newly added optional one, so after rollback, calls already using `attachments` receive an "unknown parameter" error at the MCP schema level, which is a normal feature-unavailable condition rather than data corruption, and no data rollback is needed.

### Test strategy

- Unit tests (reusing the existing `_mail_mcp()` fake client fixture in `tests/test_tools.py`, modeled on existing ones such as `test_get_message_attachments_never_pull_content_bytes`):
  - A single valid attachment -> `message["attachments"]` is assembled correctly, and `contentBytes` matches the input base64 (AC1).
  - 2-5 valid attachments -> all go into `message["attachments"]` (AC2).
  - `attachments` not passed -> no `attachments` key in the payload, byte-for-byte identical to before the change (AC3).
  - Invalid `content_base64` -> returns `invalid_argument`, and the fake client's recorded call list is empty (validation short-circuits before the HTTP request) (AC4).
  - A single attachment decoding to more than 500 KB -> `invalid_argument`, no request sent (AC5).
  - Two attachments each <=500 KB but totaling more than 700 KB -> `invalid_argument`, the message states the total limit was exceeded, no request sent (AC5).
  - More than 5 attachments -> `invalid_argument`, no request sent (AC5).
  - A single attachment of exactly 500,000 bytes (boundary value) -> should be let through rather than rejected, verifying that the boundary check uses `>` rather than `>=` (AC5 boundary).
  - Missing `filename` field -> `invalid_argument`, the message names the missing field (AC6).
  - Two consecutive calls with different attachment contents -> assert the second call's request body does not contain the first call's attachment content (AC7).
  - The `required` set assertion of `EXPECTED_TOOLS["graph_send_mail"]` (existing test `test_tools_list_snapshot`) keeps passing without changes.
- Integration/manual verification (cannot be tested locally; needs a real consented tenant): take a test mailbox account and actually call `graph_send_mail` with 1 PDF + 1 txt attachment sent to itself, then sign in to the mailbox and visually verify that the received email indeed carries 2 attachments with correct content/file names/types -- this step is performed in the dev + test leg with evidence kept (a screenshot or the return of `graph_get_message(include_attachments=true)`).
- Regression surface: no impact on any existing call path that does not pass `attachments`; the attachment metadata read path of `graph_get_message` is entirely independent and unaffected.

### Effort and split

A single subtask is enough, no split needed: changes are concentrated in one function of one file + one test file + one README line. Estimate: **0.5-1 person-day** -- the lower bound is pure coding + unit tests, and the uncertainty in the upper bound comes from how quickly "integration verification needs a real consented tenant and a test mailbox that can be signed in to and inspected" can be obtained.

### Risks and dependencies

- **Dependency**: integration verification needs a tenant/mailbox that has completed OAuth consent and whose token carries `Mail.Send`; `ms-graph-mcp` is in gateway mode and holds no credentials, and the verification account is provided by the caller (the dev + test leg, or the platform-side `mcp-service-gateway`/`mspbots-mcp-manager`); credential configuration itself is out of scope for this design.
- **Risk**: whether the Graph official documentation sets an independent total size limit for attachments inlined directly in the one-shot `sendMail` call, different from the "create draft first, then POST one by one to the `attachments` navigation property" scenario, could not be found in public documentation; this change could not find a number more precise than "3 MB per file" (the `outlook-large-attachments` documentation describes the scenario of POSTing attachments one by one against an existing message/event, which is not exactly the same as inlining multiple fileAttachments in a one-shot sendMail call). (No longer a risk: the final total limit is 700 KB, about 0.93 MB when encoded, far below Graph's request limit of about 4 MB.) The original design conservatively treated "3 MB per file + 3 MB total + at most 5" as this tool's own hard constraints, not relaxing them even if Graph actually allows more -- the failure mode is "rejecting too conservatively" rather than "letting an oversized request through to Graph and only failing there", and the cost is acceptable.
- **Risk**: the current state recorded at `README.md:164` -- on real tenants the `Mail.Read`-related authorization has not finished re-consent; sending mail uses `Mail.Send`, which should in theory already be in use (`graph_send_mail` has long been live), but if the verification account happens to be stuck on the same "tenant needs to re-authorize to get the latest scope" problem, it would slow down the integration verification step -- this does not block the design and is noted here as a troubleshooting reference for the dev + test leg.

### Decision log (2026-09-30)

- **Attachment method**: inline base64. David Hu pointed out that "having the agent produce base64 into the tool parameter consumes model tokens, so a single file can only be limited to 500 KB", and Toby Huang confirmed the actual files are tens of KB and no more than 500 KB, accepting this approach.
- **500 KB per-file limit**: kept consistent with `_MAX_WRITE_BYTES = 500_000` in `src/graph_mcp/tools/sites.py:32-42` (the content must first enter the agent's own context).
- **700 KB total limit** (confirmed by Leo): the nginx in front of the gateway is currently at the default `client_max_body_size 1m` (1,048,576 bytes). 700,000 bytes encode to about 933,334 characters, leaving about 110 KB for the body, recipients, and the MCP JSON-RPC wrapper, so it can go live without any nginx adjustment. **Note**: when the body is very long (an HTML body of more than about 100 KB) and the attachments are close to 700 KB, nginx may still reject it with 413; once nginx is raised to 8m, `_MAX_TOTAL_ATTACHMENT_BYTES` can be raised (for example to 2 MB) by changing only this one constant.
- **Token cost**: a 50 KB file encodes to about 67,000 characters, and the model must output tens of thousands of tokens. Acceptable for occasional small attachments; for high-frequency scenarios, it is recommended that a workflow code node pass the attachments rather than having the model generate base64.
- **Deployment**: the INT/PRD `vendor/ms-graph` (delegated) and `vendor/ms-graph-app` (app-only) both come from this repo, so both need to be updated, and integration verification covers both `/me/sendMail` and `/users/{id}/sendMail`.
