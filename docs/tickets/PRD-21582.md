## Requirement understanding

One line: Ginko IT (via the Rewst-to-MSPbots migration gap register, item 14) wants a new read-only tool, graph_list_applications, in the Microsoft Graph MCP connector that lists a tenant's Entra ID app registrations together with their client-secret (passwordCredentials) expiry metadata, so an automation can give early warning before an app's client secret expires.

This ticket comes from `mspbots-gap-register.xlsx` (the Rewst → MSPbots migration gap list), item 14, filed against the Ginko IT Rewst account. The gap type is "tool" — the connector itself (Microsoft Graph) already exists, but it is missing this one tool. It is replacing the Rewst flow **"[ROC] Azure: Alert on Expiring App Client Secrets"**, which the register records as having run 16 times in the last ~365 days (evidence grade A — i.e. observed execution history, the register's highest confidence tier). The register's "MSPbots current state & dependency" line states that both the Microsoft Graph (43 tools) and GDAP (51 tools) connectors' tool descriptions were checked item-by-item and neither already covers this capability.

The register specifies the target HTTP contract directly: `GET https://graph.microsoft.com/v1.0/applications?$select=appId,displayName,passwordCredentials` (paginated via `@odata.nextLink`), permission `Application.Read.All`, and the response fields the Rewst flow actually consumes: `value[].appId`, `displayName`, `passwordCredentials[].{keyId, displayName, startDateTime, endDateTime, hint}`. This is read-only in both the source flow and the requested tool — it alerts, it does not rotate or delete secrets.

## Product design

### Goals / Non-goals

Goals:
- Add one new read-only tool, `graph_list_applications`, to the Microsoft Graph connector (`ms-graph-mcp`), returning the tenant's Entra ID application (app) registrations.
- Each returned application carries its `app_id`, `display_name`, and its `passwordCredentials` (client secrets) as a `secrets` list — matching exactly the fields the Rewst flow being replaced consumes (`appId`, `displayName`, `keyId`, `displayName` of the secret, `startDateTime`, `endDateTime`, `hint`).
- Each secret additionally carries a computed `days_until_expiry` (negative once the secret has expired) so a caller does not have to do its own date-vs-now arithmetic to answer "is this secret expiring soon" — the single purpose the Rewst flow this ticket replaces exists for.
- The lookup never writes to the directory.
- Pagination follows this connector's existing one-page-per-call contract (same as `graph_list_users`/`graph_list_groups`), since a tenant can have more app registrations than fit in one page.

Non-goals (this slice):
- **No alert/threshold logic.** "Which secrets count as expiring soon" is a decision for the calling automation/agent, not this connector — the tool reports raw dates and the derived `days_until_expiry`, it does not decide what to do about them.
- **No write actions.** Rotating, adding, or deleting a secret or an app registration is out of scope; the Rewst flow being replaced is itself read-only (an alert), and this ticket only asks for the read side.
- **No `$filter`/display-name search in this slice.** The register's own Rewst call example lists the whole tenant with no filter. If a future gap needs "find this one app's secrets" instead of "list every app", that is a follow-up (see Open Questions).
- **No `/servicePrincipals` ("Enterprise applications") coverage.** The register's HTTP contract and the Rewst flow both target `/applications` (app registrations) specifically — a different Graph resource from service principals. Conflating the two would silently expand what was asked for; see Tech design Option analysis.
- **No certificate (`keyCredentials`) listing.** The register's return-fields list is `passwordCredentials` only; certificate-based credentials are a distinct field this ticket was not asked to cover.
- **Not porting this tool to the GDAP connector (`gdap-mcp`) in this slice.** The register's "MSPbots connector / MCP" field names only "Microsoft Graph"; GDAP's own tool catalogue was checked (per the register's "current state & dependency" line) and also found not to cover this, but the register does not ask for it in GDAP. See Open Questions — this is the one place this ticket's scope differs from PRD-21391's (which explicitly named both connectors).

### Acceptance criteria AC1..AC6

- **AC1** — Given a tenant with at least one Entra ID app registration that has a non-expired client secret, when `graph_list_applications` is called, then the response includes an entry for that application with `app_id`, `display_name`, and a `secrets` entry carrying `key_id`, `display_name`, `start_date_time`, `end_date_time`, `hint`, and `days_until_expiry` (a positive number).
- **AC2** — Given an app registration with no client secrets (e.g. certificate-only or a public client), when `graph_list_applications` is called, then that application still appears in the result with `secrets: []` — it is not silently dropped and this is not an error.
- **AC3** — Given more applications exist in the tenant than one page (`max_results`), when `graph_list_applications` is called, then the response returns at most `max_results` applications, `has_more` is `true`, and `next_page_token` can be passed back in to fetch the next page (mirrors `graph_list_users`'s one-page-per-call contract).
- **AC4** — The tool issues only HTTP GET calls to Microsoft Graph; calling it never creates, modifies, or deletes any application, credential, or other directory object.
- **AC5** — Given a tenant with zero application registrations, when `graph_list_applications` is called, then the response is `{"count": 0, "applications": [], "has_more": false, "next_page_token": null}`, not an error.
- **AC6** — Given an application with a client secret whose `end_date_time` is in the past, when `graph_list_applications` is called, then that secret's `days_until_expiry` is negative (distinguishing "already expired" from "expiring soon" without the caller parsing dates itself).

## Tech design

### Conclusion

Add one new read-only tool, `graph_list_applications`, in a new module `src/graph_mcp/tools/applications.py`, following this connector's existing `/users`→`/groups` pagination pattern (`$top`/`$skiptoken`, one Graph page per call) and its established `{count, <list>, has_more, next_page_token}` response envelope. The tool requires a new Graph permission scope, `Application.Read.All`, that this connector has never requested before — the code ships and merges regardless (per this repo's documented precedent for every prior new-scope tool), and returns `unauthorized` until the platform side adds the scope and a tenant re-consents. No new repo, no gateway change, no database.

### Data & API contract

Request:

```
graph_list_applications(max_results: int = 50, page_token: str | None = None) -> str   # ms-graph-mcp
```

Upstream Graph call:

```
GET https://graph.microsoft.com/v1.0/applications
    ?$select=appId,displayName,passwordCredentials
    &$top=<min(max_results, 999)>
    [&$skiptoken=<page_token>]
```

No request body, no write (AC4).

Response (JSON, `dump_json_capped`):

```json
{
  "count": 2,
  "applications": [
    {
      "app_id": "11111111-2222-3333-4444-555555555555",
      "display_name": "Ginko-RMM-Sync",
      "secrets": [
        {
          "key_id": "aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee",
          "display_name": "prod-secret",
          "start_date_time": "2026-01-15T00:00:00Z",
          "end_date_time": "2026-11-15T00:00:00Z",
          "hint": "ab12",
          "days_until_expiry": 16
        }
      ]
    },
    {
      "app_id": "66666666-7777-8888-9999-000000000000",
      "display_name": "Cert-only-app",
      "secrets": []
    }
  ],
  "has_more": false,
  "next_page_token": null
}
```

Empty tenant (AC5): `{"count": 0, "applications": [], "has_more": false, "next_page_token": null}`.
Already-expired secret (AC6): same shape, `days_until_expiry` is a negative integer.
Error case: the standard envelope from `error_envelope(code, message, retryable)`, e.g. `{"error": "unauthorized", "message": "...", "retryable": false}` — the same shape every other tool's error returns, and also what every call returns today before `Application.Read.All` is granted and a tenant re-consents (Open Questions/Risks).

Backward compatibility: purely additive (new tool, new yaml row, new README row); no existing tool's request or response shape changes.

### Key flow / sequence

1. Agent calls `graph_list_applications(max_results=50)` (or with `page_token` for a later page).
2. Tool builds Graph query params (`$select`, `$top`, optional `$skiptoken`) and calls `GET /applications` using the caller's per-request Graph access token (gateway mode — the server itself holds no credentials, same as every other tool in this connector).
3. Each returned `application` object is mapped to `{app_id, display_name, secrets: [...]}`; each `passwordCredentials` entry is mapped with `days_until_expiry` computed client-side (`end_date_time` minus the current UTC time).
4. The (possibly empty) list is wrapped in `{count, applications, has_more, next_page_token}` and returned as text.
5. On a Graph error (e.g. `403` before the tenant has re-consented to `Application.Read.All`), `GraphError.to_envelope()` returns the standard structured error shape.

### Non-functional

- **Idempotency/concurrency**: pure read, no state; safe to call concurrently and repeatedly (`idempotentHint=True`, matching every other list tool in this file).
- **Performance**: same page-size discipline as `graph_list_users` (default 50, hard cap 200, Graph's own `$top` cap 999); a tenant with many app registrations needs multiple calls via `next_page_token`, same contract as every other list tool here.
- **Security**: Microsoft Graph itself never returns a secret's plaintext value after creation — `passwordCredentials` only ever carries metadata (`keyId`, `displayName`, `startDateTime`, `endDateTime`, `hint`, a short non-reversible fragment). This is a Graph platform property, not something this tool has to enforce itself; the response genuinely cannot leak a usable secret value. No new credential storage; the server still holds no credentials (gateway mode, per-request token, same as every other tool).
- **Multi-tenant isolation**: unchanged — the per-request bearer token already scopes every call to the tenant that issued it, same as every other tool in this connector; no new isolation surface introduced.
- **Observability**: covered by the platform's existing per-tool-call logging/audit path; no new logging code needed, this is a `GET` like any other tool here.
- **Least privilege**: `Application.Read.All` is the documented minimum Graph permission for `GET /applications`; no broader scope (e.g. `Directory.Read.All`) is requested.

### Rollout & rollback

- **New Entra scope required** (`Application.Read.All`, Current state/Open questions): per this repo's established pattern for every prior new-scope tool (`Group.ReadWrite.All`/PRD-20480, `Mail.Read`/PRD-19103, `Calendars.ReadWrite`/PRD-18631, `Synchronization.ReadWrite.All`/PRD-20422), the platform side (`MCP-Management-Service`'s `auth/oauth/vendors/msgraph.py`, outside this repo) must add the scope to what it requests from Entra, and every already-connected tenant must re-consent before this tool stops returning `unauthorized`. This repo's code ships and merges regardless of that platform-side timing — it is a known, repeatable rollout shape, not a new category of risk.
- **Rollback**: a plain revert — remove the tool registration and the yaml row; no data migration, no schema, no irreversible side effect to undo (the tool never writes).
- **Release order**: `any` (`references/mcp-track.md` §1.2) — a standalone, additive tool addition in a single repo; no cross-repo dependency to sequence.

- **Regression**: existing tool tests (users/groups/domains/etc.) are untouched by this change (additive only); self-test should still show them green.
