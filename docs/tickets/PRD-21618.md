## Requirement understanding

One line: Add a tool to the Microsoft Graph MCP connector that, given an application's (client) id, finds or creates its service principal and adds it a short-lived (10-minute) password credential, matching the Rewst `microsoft_graph.graph_api_request` calls (`POST /servicePrincipals`, `POST /servicePrincipals/{id}/addPassword`) used by EMD Networking Services' "[ROC] M365: Push MFA Notification to User" flow, so that flow can be migrated off Rewst.

This is item 54 of the Rewst → MSPbots migration gap register (`mspbots-gap-register.xlsx`). The gap is a missing tool, not a missing connector: `ms-graph-mcp` already exists and already handles users/groups/licenses/mail/sites/devices/domains/calendar/conditional-access/offboarding, but has no tool over `/servicePrincipals` creation or credential management. Without it, a flow that triggers an MFA push by authenticating as an app's service principal (via a temporary password it mints for that purpose) has no equivalent on the Agent platform.

## Product design

### Goals / Non-goals

Goals:
- Add one new tool, `graph_service_principal_create_and_add_password`, to `ms-graph-mcp` that:
  - given an application id (`app_id`), finds the tenant's existing service principal for that application, or creates one if none exists yet;
  - adds a new password credential to that service principal, short-lived by default (10 minutes, matching the MFA-push use case), with the lifetime and start time overridable by the caller;
  - returns the service principal's id, whether it was newly created, and the one-time secret (plus its key id and expiry) — the secret is only ever returned at creation time and cannot be read back later, exactly like `graph_create_tap`'s `temporary_access_pass`.
- Keep the tool's input/output, error shape, and required permission documented consistently in README's Tools table, `docs/gdap-role-map.yaml`, and the MCP `tools/list` response — the same three places (plus the test file's lockstep literal — four in total, Tech design §4 "lockstep") every other tool in this connector is documented and the connector's own consistency test enforces.

Non-goals:
- No `graph_service_principal_remove_password` / credential cleanup tool. The ticket does not ask for one, and Rewst's own flow does not call one either (the 10-minute expiry is the only cleanup mechanism the reference flow relies on). Flagged as a Known Gap in Tech design §7, not built here.
- No general-purpose service principal management (list all service principals, read/update/delete a service principal, manage its owners, app roles, or any other `/servicePrincipals` sub-resource). Only the one find-or-create-then-add-password composite the ticket asks for.
- No change to how `graph_start_cloud_sync` discovers its own service principal (`offboarding.py`'s private helpers) — that code is unrelated and untouched.
- No automatic triggering of the MFA push itself. Rewst's flow uses the resulting app-identity credential to call a separate (non-Graph) endpoint to trigger the push; this MCP only supplies the Graph plumbing the ticket names (find/create the service principal, add the password), the same scope boundary the ticket's own field list draws.

### Acceptance criteria AC1..ACn

- AC1: Given a valid `app_id` for an application that has **no** existing service principal in the tenant, when `graph_service_principal_create_and_add_password` is called, then a new service principal is created for that `app_id`, a password credential is added to it, and the result reports `created: true` together with the service principal's id, the one-time secret, its key id, its display name, and its validity window (start/end).
- AC2: Given a valid `app_id` for an application that **already has** a service principal in the tenant, when the tool is called, then no new service principal is created (the existing one is reused), the result reports `created: false` with the existing service principal's id, and a **new** password credential is still added to that existing service principal (adding a password never fails because one already exists — Graph does not cap the count the way it caps some other resources).
- AC3: Given no `start_date_time` / `lifetime_minutes` arguments, when the tool is called, then the added password credential's validity window starts now and expires 10 minutes later, matching the MFA-push use case's "10 分钟有效" requirement.
- AC4: Given a caller-supplied `lifetime_minutes` (and optionally `start_date_time`), when the tool is called, then the password credential's validity window is `start_date_time` (or now, if omitted) through `start_date_time + lifetime_minutes`.
- AC5: Given an `app_id` that does not correspond to any application registration in the tenant, when the tool is called, then the result is a structured error envelope (Graph's own `invalid_argument`/`not_found` classification, surfaced via the existing `GraphError` path), not a crash and not a silently-empty success.
- AC6: Given more than one service principal already exists in the tenant for the given `app_id` (an unusual multi-tenant-app edge case), when the tool is called, then the result is a structured `service_principal_ambiguous` error listing the candidate ids, rather than guessing which one to add a password to.
- AC7: Given a caller token whose tenant has not granted `Application.ReadWrite.All` (before that tenant completes re-consent — see Tech design §7), when the tool is called, then Graph's 403 is surfaced as the connector's standard `unauthorized` envelope, not a stack trace — the same "returns 403 until re-consent" situation already documented in this README for several other tools.
- AC8: Given no `X-Ms-Graph-Token` header on the request, when the tool is called, then the result is the standard `NO_TOKEN` envelope — identical behavior to every other tool in this connector, no special-casing.
- AC9: Given a successful call, when the response is returned, then it contains the plaintext `secret_text` exactly once, in the tool's return payload only — the connector does not log the request or response body anywhere (no logging call exists in `api_client.py`'s request path today, and this ticket adds none), consistent with how `graph_create_tap`'s `temporary_access_pass` is already handled.
- AC10: The new tool has exactly one row in `README.md`'s Tools table and exactly one entry in `docs/gdap-role-map.yaml`, with matching `GDAP Role` values, and the test file's own tool-count/role-map-count literals are updated to match — so the repo's own `tests/test_gdap_role_map.py` and `test_tools_list_snapshot` pass without weakening either test.

### Open questions

- [not blocking — already assumed] Q1: Is **Cloud Application Administrator** or **Application Administrator** the better single GDAP role to document (Microsoft Learn lists both as equally valid for this exact operation)? Assumed: **list both** (`Cloud Application Administrator<br>Application Administrator`), matching the README's existing convention of listing two roles with `<br>` when Microsoft documents more than one applicable built-in role for the same tool (e.g. `graph_reset_password`, `graph_revoke_sessions`). This is metadata-only — if product later prefers naming only one, it is a one-line fix in two files, no code or contract change.
- [assumed] Q2: Should the tool's default password display name be generic (`"MSPbots MCP - Temporary Password"`) or echo Rewst's own convention (`"Rewst - MFA Temporary Password"`)? Assumed **generic**, overridable via the optional `display_name` parameter: this MCP serves every MSP tenant on the Agent platform, not only ones migrating from Rewst, so hard-coding a Rewst-specific label as the default would misname the credential for every other caller. A caller that wants Rewst's exact label can pass it. Does not block implementation; if product disagrees, changing the default string is a one-line change.
- [not blocking — already assumed] Q3: Should the "multiple existing service principals for one `app_id`" case (AC6) be treated as an error, or should the tool pick the first match? Assumed **error** (`service_principal_ambiguous`), following the same conservative precedent this repo already set for `graph_start_cloud_sync`'s `sync_job_ambiguous` (`offboarding.py:412-420`) — guessing which credential-bearing identity to hand a new secret to is a security-relevant choice, not a convenience default. Does not block implementation.

## Tech design

### Conclusion

Add one new tools module, `src/graph_mcp/tools/service_principals.py`, exposing `graph_service_principal_create_and_add_password(app_id, display_name=None, start_date_time=None, lifetime_minutes=10)`. It is a three-step composite over Graph's existing `/servicePrincipals` endpoints: (1) `GET /servicePrincipals?$filter=appId eq '{app_id}'` to find an existing service principal, (2) `POST /servicePrincipals {appId}` to create one only if none was found, (3) `POST /servicePrincipals/{id}/addPassword` to mint the short-lived secret — reusing the exact `client_factory()` / `NO_TOKEN` / `GraphError.to_envelope()` / `dump_json_capped()` pattern every other tool in this repo already uses, plus the same "ambiguous candidates → structured error, don't guess" pattern `offboarding.py` already established. No new abstractions, no new third-party dependency. The only other required changes are additive: one import + one `register()` call in `server.py`, one README table row (plus one "scopes actually requested" union line and one new rollout paragraph), and one `docs/gdap-role-map.yaml` entry.

### Option analysis

| Option | Approach | Pros | Cons | Verdict |
|---|---|---|---|---|
| A. One composite tool, `graph_service_principal_create_and_add_password(app_id, ...)`, find-or-create then add-password | As described above | Matches the exact tool name and composite shape the ticket asks for; one MCP round-trip for the agent instead of three; idempotent at the service-principal-creation step (AC2); mirrors how this repo already composes multi-call Graph flows into one tool when the ticket's use case never needs the intermediate state on its own (e.g. `graph_read_site_file_text`'s 3-call chain collapsed into 1) | The tool does two logically separate things (find-or-create; add a credential) under one name | **Chosen** — matches the ticket's named tool exactly, and the two steps are never independently useful for this use case (a service principal with no password credential cannot authenticate; the point of finding/creating one here is always to immediately add a password) |
| B. Two separate tools: `graph_service_principal_get_or_create(app_id)` + `graph_add_service_principal_password(service_principal_id, ...)` | Split by Graph operation, mirroring the general users/groups "separate get and act" convention | Each tool reusable independently (e.g. a future ticket wanting to look up a service principal without minting a credential) | Ticket explicitly names one tool, `graph_service_principal_create_and_add_password`; no current use case needs the id-lookup half standalone; two tools means two README rows, two yaml rows, doubles the lockstep surface for a request that only asks for one composite action | Rejected — more surface than the request justifies; revisit if a future ticket needs standalone service-principal lookup |
| C. Always create, never check for an existing service principal (literal reading of "create_and_add_password") | `POST /servicePrincipals` unconditionally, then `addPassword` | Smallest possible diff; matches the tool's literal name | Graph rejects a second `POST /servicePrincipals` for an `appId` that already has one with `409 Conflict` ("service principal already exists") — calling this tool twice for the same long-lived MFA app (the realistic repeat-use pattern: the same app is reused across many push events) would fail on the second and every subsequent call. AC2 would not exist, and the tool would be unusable for its own stated recurring use case | Rejected — a literal "always create" implementation breaks on its second real-world invocation; the find-or-create step is necessary, not optional |

No third-party library is a candidate here: this is three Graph REST calls through the connector's own already-built `GraphClient`, the same pattern used by all 47 existing tools. Selection order (reuse > open source > self-build) resolves to "reuse the existing `GraphClient`, the offboarding module's candidate-list/ambiguous-error pattern, and the TAP tool's secret-shaping pattern" — there is nothing to add.

### Data & API contract

Request (MCP tool call), minimal:
```json
{ "name": "graph_service_principal_create_and_add_password", "arguments": { "app_id": "11111111-2222-3333-4444-555555555555" } }
```
with overrides:
```json
{
  "name": "graph_service_principal_create_and_add_password",
  "arguments": {
    "app_id": "11111111-2222-3333-4444-555555555555",
    "display_name": "Rewst - MFA Temporary Password",
    "lifetime_minutes": 10
  }
}
```

Response — new service principal created (AC1):
```json
{
  "service_principal_id": "aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee",
  "app_id": "11111111-2222-3333-4444-555555555555",
  "created": true,
  "secret_text": "[one-time secret, 16-64 chars, Microsoft-generated]",
  "key_id": "f0b0b335-1d71-4883-8f98-567911bfdca6",
  "display_name": "MSPbots MCP - Temporary Password",
  "start_date_time": "2026-10-31T12:00:00Z",
  "end_date_time": "2026-10-31T12:10:00Z"
}
```

Response — existing service principal reused (AC2): identical shape, `"created": false`.

Errors (reusing the connector's existing envelope plus one new connector-level code):
```json
{ "error": { "code": "service_principal_ambiguous", "message": "...", "retryable": false, "candidates": ["sp-id-1", "sp-id-2"] } }
```
- `invalid_argument` / `not_found` (400/404) — `app_id` does not correspond to any application registration in the tenant (AC5); Graph's exact status for a nonexistent `appId` on `POST /servicePrincipals` was not verified against a live tenant at design time (no sandbox tenant available) — the tool does not pre-validate `app_id`'s existence itself (consistent with `graph_get_group` not pre-validating `group_id`), so whatever Graph returns flows through the existing classification unchanged.
- `unauthorized` (401/403) — missing or insufficient-scope token (AC7/AC8); 401 is the `NO_TOKEN` short-circuit before any Graph call, 403 is Graph's own response (un-consented `Application.ReadWrite.All`) surfaced via `GraphError`.
- `service_principal_ambiguous` (connector-level, not a Graph error) — more than one service principal already exists for `app_id` (AC6).

DB: none — this connector is stateless (SOP "runtime model" — no persistence, no cross-request state; `api_client.py:16-19`'s shared `httpx.AsyncClient` carries no credentials).

Backward compatibility: pure addition. No existing tool, parameter, or response shape changes. No client of this connector can be broken by this change.

### Key flow / sequence

1. Agent platform → `ms-graph-mcp` `/mcp`: `tools/call graph_service_principal_create_and_add_password` with `X-Ms-Graph-Token` header and `app_id` (plus optional overrides).
2. `GatewayTokenMiddleware` (`server.py`) extracts the token into the per-request contextvar; 401 short-circuit if missing (AC8).
3. Tool body calls `client_factory()` → `GraphClient(token, ...)`.
4. `GET /servicePrincipals?$filter=appId eq '{app_id}'&$select=id,appId` → 0, 1, or 2+ matches.
5. 2+ matches → return `service_principal_ambiguous` envelope (AC6); stop.
6. 0 matches → `POST /servicePrincipals {"appId": app_id}` → new `id`, `created = True`. 1 match → reuse its `id`, `created = False`.
7. Compute `end_date_time` from `start_date_time` (or now) + `lifetime_minutes`.
8. `POST /servicePrincipals/{id}/addPassword` with the computed `passwordCredential` body → `secretText`/`keyId`/`startDateTime`/`endDateTime`/`displayName`.
9. Tool returns `dump_json_capped({...})` on success or `e.to_envelope()` on `GraphError` from any of the three Graph calls.
10. Response flows back through FastMCP to the Agent platform exactly like every other tool's response.

### Non-functional

- Idempotency & concurrency: **not fully idempotent, and this is documented, not hidden** — the find-or-create step (steps 4/6) is idempotent (calling with the same `app_id` repeatedly reuses the same service principal), but the `addPassword` step (step 8) is not: every call mints a brand-new credential, the same non-idempotent shape this repo already ships and documents for `graph_create_tap` (`users.py:908`: "not idempotent"). Unlike TAP, which invalidates the previous pass on each call, `addPassword` does **not** invalidate prior credentials — repeated calls accumulate `passwordCredentials` entries on the service principal over time (flagged as a Known Gap below, since no removal tool exists). No shared mutable state is introduced (the shared `httpx.AsyncClient` carries no credentials, per `api_client.py:16-19`; per-request contextvar token isolation in `server.py` is unchanged).
- Performance: two or three Graph calls per invocation (find, optionally create, add-password) — no N+1, no new hot path, no pagination needed (the `$filter` on `appId` returns at most a handful of rows for any real tenant).
- Security: **this is the tool's central risk and must be read by whoever approves the new scope.** `Application.ReadWrite.All` is the least-privileged Graph permission for this operation (confirmed against Microsoft Learn, no narrower delegated alternative exists), but it is also one of the broadest permissions in this connector's union: it grants the caller the ability to create, read, and manage credentials for **every** application and service principal in the tenant, not only the one MFA app this ticket's use case targets. This is inherent to Graph's own permission model for this endpoint family (there is no "credentials only, scoped to one app" delegated permission), not a design shortfall of this tool — but the blast radius is materially larger than, say, `Policy.Read.All` (read-only, one resource type) or `UserAuthenticationMethod.ReadWrite.All` (scoped to one user's auth methods). The secret itself (`secret_text`) is returned exactly once in the tool's response payload and is never logged or persisted anywhere in this connector (no logging call exists in `api_client.py`'s request/response path; `GraphClient` holds no state between calls) — same handling as `graph_create_tap`'s `temporary_access_pass`.
- Multi-tenant isolation: unaffected — every call is scoped by the caller's own bearer token, same as all 47 existing tools; no tenant id is ever accepted as a parameter.
- Observability: no new logging/metrics beyond what `GraphClient`'s existing error classification already provides; a failed call surfaces its `GraphError` status code and message in the structured envelope, consistent with every other tool. The connector-level `service_principal_ambiguous` error includes the candidate ids in the envelope's `extra` field so a caller (or a human debugging the flow) can see exactly what was found without a second Graph call.
