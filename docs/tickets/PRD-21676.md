## Requirement understanding

One line: Don wants `graph_get_group` (required) and, ideally, `graph_list_user_groups` (desirable) to return `isAssignableToRole` — together with `mailEnabled`, `securityEnabled`, `groupTypes` and `onPremisesSyncEnabled`, which are mostly already returned — in both the Microsoft Graph and the Microsoft 365 GDAP (multi-tenant) connectors, so an onboarding agent copying a reference user's ordinary groups can tell role-assignable groups apart and leave them to a person instead of defaulting to copying nothing.

Restatement: onboarding agents (FocusTSI #266, PRECICOM #239) copy a named reference user's group memberships onto a new hire. They must exclude role-assignable, dynamic, on-premises-synced and licensing groups, but today `graph_get_group` and `graph_list_user_groups` don't expose `isAssignableToRole`, so the agent cannot tell an ordinary group from one that carries administrator rights — the only safe fallback is to copy nothing and hand every group to a technician. Success is `graph_get_group` returning `isAssignableToRole: true` for a role-assignable group and not-true for an ordinary one, in both connectors, with `customer_tenant_id` accepted on the GDAP side.

Reconciling with the ticket's own "Existing Capability Check": the reporter explicitly flagged an overlap with **PRD-21647** ("isAssignableToRole in GDAP `graph_get_group`, `graph_list_groups`, and `graph_list_user_groups`, plus clearer protected-group permission errors") and noted a routing comment from Micus (2026-10-30) describing a combined "build together" change spanning PRD-21647, PRD-21676 and PRD-21706 across all three tools (`graph_get_group`, `graph_list_groups`, `graph_list_user_groups`) in both connectors. This design scopes strictly to what **PRD-21676 itself** asks for — `graph_get_group` and `graph_list_user_groups`, not `graph_list_groups` — to avoid two tickets independently editing the same lines with conflicting intent; see Tech design §11 (Risks & dependencies) for how this stays safe to land in either order relative to PRD-21647/PRD-21706.

## Product design

### Goals / Non-goals

**Goals**:
- `graph_get_group` returns `isAssignableToRole` in both the Microsoft Graph connector and the Microsoft 365 GDAP connector (with `customer_tenant_id` on the GDAP side), so an onboarding agent can decide whether a group is safe to auto-copy.
- `graph_list_user_groups` returns `isAssignableToRole` per group, in both connectors, so the same decision can be made without an extra `graph_get_group` call per group (AC5, the "ideally" / desirable half of the ticket).
- The already-returned classification fields (`mailEnabled`, `securityEnabled`, `groupTypes`, `onPremisesSyncEnabled`/`sync_source`) keep working unchanged in both tools and both connectors (regression, not a new feature).

**Non-goals** (explicitly out of scope for this ticket):
- `graph_list_groups` is **not** touched by this ticket. The ticket's own AC and Minimal Viable Slice name only `graph_get_group` (required) and `graph_list_user_groups` (desirable); `graph_list_groups` is named in the overlapping **PRD-21647**'s description instead. Editing it here risks a silent merge conflict in intent with that ticket. See Tech design §11.
- Reconciling or re-scoping PRD-21647 itself (whether it is Graph-only or GDAP-only) — that reconciliation is explicitly called out in the ticket as unresolved and is a product/BA decision, not something this design can settle. This design is written so it does not depend on how that reconciliation lands (see Tech design §11).
- Any change to the onboarding agent's own orchestration logic (deciding which groups to skip based on `isAssignableToRole`). That logic lives outside both MCP connectors; this ticket only makes the data available.
- Adding `isAssignableToRole` (or anything else) to `graph_list_owned_groups` or `graph_list_group_members` — not named in the ticket.
- Changing the declared/required Graph permission scope. Both tools already document `Group.Read.All` (README.md:156-158); see Open Questions for the one caveat on this.
- Converging `gdap-mcp`'s `graph_list_user_groups` onto `ms-graph-mcp`'s `/memberOf/microsoft.graph.group` type-cast query shape (a pre-existing divergence noted in Current state/Tech design §4a) — that is a separate, higher-risk behavioral change, not requested here.

### Acceptance criteria AC1..ACn

- **AC1**: Given a known role-assignable group's id, When `graph_get_group` is called in the Microsoft Graph connector, Then the response includes `isAssignableToRole: true`.
- **AC2**: Given an ordinary (never provisioned as role-assignable) group's id, When `graph_get_group` is called in the Microsoft Graph connector, Then `isAssignableToRole` is not `true` — Microsoft Graph returns `null`, not a literal `false`, for a group that was never created as role-assignable (see Open Questions); the tool passes the raw value through unchanged, and callers treat anything other than `true` as "not role-assignable".
- **AC3**: Given the same two groups (one role-assignable, one ordinary) in a GDAP customer tenant, When `graph_get_group` is called in the Microsoft 365 GDAP connector with that tenant's `customer_tenant_id`, Then the result matches AC1/AC2 for that tenant.
- **AC4** (backward compatibility / regression): Given `graph_get_group` is called in either connector, When the response is compared against today's response shape, Then `mailEnabled`, `securityEnabled`, `groupTypes`, `onPremisesSyncEnabled`, `sync_source` and every other field present today are still present with the same values — `isAssignableToRole` is additive only.
- **AC5**: Given a user who belongs to at least one role-assignable and one ordinary group, When `graph_list_user_groups` is called for that user in either connector (GDAP with `customer_tenant_id`), Then every group entry in the response includes `isAssignableToRole` with the correct value for that group.
- **AC6** (backward compatibility / regression): Given `graph_list_user_groups` is called in either connector, When the response is compared against today's shape, Then pagination (`has_more`/`next_page_token`), `sync_source` derivation and every other existing field are unchanged — `isAssignableToRole` is additive only.
- **AC7** (multi-tenant isolation, GDAP only): Given two different GDAP customer tenants each with their own role-assignable/ordinary groups, When `graph_get_group` or `graph_list_user_groups` is called once per tenant with that tenant's `customer_tenant_id`, Then each call's `isAssignableToRole` values reflect only that tenant's groups — this change introduces no new way to read another tenant's directory data.

### Open questions

- [non-blocking, already-assumed] AC2's wording in the ticket says an ordinary group's `graph_get_group` call "returns `isAssignableToRole: false`". Microsoft Graph's actual, documented behavior is that this property is `null` for groups that were never explicitly provisioned as role-assignable (it can only be set at group-creation time) — it is not retroactively computed to `false`. This design assumes **passthrough of the raw value** (so an ordinary group may show `isAssignableToRole: null`, not `false`) rather than coercing `null` to `false` in the tool, because (a) it is simpler (no extra branch, YAGNI) and (b) coercing could misrepresent a group Microsoft hasn't classified either way. If the onboarding agent's caller-side logic needs a literal boolean, that coercion belongs on the caller's side, or needs a separate, explicit ask. If this assumption is wrong, the AC2/AC4 wording and the two tool bodies in both repos need one extra line each (`is_assignable = bool(result.get("isAssignableToRole"))`) — a small, reversible change.
- [non-blocking] Whether `isAssignableToRole` can be read via `$select` under the already-granted `Group.Read.All` scope (no extra Graph permission) is assumed based on `Group.Read.All` already covering the rest of the group object's properties in the same `$select`; this is not independently re-verified against Microsoft's live documentation in this design leg (see Current state). If a live/sandbox tenant test (TC11, manual, see Test cases) surfaces a permission error instead of the property, the fix is a README permission-column update, not a code change — low risk either way.
- [non-blocking] The exact relationship with PRD-21647 (which connector(s) it actually covers) is explicitly unresolved in the ticket itself and needs human reconciliation (Don vs. the retrieved PRD-21647 description disagree). This design does not depend on the answer: it only ever adds `isAssignableToRole` to `graph_get_group`/`graph_list_user_groups` in both connectors, which is a strict subset of what either reading of PRD-21647 would also do to the same two tools, so there's no behavior to undo whichever way that reconciliation lands. See Tech design §11 for the git-level mechanics of this (idempotent `$select` addition, trivial merge either order).

## Tech design

### Conclusion

In both `ms-graph-mcp` and `gdap-mcp`, add `isAssignableToRole` to the existing `$select` list of `graph_get_group` and `graph_list_user_groups` in `groups.py`, and update each tool's docstring and the `ms-graph-mcp` README tool-table row to mention it. No new tool, no new parameter, no new permission, no schema/DB change, and — because `gdap-mcp`'s `graph_tools/groups.py` is a copy of `ms-graph-mcp`'s with `customer_tenant_id` injected centrally by `registry.py`'s `_wrap` — the same four-line `$select` edit is the entire GDAP-side change too.

### Option analysis

No real alternative: the requested data is a single documented Microsoft Graph group property, already exposed by every other field in the same `$select`, on tools that already return the sibling fields the ticket asks to confirm. The only decision with more than one reasonable answer is the `null`-vs-`false` passthrough question, covered as Open Questions / Decision below rather than as a competing implementation option.

| Decision | Approach | Pros | Cost | Verdict |
|---|---|---|---|---|
| Passthrough raw `isAssignableToRole` (may be `true`/`false`/`null`) | Add the field name to `$select`; no post-processing | Matches how every other field in these two tools is already handled (no precedent for deriving booleans here except `sync_source`, which exists only because `onPremisesSyncEnabled` needed a human-readable label, not because raw booleans need normalizing); zero extra code | Response literally says `null` for most ordinary groups, not the literal `false` the ticket's AC2 wording expects | **Chosen** — see Open Questions |
| Derive a normalized boolean (e.g. coerce `null`→`false`, maybe rename to a new field) | Add an `is_assignable_to_role: bool` convenience field alongside the raw one, mirroring `sync_source`'s derivation pattern | Literally matches AC2's wording; one obvious true/false the caller can test without knowing Graph's `null` quirk | A second field name to maintain and document; `sync_source`'s derivation exists because the raw field needed string labeling, not boolean coercion — adding this here would be inventing a convention the rest of the file doesn't have, for a case where the raw value is already directly truthy-testable (`if not group.get("isAssignableToRole"): ...`) | **Rejected** (for now) — see Open Questions for how to flip this if the raw-`null` behavior turns out to be a real problem for the caller |

### Key flow / sequence

**Microsoft Graph connector (`ms-graph-mcp`), `graph_get_group`:**
1. Caller → `graph_get_group(group_id)`
2. Tool → Graph: `GET /groups/{id}?$select=...,isAssignableToRole` (new field appended)
3. Graph → Tool: group object, now including `isAssignableToRole` (`true`/`false`/`null`)
4. Tool derives `sync_source` (unchanged) and returns the object as-is (no new derivation for the new field)

**Microsoft 365 GDAP connector (`gdap-mcp`), `graph_get_group`:**
1. Caller → `graph_get_group(customer_tenant_id, group_id)` (the `customer_tenant_id` parameter is injected by `registry.py`'s `_wrap`, not part of the copied function body)
2. `registry._wrap`'s `wrapper` → `toolrun.run(..., customer_tenant_id=customer_tenant_id, graph=True, ...)` — tenant/customer-token resolution and audit happen here, **unchanged by this ticket**
3. `toolrun._run_graph` → the copied `graph_get_group` body (same code as `ms-graph-mcp`, same new `$select` field) against that customer's Graph endpoint
4. Same response shape as the single-tenant case, scoped to that customer tenant

`graph_list_user_groups` follows the same two shapes, substituting the paginated `/users/{id}/memberOf` call.

### Non-functional

- **Idempotency/concurrency**: unchanged — both tools are already read-only (`readOnlyHint=True`, `idempotentHint=True`); adding a field to a read does not change this.
- **Performance**: negligible. No extra Graph round-trip in either tool; one more property name in an existing `$select` string adds a few bytes to the request URL and a boolean per group to the response — well within `dump_json_capped`'s 20,000-char cap (`ms-graph-mcp/src/graph_mcp/_json.py:11-20`; `gdap-mcp` uses the same capped-dump pattern via its own `_json.py`), which truncates whole list items under pressure, not individual fields, so this does not change truncation behavior for realistic group counts.
- **Security**: `isAssignableToRole` is itself a security-relevant classification (it is the whole point of this ticket — letting a caller *avoid* silently granting administrator-capable group membership). No new sensitive data is logged: `toolrun._redact` (`gdap-mcp/app/toolrun.py:30-41`) redacts by argument name, not response content, and this change adds a response field, not an argument — unaffected either way. No credential or token handling changes in either repo.
- **Multi-tenant isolation**: `ms-graph-mcp` is single-tenant per call (its own README: "The server itself holds no credentials" — tenancy comes entirely from the caller's access token) and is unaffected. `gdap-mcp`'s tenant scoping is enforced once, centrally, by `toolrun.run`/`customers.resolve` based on `customer_tenant_id` — this ticket adds a response field to code that already runs inside that scoping, so it inherits the existing isolation guarantee rather than needing a new one. AC7 is this ticket's concrete regression check that this remains true.
- **Observability**: no new logging needed; `gdap-mcp`'s existing `gdap_audit` row per call (`toolrun.py`) already records every `graph_get_group`/`graph_list_user_groups` call per tenant, unaffected by the response growing one field.

### Rollout & rollback

No feature flag — purely additive, deterministic field, not a gradual-rollout feature. Each repo follows the MCP vendor track (`references/mcp-track.md`): a `dev/PRD-21676` work branch, dev-leg self-test, merge to the repo's own default branch (`master` for `ms-graph-mcp`, `main` for `gdap-mcp`) and an independent `/api/deploy-int` publish per repo, done by the review leg after code review passes — **not** by this design leg. **Release order: `any`** — the two repos are independent deployables (GDAP's copy does not import from or call the single-tenant connector) with no new header, field or parameter that one side needs the other to already understand; each repo's own existing tools, and each other's unrelated tools, are unaffected regardless of which repo ships first (`references/mcp-track.md` §1.2).
