## Requirement understanding

One line: Add a graph_get_security_defaults_policy tool to the Microsoft Graph connector so an agent can read whether a tenant's Security Defaults are enabled, closing gap item 13 of the Rewst-to-MSPbots migration register.

This ticket is item 13 of `mspbots-gap-register.xlsx` (Rewst account Ginko IT). Rewst's `[REWST - PROC] Detailed MFA Reporting` flow (1616 runs in the last 365 days, evidence grade A) calls `GET https://graph.microsoft.com/v1.0/policies/identitySecurityDefaultsEnforcementPolicy` (Rewst's own implementation happens to call the beta endpoint) to get `isEnabled` and `displayName`, and uses that to decide what to say in an MFA report. The requester checked all 43 Microsoft Graph tools plus the 51 GDAP tools in this connector and found no tool that reads this policy, so the ask is a straight gap-fill: one new read-only tool, no change to any existing tool.

## Product design

### Goals / Non-goals

**Goals:**
- Add one new read-only MCP tool, `graph_get_security_defaults_policy`, that lets an agent workflow (replacing the Rewst "Detailed MFA Reporting" flow, and any future consumer) check whether Microsoft Entra Security Defaults are enabled for the tenant the caller's token belongs to.
- Keep the tool's shape, error handling, and documentation consistent with every other tool in this connector, so an agent that already knows how to call `graph_list_domains` needs no new mental model for this one.

**Non-goals:**
- Not adding a tool to *change* Security Defaults (enable/disable) — the ticket and the Rewst flow it replaces are both read-only ("MFA reporting"). A write tool is a different, unasked-for capability.
- Not adding Conditional Access policy tools, authentication methods policy tools, or any other tenant policy beyond the one named in the ticket. The new `policies` module (Tech design) is a domain with room to grow, but this ticket populates it with exactly one tool.
- Not verifying the `Policy.Read.All` grant against a real tenant during design — no test tenant is available to this leg; the dev leg's self-test runs against the repo's existing fake-client test harness, same as every other tool here (see "缺厂商测试账号不算阻塞", `mcp-track.md` §3).

### Acceptance criteria

- **AC1 (happy path):** Given a valid `X-Ms-Graph-Token` with `Policy.Read.All`, when the caller invokes `graph_get_security_defaults_policy` with no arguments, then the tool returns a JSON object containing at least `isEnabled` (boolean) and `displayName` (string) for that tenant's Security Defaults policy, sourced from `GET /policies/identitySecurityDefaultsEnforcementPolicy`.
- **AC2 (no parameters):** The tool takes zero arguments — the tenant is implied by the caller's token, exactly like `graph_list_gdap_roles` and `graph_check_license_stock`. There is no `tenant_id` or similar parameter to get wrong.
- **AC3 (missing/absent token):** If the tool is ever invoked without a resolvable per-request Graph client (the defensive branch — normal `/mcp` traffic is already rejected with `401` by the existing middleware before reaching any tool), it returns the same `NO_TOKEN` structured envelope every other tool in this connector returns, not an unhandled exception.
- **AC4 (upstream Graph error):** If Graph returns an error (403 — token lacks `Policy.Read.All`; 401 — expired/invalid token; 429 — rate limited; 5xx — upstream failure), the tool surfaces it as the connector's standard structured error envelope (`{"error": {"code", "message", "retryable"}}` via `GraphError.to_envelope()`), with the same code/retryable mapping every other tool already gets from `api_client._classify` — no new error-mapping logic needed or wanted.
- **AC5 (per-tenant isolation):** Two concurrent calls to this tool, one per request context, each carrying a different tenant's token, each return that tenant's own policy value with no cross-contamination — relying on, and exercising, the connector's existing per-request `contextvars` isolation (`server.py`'s `GatewayTokenMiddleware` / `_gateway_token_var`), not anything new this ticket has to build.
- **AC6 (documented and discoverable):** The new tool is registered in `tools/list`, has a row in README's Tools table (Required Scope `Policy.Read.All`), has an entry in `docs/gdap-role-map.yaml` with a non-empty note, and the repo's own three-way consistency test (`tests/test_gdap_role_map.py::test_gdap_role_map_matches_registered_tools_and_readme`) passes with the updated count.

### Open questions

- **Q1 — exact least-privileged GDAP/Entra directory role for reading this policy (not blocking).** Microsoft's permissions-reference page confirms `Global Reader` has `microsoft.directory/policies/standard/read`; the fetched excerpt of the `Security Reader` role's resource-action table was truncated and did not conclusively list (or rule out) the same action for `Security Reader`. This repo's own convention (e.g. `graph_update_user`'s and `graph_list_user_roles`'s `docs/gdap-role-map.yaml` notes) is to write the best-supported role and flag it as unverified rather than block on it. **Decision made for this ticket:** list the GDAP role as `Security Reader` (the standard least-privileged role for reading tenant security configuration, and the one a GDAP-scoped MSP relationship would realistically hold) with an explicit note that the exact role has not been confirmed against Microsoft's GDAP task-to-role mapping table or a real tenant, and should be verified the same way `graph_list_user_roles`'s note (3) flags its own unverified scope assumption. This does not block implementation: the tool's actual permission check at runtime is Graph's own (`Policy.Read.All` via the bearer token), not this connector's role-map file — the role-map is documentation for GDAP-scoped MSPs picking a role to grant, and being off by one role (e.g. if it turns out to need `Global Reader` instead) does not change what the tool does, only what the README recommends granting.
- **Q2 — `v1.0` vs `beta` endpoint (not blocking, decided).** The ticket notes Rewst's own flow calls the `beta` version of this endpoint. Microsoft Learn confirms the `v1.0` (GA) endpoint exists, returns the same shape, and is the version every other tool in this connector uses (`api_client.DEFAULT_BASE_URL`, `config.graph_base_url` are both `v1.0`; there is no precedent anywhere in this repo for a tool hard-coding `beta`). **Decision:** use `v1.0`, not `beta`. Rewst calling `beta` reflects Rewst's own implementation choice, not a Microsoft requirement — nothing in the identitySecurityDefaultsEnforcementPolicy resource is beta-only.

### Option analysis

**Where does the new tool live — a new `policies.py` module, or inside an existing module?**

- Considered: adding it to `domains.py` (also a "miscellaneous tenant-wide GET" file) or `users.py` (closest to "security" conceptually, since it already has `graph_list_auth_methods`).
- Chosen: a new `policies.py` module. Reasoning — `domains.py` is about verified sign-in domains, a different Graph resource family (`/domains`) with no conceptual overlap with `/policies/*`; `users.py` is per-user, while this tool is tenant-wide with no `user_id` parameter, which would make it the one parameter-less tool in an otherwise all-per-user file. The repo's own module boundary is "one Graph resource family per file" (`domains.py` → `/domains`, `gdap_roles.py` → the static role map, `licenses.py` → `/subscribedSkus` + license assignment). `/policies/*` is Graph's own resource family name, and Graph has other policy sub-resources (authorization policy, authentication methods policy, Conditional Access) a future ticket could add here without re-litigating where they go. This mirrors `gdap_roles.py` being spun out as its own module for the same reason rather than bolted onto `users.py`.
- Not chosen: a one-off function added to `domains.py` with a comment explaining it doesn't fit — rejected because it would make `domains.py`'s name misleading and set a precedent that "small tools get appended to whatever file already exists" instead of being named for what they read.

**`$select` vs full object.**

- Chosen: `$select=id,displayName,description,isEnabled` (the full resource — it has only four fields total, per the Graph docs response shape, so `$select` buys nothing here beyond making the intent explicit and matching the `domains.py` precedent of always passing `$select`). Returning `description` as well as the two fields the ticket's flow actually uses (`isEnabled`, `displayName`) costs nothing (the string is static Microsoft boilerplate, not large) and avoids the next caller filing another gap-register ticket to add a field that was already available.
- Not chosen: hand-picking only `isEnabled` and `displayName` to minimize payload — rejected because the policy object has exactly four fields and is never going to be large enough for `dump_json_capped`'s truncation logic to matter; narrowing further has no token-budget benefit and risks a future "why doesn't this tool return `id`" ticket.

### Data & API contract

**Tool:** `graph_get_security_defaults_policy`
**Parameters:** none.
**Upstream call:** `GET {graph_base_url}/policies/identitySecurityDefaultsEnforcementPolicy?$select=id,displayName,description,isEnabled` (default `graph_base_url` is `v1.0`; sovereign-cloud overrides apply automatically via `Settings.graph_base_url`, same as every other tool).

**Success response** (JSON string, via `dump_json_capped`):
```json
{"id":"00000000-0000-0000-0000-000000000005","displayName":"Security Defaults","description":"Security defaults is a set of basic identity security mechanisms recommended by Microsoft...","isEnabled":true}
```
(Example values from Microsoft's own documented response.)

**Error response** (same shape as every other tool):
```json
{"error":{"code":"unauthorized","message":"...","retryable":false}}
```

**Backward compatibility:** purely additive — a new tool, no change to any existing tool's request or response shape, no schema migration (this connector has no database).

### Key flow / sequence

1. Agent client sends `tools/call` for `graph_get_security_defaults_policy` with `X-Ms-Graph-Token: <token>` on the `/mcp` request.
2. `GatewayTokenMiddleware` (unchanged) validates the header is present, stores the token in the per-request `contextvars.ContextVar`, forwards the request.
3. FastMCP dispatches to `policies.py`'s registered tool function.
4. The tool calls `client_factory()` → `get_client_from_context(settings)` → a fresh `GraphClient(token, settings.graph_base_url)` scoped to this request/task only (no change to this mechanism).
5. `GraphClient.get("/policies/identitySecurityDefaultsEnforcementPolicy", params={...})` → Graph API → `200 OK` with the policy object, or a `4xx`/`5xx` that `_raise_for_status` turns into a `GraphError`.
6. Tool returns `dump_json_capped(result)` or `e.to_envelope()`.

No new sequence, no new state, no persistence — this is the same five-step flow every read-only tool in this connector already follows.

### Non-functional

- **Idempotency / concurrency:** `readOnlyHint=True, idempotentHint=True` — a pure `GET`, safe to retry, safe to call concurrently. No state shared across calls (see AC5 / per-request `contextvars` isolation, which this tool relies on but does not modify).
- **Performance:** single Graph API call, no pagination (singleton resource), response is four small fields — well under `dump_json_capped`'s 20,000-char cap; no performance concern.
- **Security:** credentials are never read from anywhere but the per-request `X-Ms-Graph-Token` header (unchanged mechanism); the tool never logs the token (inherited from `GraphClient`, which only ever puts it in the `Authorization` header); no new attack surface — this is a read of a single, non-sensitive-beyond-tenant-scope boolean setting, already gated by Graph's own `Policy.Read.All` permission check, which this connector does not and cannot bypass (it has no credentials of its own).
- **Multi-tenant isolation:** relies entirely on the existing `GatewayTokenMiddleware` / `_gateway_token_var` contextvar mechanism (`server.py:15-18,27-44`), which is already the isolation boundary for all 45 existing tools; AC5 / the new test case exercise it for this tool specifically rather than re-verifying the mechanism itself.
- **Observability:** no new logging added; errors surface through the existing structured `GraphError.to_envelope()` path, consistent with every other tool, so existing observability (if any is layered on top of tool-call envelopes) is unaffected.
