## Requirement understanding

One line: Add a graph-mcp tool that lists all of a tenant's Conditional Access policies (state, conditions, grant/session controls) so MSPbots can detect policy changes and produce MFA reports, the way Rewst's existing automations do today.

The ticket is sourced from `mspbots-gap-register.xlsx` (Rewst → MSPbots migration gap list), item 11, Rewst account "Ginko IT". It is a "tool gap" against an existing connector, not a request for a new connector: Microsoft Graph already exists in MSPbotsAIFramework as `ms-graph-mcp` with 43 tools. Two Rewst flows on this account call `GET /identity/conditionalAccess/policies` (the ticket notes Rewst itself calls both the `beta` and `v1.0` versions) and use the result to (a) diff against the last snapshot and generate an LLM-written change narrative, and (b) produce MFA reporting:
- "[REWST - PROCESS] Notify on Conditional Access Changes" — 2,408,319 runs in the last 365 days (evidence grade A per the ticket).
- "Detailed MFA Reporting" — 1,616 runs in the last 365 days.

The ticket states the reporter cross-checked both `ms-graph-mcp` (43 tools) and the GDAP connector (51 tools, a different repo — see Tech design §2) tool-by-tool and found no equivalent tool in either.

## Product design

### Goals / Non-goals

Goals:
- Add one new read-only tool, `graph_list_conditional_access_policies`, to `ms-graph-mcp` that lists a tenant's Conditional Access policies with the fields the two cited Rewst flows need: `id`, `displayName`, `state`, `createdDateTime`, `modifiedDateTime`, `conditions`, `grantControls`, `sessionControls`.
- Document the new tool, its required scope (`Policy.Read.All`), and its GDAP role in `README.md`'s Tools table and `docs/gdap-role-map.yaml`, following the existing per-tool conventions.

Non-goals:
- No Conditional Access policy create/update/delete tool. The ticket's two cited Rewst flows only read and diff; no write capability was requested.
- No "diff against last snapshot" or "LLM-generated change narrative" logic in this repo. Every existing `graph_list_*` tool in this repo returns current state only, never a diff; the diff/narrative step described in the ticket is Agent-Platform-side orchestration built on top of the raw list this tool returns, not a capability any tool in this repo provides today.
- No change to `MCP-Management-Service`'s OAuth scope registration or tenant re-consent flow in this ticket (different repo, not this ticket's Code Repo). See Tech design §8 and Rollout & rollback for why this is a flagged, non-blocking dependency rather than in-scope work.

### Acceptance criteria

- AC1: Given a caller holds a valid Graph access token with `Policy.Read.All` consented for the tenant, When they call `graph_list_conditional_access_policies` with no arguments, Then the response lists every Conditional Access policy in the tenant, each with `id`, `displayName`, `state`, `createdDateTime`, `modifiedDateTime`, `conditions`, `grantControls`, `sessionControls`, plus a `count`.
- AC2: Given a tenant has zero Conditional Access policies, When the tool is called, Then it returns `count: 0` and an empty `policies` list — not an error.
- AC3: Given the caller passes `state="enabled"` (or `"disabled"` / `"enabledForReportingButNotEnforced"` — Graph's three documented values), When the tool is called, Then only policies whose `state` matches the argument are returned.
- AC4: Given the caller's token does not have `Policy.Read.All` consented yet, When the tool is called, Then it returns the same structured error envelope every other tool in this repo returns on a 403 (`GraphError.to_envelope()`), not a stack trace and not an ambiguous "tool does not exist" symptom.
- AC5 (permissions / multi-tenant, required by the quality line): Given a caller's token is scoped to tenant A (the existing per-request `get_client_from_context()` / `GatewayTokenMiddleware` contextvar wiring every tool already uses, `src/graph_mcp/server.py:13-18,28-65`), When `graph_list_conditional_access_policies` is invoked, Then there is no parameter or code path that lets the caller target a different tenant's policies — isolation is enforced entirely by the existing per-request credential wiring, not by any new logic this ticket adds.

### Open questions

- [not blocking] Should the tool expose a caller-facing `$select` (the way `graph_list_domains` does not, but Rewst's own cited usage names "$filter / $select" as generic optional inputs)? Default: no — v1 always requests the fixed 8-field `$select` the two cited Rewst flows need (see Data & API contract); add a caller-facing `$select` later only if a real conversation needs a lighter response shape.
- [not blocking] Should `state` be a server-side Graph `$filter` instead of a client-side Python filter? Default: client-side, matching `graph_list_domains`'s `verified_only` pattern (Tech design §3) — avoids depending on undocumented server-side `$filter` support for this Graph resource.
- [needs a human, non-blocking for design but blocking for go-live] `graph_list_conditional_access_policies` needs `Policy.Read.All`, a Graph permission not currently in the platform's requested scope set. Granting it and getting already-connected tenants to re-consent is a `MCP-Management-Service` change — outside this ticket's repo and Code Repo, and not actionable by this ticket's implementer alone. This is fully specified (exact scope string, exact mechanism, four prior precedents in this same repo — PRD-19103, PRD-18631, PRD-20422, PRD-20480), so it is a sequencing dependency flagged at rollout time, not a design blocker. See Tech design, Rollout & rollback for why this follows PRD-20480's precedent rather than a `[BLOCKED]`/Leo hand-off.

## Tech design

### Conclusion

Add one new module, `src/graph_mcp/tools/policies.py`, with a single read-only tool, `graph_list_conditional_access_policies`, following the exact shape of `graph_list_domains` (`src/graph_mcp/tools/domains.py`): one `GraphClient.get()` call to `/identity/conditionalAccess/policies`, a fixed `$select` of the 8 fields the ticket's two cited Rewst flows need, an optional client-side `state` filter, and `GraphError` pass-through on failure. Register it in `server.py` next to the other 8 tool domains. This is additive only — no existing tool, scope, or GDAP role entry changes.

| A. ### Data & API contract

**Upstream (Microsoft Graph)**: `GET https://graph.microsoft.com/v1.0/identity/conditionalAccess/policies?$select=id,displayName,state,createdDateTime,modifiedDateTime,conditions,grantControls,sessionControls`. Permission: `Policy.Read.All` (delegated or application). No request body. Errors use the existing Graph error mapping in `api_client.py` (401/403 → `unauthorized`, 404 → `not_found`, 429 → `rate_limited`, 5xx → `upstream_error`).

**This tool's MCP contract**:
- Input: `state: "enabled" | "disabled" | "enabledForReportingButNotEnforced" | null` (optional; omitted or `null` returns all policies regardless of state).
- Output (success), example:
  ```json
  {
    "count": 1,
    "policies": [
      {
        "id": "a1b2c3d4-...",
        "displayName": "Require MFA for all users",
        "state": "enabled",
        "createdDateTime": "2025-01-10T12:00:00Z",
        "modifiedDateTime": "2026-09-01T08:30:00Z",
        "conditions": {"users": {"includeUsers": ["All"]}, "applications": {"includeApplications": ["All"]}},
        "grantControls": {"operator": "OR", "builtInControls": ["mfa"]},
        "sessionControls": null
      }
    ]
  }
  ```
- Output (error): the existing `error_envelope(code, message, retryable)` shape every other tool returns via `GraphError.to_envelope()`, e.g. `{"error": "unauthorized", "message": "...", "retryable": false}`.

**Backward compatibility**: purely additive — new tool, new README row, `Policy.Read.All` added to a scope *union* (existing scopes untouched), new `gdap-role-map.yaml` entry. No existing tool's request/response shape changes.

**DB**: none — this server is stateless (`README.md:141`, "Rollout = deploy the new image").

### Key flow / sequence

1. Agent Platform calls `graph_list_conditional_access_policies` (optionally with `state`) through the MCP `/mcp` endpoint, `X-Ms-Graph-Token` header carrying the tenant's Graph access token.
2. `GatewayTokenMiddleware` (`server.py:28-65`) extracts the token into the per-request contextvar; `get_client_from_context()` builds a `GraphClient` scoped to that token only.
3. The tool calls `GraphClient.get("/identity/conditionalAccess/policies", params={"$select": ...})`.
4. Graph returns `{"value": [...]}`; the tool optionally filters by `state` in Python, wraps the result as `{"count", "policies"}`, and returns it via `dump_json_capped`.
5. On any Graph error (most commonly 403 before the tenant has `Policy.Read.All` consented — see Rollout & rollback), `GraphError.to_envelope()` returns the structured error instead of raising.

### Non-functional

- **Idempotency & concurrency**: read-only GET, naturally idempotent. No shared mutable state — the module-level `httpx.AsyncClient` connection pool is already documented as safe across concurrent tenants (`api_client.py`'s own comment: credentials travel per-request, never stored on the pool).
- **Performance**: one Graph call per invocation; Conditional Access policy counts are small (tens, not thousands) for every tenant shape this repo has documented, so no pagination or streaming concern (see Option analysis, Option C).
- **Security**: no new credential handling — same per-request bearer-token forwarding every tool already uses. `Policy.Read.All` is read-only; this ticket adds no write/delete capability.
- **Multi-tenant isolation**: enforced entirely by the existing per-request `GatewayTokenMiddleware`/contextvar wiring (`server.py:13-18`); this tool adds no tenant-id parameter and has no code path that could target a tenant other than the one whose token was presented. Same guarantee AC5 states.
- **Observability**: `GraphError` pass-through already carries `status_code`/`message`; no new logging is needed beyond what every other tool already gets from the shared `GraphClient`.

### Rollout & rollback

- No DB, no feature flag (server is stateless, `README.md:141-142`). Rollout = land the PR, merge to `master`, deploy the new image, publish to INT (review leg, per `references/mcp-track.md` §4).
- **This tool will return a 403 for every tenant until `MCP-Management-Service`'s `auth/oauth/vendors/msgraph.py` adds `Policy.Read.All` to the requested delegated/application scope set, and every tenant that already connected the Microsoft Graph connector re-authorizes.** This is the exact rollout shape already used four times in this repo — `Mail.Read` (PRD-19103), `Calendars.ReadWrite` (PRD-18631), `Synchronization.ReadWrite.All` (PRD-20422), `UserAuthenticationMethod.ReadWrite.All` + `Group.ReadWrite.All` (PRD-20480) — a known, repeatable process, not a new risk class.
  Per `references/mcp-track.md` §2.3, an OAuth-scope change in a control-plane repo (`MCP-Management-Service`) would normally route to Leo Yang. PRD-20480 (same repo, same shape of dependency — two new Graph scopes needed for two new tools) instead landed the vendor-repo tool and flagged the scope grant as a **non-blocking, sequencing-only Open Question**, not a `[BLOCKED]` hand-off, because the vendor-repo work itself (adding, testing, and reviewing the tool) is fully doable without the scope grant — only *live, 200-response* verification on a real tenant is blocked until the scope lands (`docs/tickets/PRD-20480.md:69,143,159`, read on this branch). This ticket follows that same precedent.
- Rollback: `git revert` of the merge commit. No data migration, no backward-incompatible change to undo.
