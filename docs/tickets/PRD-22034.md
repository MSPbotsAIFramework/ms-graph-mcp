## Requirement understanding

One line: Add three read-only tools to the ms-graph connector -- graph_list_teams, graph_list_channels, graph_get_channel -- so any SOP agent can discover a Microsoft Teams team and channel (with paging, a membership-type filter, and an explicit empty email value instead of a failure), with a clear error when the tenant has not consented to the needed Graph scope, before any send/preview capability is added.

This is slice A of the parent request PRD-22030 ("Teams channel tools for SOP agents"): the platform-wide root need is that on-shift teams get actionable notifications even when no individual owns the work, but today no tool can even find the team or channel to notify. Slice A delivers only the three reads; slice B (preview + send with an allowlist, a separate ClickUp card, id 1dfhfaqak4y) is explicitly out of scope here and is blocked on this card ("blocks" relationship) because it will need the team_id/channel_id these reads return. The description has 7 binary Done-when items (paging, a membership-type filter, an explicit-empty email, a named-scope consent error, own-tenant-only, independent per-tool switches with no send tool enabled, and a dev comment naming the least scopes); the spec check (comment #1600390000055652, 2026-11-09) passed all 9 definition-of-ready points and moved the card straight to 5b for Dev01 design, confirming Code Repo is this ticket's job to fill in.

## Current state (every claim carries path:line, read at ms-graph-mcp@master 9d3291d)

- **No Teams team/channel tool exists in this connector today.** `src/graph_mcp/server.py:116-148` registers 15 tool modules (users, groups, licenses, mail, sites, devices, domains, applications, calendar, offboarding, gdap_roles, invitations, conditional_access, policies, service_principals); there is no `teams.py` module and no `graph_list_teams`/`graph_list_channels`/`graph_get_channel` tool anywhere in `src/graph_mcp/tools/`. A full-repo search for "team" or "channel" (`grep -rniE "team|channel" src/ README.md`) only turns up unrelated references: a Teams-meeting-link option on `graph_create_calendar_event` (`src/graph_mcp/tools/calendar.py:224,261`) and a note that a Team is backed by an M365 Group (`src/graph_mcp/tools/groups.py:72-80`). This matches the ticket's own premise ("the ms-graph connector has no Teams team or channel tools today") exactly.
- **The connector is gateway mode with per-request tenant isolation already in place.** The caller's Azure access token is read from the `X-Ms-Graph-Token` header per request and stored in a `contextvars.ContextVar` for the lifetime of that request/task (`src/graph_mcp/server.py:14-24,28-66`); the server holds no credentials of its own. The FastMCP `instructions` string already states "All tools act on the caller's own tenant via a per-request token; no cross-tenant access" (`src/graph_mcp/server.py:105-106`). Every new tool inherits this isolation automatically -- there is nothing Teams-specific to add for tenant scoping.
- **Pagination, error handling and "explicit empty value" already have one established shape each**, reused by every list/get tool in this repo:
  - `skiptoken()` in `src/graph_mcp/tools/_common.py:22-32` pulls `$skiptoken` out of Graph's `@odata.nextLink`; every paginated tool (`graph_list_user_groups`, `graph_list_groups`, `graph_list_group_members` -- `src/graph_mcp/tools/groups.py:124-186,200-260,400-460`; `graph_list_conditional_access_policies`-adjacent `graph_resolve_named_location` -- `src/graph_mcp/tools/conditional_access.py:55-101`) takes a `page_token` input, sends it back as `$skiptoken`, and returns `has_more`/`next_page_token` computed from whether a new skiptoken came back. All of them take an input `page_size`/`max_results` with `_DEFAULT_MAX_RESULTS = 50` and `_HARD_CAP_MAX_RESULTS = 200` (`src/graph_mcp/tools/groups.py:18-20`).
  - `GraphError` (`src/graph_mcp/api_client.py:34-67`) classifies a Graph HTTP status into `(code, retryable)` via `_STATUS_TO_CODE` (403 -> `("unauthorized", False)`) and `.to_envelope()` turns it into `error_envelope(code, message, retryable)`. **Today a 403 just forwards Graph's own message** -- it does not name which scope is missing. Three existing tools already document (in their own docstring, not in the error payload) that they 403 until a scope is added and the tenant re-consents: `graph_list_conditional_access_policies` ("Needs Policy.Read.All, not yet in the platform's requested scope set -- calls return 403 until the tenant re-consents, see README" -- `src/graph_mcp/tools/policies.py:19-30,29-30`), `graph_create_tap`/`graph_delete_auth_method` and `graph_add_group_owner` (README rows, `README.md:152,155`), `graph_service_principal_create_and_add_password` (`src/graph_mcp/tools/service_principals.py:89`). None of them puts the scope name in the error the caller actually gets back -- the scope is only in the README and the docstring, which the calling agent never reads. Done-when 4 of this ticket is a new requirement, not an existing pattern to copy as-is (see Tech design S3/S4).
  - `error_envelope(code, message, retryable, extra=None)` (`src/graph_mcp/_json.py:76-88`) already supports an `extra` dict merged into the error object "so a caller can branch on structured context ... without parsing `message`" (added for PRD-20413) -- this is the hook Done-when 4 needs, no change to the shared function required.
  - The "explicit empty value, never a missing key" idiom is already used throughout the repo as `result.get("<field>") or ""` (e.g. `src/graph_mcp/tools/sites.py:84,479`, `src/graph_mcp/tools/offboarding.py:121,132,134`).
- **Scope rollout is a two-step, platform-then-tenant process, already documented and repeatable.** Every time this repo has needed a Graph permission it did not already have, the pattern (`README.md:227,233,235,239` -- the "scope union notes") has been: (1) the platform side adds the scope to the requested set in `auth/oauth/vendors/msgraph.py` in `MCP-Management-Service` (**outside this repository**), then (2) every tenant that already connected the Microsoft Graph connector must re-consent once; until step 2, the new tool keeps returning 403/`unauthorized`. This repo's own code never performs step 1 or 2 -- it only documents which scope a tool needs. `Team.ReadBasic.All` and `Channel.ReadBasic.All` (and possibly `ChannelSettings.Read.All`, see Tech design Open question) are new scopes by this same definition and will need the same two-step rollout; that rollout is outside this ticket's Code Repo and is not something this connector's code can do or verify by itself.
- **Every registered tool needs a matching row in two more files, enforced by a test.** `docs/gdap-role-map.yaml` (header comment: "One entry per tool this server registers (enforced by tests/test_gdap_role_map.py)") and `README.md`'s Tools table must each have exactly one row per tool, and the GDAP role values in both must match (`tests/test_gdap_role_map.py:41-68`, `check_consistency()`). The same test also hardcodes the current tool count: `assert len(role_map) == 53` (`tests/test_gdap_role_map.py:72`). Adding 3 tools without updating this constant and the two tables fails the gate immediately -- this is the sharpest trap in this change and is called out explicitly in the change list below.
- **Per-tool on/off switches are a platform (MCP Admin / Agent Connectors panel) feature, not something this repo implements.** Confirmed against the product fact base: expanding a connector row in an agent's `Connectors` section opens a per-tool authorization panel where "every tool [gets] its own switch" and toggling one restarts the agent to apply the change (wiki: `ProductDocs/11-SOP-Agents.md` S "Connector row expands into a tool-level authorization panel (depth: actions)", walked 2026-09-15 per `ProductDocs/Changes/2026-09-15-2.md`, no `_verified_` tag on this excerpt -- treated as current but not re-verified today; walked on ClickUp as the example connector, and separately confirmed Microsoft Graph specifically renders a connector detail view with a per-tool list, `ProductDocs/15-Capabilities.md` S "Connector detail view", _verified_ 2026-08-31 v4.1.518). This means Done-when 6 is satisfied automatically the moment the three tools are registered on the MCP server and the gateway refreshes its tool list -- there is no UI code in this repository to write for it (ms-graph-mcp exposes `transport: streamable-http`/an MCP tool list; the platform renders the switches from that list, not from anything specific to this connector). No send/preview tool exists anywhere in this repository today (confirmed by the module list above), so "turning them on enables no send tool" (Done-when 6) is true by construction, not by a new guard this ticket has to add.

## Product design

### Goals / Non-goals

- **Goal**: an SOP agent (or any other tool caller) can, using only the Microsoft Graph connector, (1) find a team by name or by a user's membership, (2) list that team's channels and filter by membership type, and (3) get one channel's details including an explicit (possibly empty) email -- all read-only, all scoped to the caller's own Microsoft 365 tenant.
- **Goal**: when the tenant has not consented to a Graph permission one of these tools needs, the caller gets back a clear, structured error that names the missing permission and says an admin must re-consent -- not Graph's generic "insufficient privileges" text and not an unhandled exception.
- **Non-goal (out of scope, slice B / PRD-22030 child, id 1dfhfaqak4y)**: sending or previewing a channel message, the channel allowlist, thread replies. No code for any of these is added by this ticket.
- **Non-goal**: a UI/screen. The ticket itself says "No screen. Bugs, MCP and connector-tool cards skip the prototype step" -- there is no product design section 4.2 (interface/interaction) because there is no interface in this repository; the only user-facing surface is the MCP tool contract itself (names, inputs, outputs, error shape) and the existing platform-level per-tool switch panel (Current state, last bullet).

### Acceptance criteria

(Numbered AC1..AC11; each line names which card Done-when (DW1..DW7) it verifies -- see the ticket description's "Done when" list, items counted top to bottom.)

- **AC1** (DW1): Given a tenant with more teams matching `name_prefix` than `page_size`, When `graph_list_teams(name_prefix=..., page_size=<N>)` is called, Then the response has `has_more: true` and a `next_page_token`; calling again with that token returns the remaining matching teams with no duplicate and no gap across the two calls.
- **AC2** (DW1): Given a known test team's display name prefix, When `graph_list_teams(name_prefix=<prefix>)` is called, Then `teams[]` contains that team's `id` and `displayName`.
- **AC3** (DW1): Given a known `user_id` who has joined a known team, When `graph_list_teams(user_id=<id>)` is called, Then `teams[]` contains that team (same `id`/`displayName` shape as AC2).
- **AC4** (DW2): Given a known `team_id` with a known test channel, When `graph_list_channels(team_id=<id>)` is called, Then `channels[]` contains that channel's `id`, `membershipType` and `webUrl`.
- **AC5** (DW2): Given that same team has channels of more than one `membershipType`, When `graph_list_channels(team_id=<id>, membership_type="private")` (or `"standard"`/`"shared"`) is called, Then every returned channel has that exact `membershipType` and no channel of a different type is returned.
- **AC6** (DW3): Given a known channel with a configured email, When `graph_get_channel(team_id=<id>, channel_id=<id>)` is called, Then the response includes that channel's `webUrl`, `isArchived`, and a non-empty `email`.
- **AC7** (DW3): Given a known channel with no configured email, When `graph_get_channel(team_id=<id>, channel_id=<id>)` is called, Then the response's `email` field is present and is the explicit empty string `""` (never a missing key, never `null`, never a tool failure).
- **AC8** (DW4): Given a tenant whose admin consent does not yet cover the Graph permission a tool needs (e.g. `Team.ReadBasic.All` for `graph_list_teams`), When that tool is called, Then the response is a structured error whose message names the missing permission and states that an admin must re-consent -- not a generic/opaque failure.
- **AC9** (DW5): Given the caller's access token is issued for the agent's own Microsoft 365 tenant, When any of the three tools is called, Then only that tenant's data is returned; none of the three tools accepts a parameter that lets the caller target a different tenant.
- **AC10** (DW6): Given the three tools are registered on the ms-graph MCP server, When an admin opens this connector's per-tool authorization panel for an agent, Then each of the three tools appears with its own independent on/off switch (same as every existing ms-graph tool), and turning any or all of them on enables no message-sending tool (none exists in this connector).
- **AC11** (DW7): Given the three tools are implemented, When the dev leg posts its ticket comment, Then it names the exact Graph permission each tool needs and states they are the least set that passes AC1-AC7 (i.e., it does not request a broader scope "just in case").

Assumption this design is built on: request `Channel.ReadBasic.All` only first (least scope); if `email` is consistently missing/erroring under that scope alone against the real test tenant, add `ChannelSettings.Read.All`. This does not block AC7 (the explicit-empty-string behavior is correct either way) and is exactly the kind of thing Done-when 7's "dev comment" and the existing scope-union rollout process (Current state) are for -- it does not change this ticket's shape, only which scope name ends up in the README row and the platform-side request.
- **[already assumed, non-blocking]** Whether `GET /teams` accepts `$filter=startswith(displayName,'<prefix>')` and standard `$top`/`@odata.nextLink` paging the way the reporter's proposed contract assumes, and whether `GET /teams/{id}/channels` returns only `membershipType: standard` channels unless `$filter=membershipType eq '<value>'` is passed, are both standard, documented Microsoft Graph behaviors this design relies on but that this environment cannot call Graph to confirm live. ## Tech design

### Conclusion

Add one new tool module, `src/graph_mcp/tools/teams.py`, registered the same way every existing module is (`src/graph_mcp/server.py:134-148`), reusing this repo's existing pagination helper (`skiptoken()`), error-envelope machinery (`GraphError.to_envelope()`/`error_envelope(..., extra=...)`) and "explicit empty string" idiom. The one genuinely new piece of machinery is a small helper that turns a 403 into a message naming the specific Graph scope the calling tool needs (Done-when 4) -- nothing like that exists yet in this repo (today's 403s only explain themselves in the README, not in the response), so it is added as a 6-line, additive, tool-local helper rather than touched into the shared `GraphError`/`_classify` machinery that every other tool depends on.

### Option analysis

No real alternative was considered for where the code goes -- a new tool module in the existing `src/graph_mcp/tools/` package, following the existing registration and pagination/error conventions, is the only natural fit; everything these three tools need (contextvar-isolated `GraphClient`, `skiptoken`, `error_envelope`) already exists and is reused as-is.

One real choice: **how to surface the missing-scope message (Done-when 4)**.

| Option | How | Pros | Cost | Verdict |
|---|---|---|---|---|
| A: per-tool `except GraphError` + a new small helper | Catch `GraphError` in each of the 3 tools; on `status_code == 403`, return `error_envelope("missing_scope", "<scope> required...", False, extra={"missing_scope": scope})`; otherwise `e.to_envelope()` as today | Additive only -- zero risk to the other 53 tools that already depend on `GraphError`/`_classify`/`.to_envelope()`; the scope name is static per tool (known at call-site, not something Graph tells us), so this is the only place that can supply it | 3 call sites each need the same 4-line except-block (minor duplication, factored into one shared helper, see below) | **Chosen** |
| B: extend `_classify()`/`GraphError` to carry a scope name globally | Add a `required_scope` parameter threaded through every `GraphClient` call | Centralizes the mapping | Touches the one piece of machinery all 53 existing tools already rely on, for a need only these 3 tools have today; the scope needed is a property of the *tool*, not of the *Graph status code*, so a global `_classify()` table (which maps status->meaning, not endpoint->scope) is the wrong layer for it | Rejected -- wrong layer, needless shared-code risk |
| C: let Graph's own 403 body speak for itself (no translation) | Just `e.to_envelope()` like every other tool today | No new code | Does not satisfy Done-when 4 -- Graph's `Authorization_RequestDenied` message does not name a scope; the repo's own precedent (`policies.py:29-30` etc.) is exactly this gap, only papered over by README prose the calling agent never reads | Rejected -- fails the acceptance criterion this ticket exists to deliver |

To avoid writing the same 4-line except-block three times (DRY), the helper is a single function used by all three tools:

```python
# src/graph_mcp/tools/_common.py
def missing_scope_error(e: GraphError, scope: str) -> str:
    """Turn a 403 into an error that names the Graph permission this tool
    needs, instead of Graph's generic "Insufficient privileges" message
    (PRD-22034 Done-when 4). Every other status code keeps today's
    behavior (e.to_envelope()) -- this only changes what a tenant without
    consent for `scope` sees."""
    if e.status_code == 403:
        return error_envelope(
            "missing_scope",
            f"This tool needs the Microsoft Graph permission {scope}. "
            f"An admin must grant consent for {scope} on the Microsoft Graph "
            f"connector, then retry.",
            False,
            extra={"missing_scope": scope},
        )
    return e.to_envelope()
```

Each tool's `except GraphError as e:` becomes `return missing_scope_error(e, "Team.ReadBasic.All")` (or `"Channel.ReadBasic.All"`), one line, same shape as every other tool's `except GraphError as e: return e.to_envelope()`.

### Data & API contract

All three tools call Microsoft Graph v1.0 (`DEFAULT_BASE_URL = "https://graph.microsoft.com/v1.0"`, `src/graph_mcp/api_client.py:8`) through the existing `GraphClient.get()`. No new HTTP methods, no writes.

**`graph_list_teams`**

- Input: `name_prefix: str | None` (prefix match on `displayName`), `user_id: str | None` (list only this user's joined teams), `page_size: int = 50` (same clamp as `groups.py`: `max(1, min(page_size, 200))`, capped to Graph's own `$top` ceiling of 999), `page_token: str | None` (the previous response's `next_page_token`).
- Call:
  - `user_id` given -> `GET /users/{user_id}/joinedTeams`, `$select=id,displayName,description,visibility`, `$top`, `$skiptoken` if `page_token` given. `name_prefix`, if also given, is applied client-side on the returned page (this endpoint has no server-side display-name filter) -- documented in the docstring as a known limitation, acceptable because a single user's joined-teams list is small (rarely multi-page in practice, unlike the tenant-wide `/memberOf` case `groups.py:163-166` already had to special-case for exactly this class of bug).
  - `user_id` omitted -> `GET /teams`, `$select=id,displayName,description,visibility`, `$filter=startswith(displayName,'<odata_quote(name_prefix)>')` if `name_prefix` given, `$top`, `$skiptoken` if `page_token` given.
- Response: `{"count": <int>, "teams": [{"id","displayName","description","visibility"}...], "has_more": <bool>, "next_page_token": <str|null>}`.
- Errors: 403 -> `missing_scope_error(e, "Team.ReadBasic.All")`; everything else -> `e.to_envelope()`.

**`graph_list_channels`**

- Input: `team_id: str` (required), `membership_type: Literal["standard","private","shared"] | None`.
- Call: `GET /teams/{team_id}/channels`, `$select=id,displayName,membershipType,webUrl`, `$filter=membershipType eq '<membership_type>'` when given. (Note for whoever implements/verifies this: Graph's default response for this endpoint without a filter is standard channels only -- `private`/`shared` channels require the explicit filter to appear at all. This is standard, documented Graph behavior this design relies on per the Open Questions above, not a bug in this tool.)
- Response: `{"team_id": <str>, "count": <int>, "channels": [{"id","displayName","membershipType","webUrl"}...]}`. Not paginated (the ticket's proposed contract does not ask for paging here, and a team's channel count is Microsoft-capped well below one Graph page).
- Errors: 403 -> `missing_scope_error(e, "Channel.ReadBasic.All")`; everything else -> `e.to_envelope()`.

**`graph_get_channel`**

- Input: `team_id: str`, `channel_id: str` (both required).
- Call: `GET /teams/{team_id}/channels/{channel_id}`, `$select=id,displayName,description,membershipType,email,webUrl,isArchived`.
- Response: `{"id","displayName","description","membershipType","email","webUrl","isArchived"}`; `"email": result.get("email") or ""` -- always present, never `null`, never a missing key (Done-when 3/AC7).
- Errors: 403 -> `missing_scope_error(e, "Channel.ReadBasic.All")` (Open Questions: escalate to `ChannelSettings.Read.All` if confirmed needed for `email`); everything else -> `e.to_envelope()`.

**Backward compatibility**: purely additive -- three new tool names, no existing tool's input, output or error shape changes. No DB (this connector is stateless, gateway mode, holds no data of its own). No migration.

### Key flow / sequence

```
Agent (SOP or interactive)
  -> graph_list_teams(name_prefix | user_id, page_size, page_token)
       -> GraphClient.get("/teams" | "/users/{id}/joinedTeams", $select, $filter?, $top, $skiptoken?)
       -> Graph API (caller's own tenant, via X-Ms-Graph-Token)
       <- {id, displayName, ...}[] + @odata.nextLink?
       <- {teams, has_more, next_page_token}
  -> graph_list_channels(team_id, membership_type?)
       -> GraphClient.get("/teams/{team_id}/channels", $select, $filter?)
       <- {channels}
  -> graph_get_channel(team_id, channel_id)
       -> GraphClient.get("/teams/{team_id}/channels/{channel_id}", $select)
       <- {..., email: "" | "<address>"}
```

Typical usage (added to `server.py`'s `instructions` string, Change list): `graph_list_teams -> graph_list_channels -> graph_get_channel`, the same discovery chain Done-when 1-3 test in order.

### Non-functional

- **Idempotency/concurrency**: all three tools are pure reads (`readOnlyHint=True, idempotentHint=True` annotation, matching every other read tool, e.g. `src/graph_mcp/tools/policies.py:20`); no shared mutable state, no special handling needed.
- **Performance**: `graph_list_teams` is the only one that can be tenant-wide and large -- covered by the existing paging contract (AC1). `graph_list_channels`/`graph_get_channel` are bounded by Microsoft's own per-team channel cap (in the low hundreds at most), so no pagination or additional throttling is added for them, consistent with the ticket's own proposed contract (no paging params on either).
- **Security**: no new surface -- the token is read the same way, from the same per-request contextvar, as every other tool (Current state); no credential is ever logged or persisted by this connector (unchanged). These are read-only tools; no write capability is introduced, so the "turning a switch on enables no send tool" guarantee (AC10) holds by the absence of any send tool in this repository, not by new code.
- **Multi-tenant isolation**: inherited, not reimplemented -- the contextvar-per-request token model (`server.py:14-24`) already means a call can only ever reach the tenant the caller's own token was issued for; none of the three new tools accepts a tenant identifier as input, so there is no code path that could be made to cross tenants (AC9).
- **Observability**: no new logging added -- consistent with every other read-only list/get tool in this repo (`groups.py`, `policies.py`, `conditional_access.py` do not log; only `mail.py`, which sends mail, does). If a future audit requirement appears, it should be added uniformly across all read tools, not singled out for this one ticket.

### Rollout & rollback

- No feature flag -- this connector has none (confirmed: no flag/toggle mechanism anywhere in `src/graph_mcp`); the platform-level per-tool switch (Current state, AC10) is the only on/off control, and it defaults to whatever the agent's existing connector configuration does for newly-appearing tools (same as every previous tool addition in this repo's history, e.g. PRD-21582/21618/21578 above).
- **Scope rollout is two separate steps outside this repository's control** (Current state, "scope rollout" bullet): (1) `Team.ReadBasic.All`/`Channel.ReadBasic.All` must be added to the platform's requested Graph scope set (`MCP-Management-Service`'s `auth/oauth/vendors/msgraph.py`), then (2) each already-connected tenant must re-consent once. Until both happen, every call to these three tools 403s with the new named-scope error (which is the intended, correct behavior for Done-when 4, not a rollout bug). This ticket's code change does not block on that rollout and does not perform it.
- Rollback: revert the merge commit on the default branch (`master`); no data was written, no migration to undo, no scope to revoke (the platform-side scope request, once made, is independent of this code and is not something this ticket's rollback touches).
