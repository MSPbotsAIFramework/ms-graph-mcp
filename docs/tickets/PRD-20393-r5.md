**COV1/COV2 — `gdap-mcp`'s `graph_remove_manager` never implemented the removed/previous_manager/reason contract.**

`app/graph_tools/users.py:1048-1067` (`gdap-mcp@0a706f3`):
```python
async def graph_remove_manager(user_id) -> str:
    ...
    try:
        await client.delete(f"/users/{user_id}/manager/$ref")
        return dump_json_capped({"status": "removed", "user_id": user_id})
    except GraphError as e:
        if e.status_code == 404:
            return dump_json_capped({"status": "no_manager", "user_id": user_id})
        return e.to_envelope()
```
This is rounds-1-era shape (`{"status": ..., "user_id": ...}`) with no `removed`/`previous_manager`/`reason` keys at all, and it deletes first then infers "no manager" from a 404 on DELETE — exactly the approach `ms-graph-mcp` moved away from in its own round 2 (deleting twice on an already-managerless user does not reliably 404 against a real tenant) and round 3 (a DELETE 404 cannot tell "no manager" from "user does not exist"). Compare the reference at `ms-graph-mcp@999f6f9` `src/graph_mcp/tools/users.py:752-818`: reads the manager first (`GET /users/{id}/manager`), disambiguates a 404 there with a plain existence check, and only then calls DELETE — see Tech design for the full reference.

**COV3 — `gdap-mcp`'s `graph_get_user` default `$select` is missing four fields.**

`app/graph_tools/users.py:38-47` (`_USER_PROFILE_SELECT`, `gdap-mcp@0a706f3`):
```python
_USER_PROFILE_SELECT = (
    "id,displayName,givenName,surname,userPrincipalName,mail,"
    "accountEnabled,usageLocation,jobTitle,department,mobilePhone,"
    "businessPhones,officeLocation,streetAddress,city,state,postalCode,"
    "companyName,employeeHireDate,employeeId,"
    "proxyAddresses,identities,onPremisesSyncEnabled,"
    "onPremisesLastSyncDateTime,onPremisesDistinguishedName,"
    "provisionedPlans,assignedLicenses,"
    "licenseAssignmentStates"
)
```
`onPremisesImmutableId`, `onPremisesSamAccountName`, `createdDateTime`, `lastPasswordChangeDateTime` are absent — the exact four QA-AUTO reports missing. `ms-graph-mcp`'s equivalent constant (`src/graph_mcp/tools/users.py:35-46`) has all four, added in `ms-graph-mcp`'s own round 2 (Defect 4a) and never ported here.

**COV4 — `gdap-mcp`'s `graph_get_user` never routes `manager` in `select` to `$expand`, and has no null-injection.**

`app/graph_tools/users.py:733-746` (`gdap-mcp@0a706f3`):
```python
params: dict = {}
if select:
    fields = ["id"] + [f for f in select if f != "id"]
    params["$select"] = ",".join(fields)
else:
    params["$select"] = _USER_PROFILE_SELECT
    params["$expand"] = "manager($select=id,displayName,userPrincipalName)"

try:
    result = await client.get(f"/users/{user_id}", params=params)
    return dump_json_capped(result)
```
When `select` is given, `manager` is pushed into `$select` (a navigation property Graph silently drops from `$select`, never erroring) and `$expand` is never set — so `select=["proxyAddresses","manager"]` returns `{id, proxyAddresses}` with no `manager` key at all, regardless of whether the user has one. This is `ms-graph-mcp`'s round-2-era bug (Defect 4, fixed there as `src/graph_mcp/tools/users.py:446-454`'s `manager_requested`/`$expand`-routing logic) plus `ms-graph-mcp`'s own round-4 fix (the `"manager" not in result` null-injection, `:462-468`) — `gdap-mcp` has neither. The default (no-`select`) call does set `$expand=manager(...)`, so COV4's underlying key-omission-on-no-manager gap exists there too, not just on the `select` path — round 4's regression guard (TC27 below) covers both call shapes, matching `ms-graph-mcp`'s own AC1 scope.

**Unaffected**: items 1-4 (pagination, `graph_update_user`) are not part of this rework's scope — comment `1600390000029562` names only items 5/6 (this comment's 1.5/1.6), and QA-AUTO's passing cases TC1-TC5 are the `ms-graph-mcp` ledger, not `gdap-mcp` equivalents (pagination/`graph_update_user` on `gdap-mcp` were never flagged by any retest and are out of scope here).

**Test infrastructure gap (new finding, not previously flagged):** `gdap-mcp`'s fake Graph test double (`tests/fake_microsoft.py`) has no `manager` modeling at all — no `state.managers`, no `GET/DELETE /users/{id}/manager` routes — and its single-user `GET /users/{id}` route (`:782-790`) ignores `$select`/`$expand` entirely, always returning the full fixture dict. `ms-graph-mcp`'s equivalent tests use a different, lighter-weight fake-client pattern (`_register(users)` at the client level) that already supports this. Closing COV1-COV4 with real red-green tests requires extending `gdap-mcp`'s fake server first — see Tech design's Change list, item 3. Checked that every current caller of `GET /users/{id}` in this repo always passes an explicit `$select` (`app/graph_tools/groups.py:228`, `app/graph_tools/users.py:746`) — tightening the fake to honor `$select` cannot change any existing test's observed response.

## Product design

### Goals / Non-goals

**Goals** (unchanged from the original ticket's items 5/6, now scoped to a second repo):
- G1 (R5-AC1): `gdap-mcp`'s `graph_remove_manager` matches `ms-graph-mcp`'s already-shipped contract: `{user_id, removed: bool, previous_manager: {id, display_name, user_principal_name} | null, reason: "no_manager" | null}`, read-then-delete, with a not_found guard for a user_id that does not resolve.
- G2 (R5-AC2): `gdap-mcp`'s `graph_get_user` default `$select` includes `onPremisesImmutableId`, `onPremisesSamAccountName`, `createdDateTime`, `lastPasswordChangeDateTime`.
- G3 (R5-AC3): `gdap-mcp`'s `graph_get_user` returns an explicit `manager: null` (not an omitted key) when `manager` was requested (default call, or `select` including `"manager"`) and the resolved user has none; routes `manager` in `select` through `$expand` instead of a dropped `$select` entry.

**Non-goals**:
- Any change to `ms-graph-mcp` — already correct and QA-validated (comment `1600390000029490`).
- Items 1-4 (pagination, `graph_update_user`) on either repo — not reported as failing by any retest.
- Any change to `gdap-mcp`'s `graph_assign_manager` (the PUT counterpart) — not reported, not part of items 5/6.
- Unifying `gdap-mcp` and `ms-graph-mcp` into one codebase, or extracting shared logic between them — out of scope for this ticket; they remain two independently-maintained connectors that happen to need the same fix applied twice.

### Acceptance criteria R5-AC1..R5-AC3

- **R5-AC1** (`graph_remove_manager`, `gdap-mcp`): Given a user with no manager, When `ms-graph-gdap_graph_remove_manager` is called, Then it returns `{user_id, removed: false, previous_manager: null, reason: "no_manager"}` with no error and without ever issuing `DELETE /users/{id}/manager/$ref`. Given a user with an assigned manager, When called, Then it returns `{user_id, removed: true, previous_manager: {id, display_name, user_principal_name}, reason: null}`, and a subsequent read of the user's manager confirms none remains. Given a `user_id` that does not resolve to any user, When called, Then it returns a `not_found` error envelope, never a `no_manager` result.
- **R5-AC2** (`graph_get_user` default fields, `gdap-mcp`): Given `ms-graph-gdap_graph_get_user` is called with no `select`, When the tool builds its request, Then the default `$select` includes `onPremisesImmutableId`, `onPremisesSamAccountName`, `createdDateTime`, and `lastPasswordChangeDateTime` alongside the existing default profile fields.
- **R5-AC3** (`graph_get_user` manager null, `gdap-mcp`): Given `ms-graph-gdap_graph_get_user` is called with no `select` (default, which always expands `manager`) or with `select` including `"manager"`, and the resolved user has no manager, When Graph's response does not contain a `manager` key, Then the tool's returned JSON contains `"manager": null`, not an omitted key. Given the same calls on a user who does have a manager, Then `manager` continues to carry the expanded `{id, displayName, userPrincipalName}` object unchanged (regression guard).

## Tech design

### Conclusion

Port `ms-graph-mcp`'s already-shipped, already-validated `graph_remove_manager` and `graph_get_user` logic into `gdap-mcp`'s `app/graph_tools/users.py`, adapted to this repo's existing helper names (`client_factory`, `GraphError`, `dump_json_capped`, which are structurally identical between the two repos). No new file, no new dependency, no schema/DB change (these MCPs are stateless proxies onto Microsoft Graph). The one piece of genuinely new work is extending `gdap-mcp`'s fake Graph test double (`tests/fake_microsoft.py`) with `manager` modeling, since it has none today — without this, the new production code has nothing to red-green against.

- **New API/param shape**: `graph_remove_manager`'s return shape changes from `{"status", "user_id"}` to `{"user_id", "removed", "previous_manager", "reason"}` — additive in the sense that it's the same shape `ms-graph-mcp` already ships and the retest already expects, but it is a breaking shape change for any existing `gdap-mcp` caller relying on the old `{"status": ...}` keys. No such caller was found in this repo's own code (`graph_remove_manager` is only ever invoked as an MCP tool, not called internally by other tools) — see Data & API contract.
- **In-scope cleanup**: none identified in the two touched functions beyond the fix itself — both are already narrowly-scoped, single-purpose tools.
- **Out-of-scope / follow-up** (not this ticket): (a) the Option-C "extract shared logic" idea above, to prevent this class of bug (fixed in one connector, not the other) from recurring across `ms-graph-mcp`/`gdap-mcp`'s other overlapping tools — flagged, not actioned; (b) auditing whether any other `gdap-mcp` tool independently duplicates a since-fixed `ms-graph-mcp` behaviour (Open questions) — out of this round's four-point scope.

### Data & API contract

**`ms-graph-gdap_graph_remove_manager`** (modified) — **breaking for this one tool's response shape**: old `{"status": "removed"|"no_manager", "user_id"}` → new `{"user_id", "removed": bool, "previous_manager": {id, display_name, user_principal_name} | null, "reason": "no_manager" | null}`. This is the exact shape change the rework explicitly asks for (comment `1600390000029419`'s acceptance points), and matches what `ms-graph-mcp` already ships for the same tool name — an agent prompt or integration built against `ms-graph-mcp`'s `graph_remove_manager` already expects this shape, so this brings `gdap-mcp` into alignment rather than diverging further.

**`ms-graph-gdap_graph_get_user`** (modified) — **additive, not breaking**: default `$select` gains four more fields (any caller ignoring unrequested fields is unaffected); the only behaviour change is that a previously-omitted `manager` key now appears with value `null` in the one specific "manager requested, user has none" case — identical framing to `ms-graph-mcp` round 4's own contract note.

### Key flow / sequence

`graph_remove_manager` (new flow, replacing the delete-then-infer-404 flow):
1. Caller → `graph_remove_manager(user_id="u1")`.
2. Server → `GET /users/u1/manager?$select=id,displayName,userPrincipalName`.
3a. 404 → Server → `GET /users/u1?$select=id` (existence check). 404 again → return that error envelope (not_found). 2xx → return `{user_id, removed: false, previous_manager: null, reason: "no_manager"}`.
3b. 2xx → capture `previous_manager` from the response → Server → `DELETE /users/u1/manager/$ref` (a 404 here is treated as a benign race, not an error) → return `{user_id, removed: true, previous_manager, reason: null}`.

`graph_get_user` (new step appended to the existing flow, same shape as `ms-graph-mcp` round 4):
1. Caller → `graph_get_user(user_id="u1")` (default) or with `select=[..., "manager"]`.
2. Server computes `params`: default → `$expand=manager(...)` always set; `select` containing `"manager"` → routed to the same `$expand` (new this round — previously dropped silently into `$select`).
3. Server → `GET /users/u1` with those params.
4. **(new this round)** If `manager` was requested and `"manager" not in result`: set `result["manager"] = None`.
5. Return `dump_json_capped(result)`.

### Non-functional

- **Idempotency & concurrency**: `graph_remove_manager`'s new flow adds one extra `GET` before the `DELETE` (was: delete only); calling it twice on an already-managerless user is idempotent (second call sees no manager, returns `no_manager`, issues no DELETE) — this is strictly safer than the old flow, which issued a DELETE on every call regardless. `graph_get_user`'s null-injection is a pure post-read dict check, no new call, equally idempotent.
- **Performance**: `graph_remove_manager` goes from 1 Graph call (success path) to 2 (GET then DELETE) on the has-a-manager path, and from 1 to up to 2 on the no-manager path (GET manager 404, then GET user for existence) — same cost profile `ms-graph-mcp` already accepted in its own round 2/3 fixes for the same reason (correctness over call count; `graph_remove_manager` is not a hot-path list tool). `graph_get_user`'s change is a zero-extra-call O(1) dict check, same as `ms-graph-mcp` round 4.
- **Security**: no new auth surface on either tool — both post-process or reshape a response already fetched under the caller's existing GDAP-scoped token; the `customer_tenant_id` plumbing (auto-injected by `app/graph_tools/registry.py`, unrelated to this fix) is unchanged.
- **Multi-tenant isolation**: unchanged — every Graph call stays scoped by the GDAP wrapper's per-call `customer_tenant_id` → delegated/app-only client, same as every other tool in this repo; this round adds no cross-tenant call.
- **Observability**: none needed — response-shape and request-parameter fixes, not new error paths beyond the existing `GraphError.to_envelope()` pattern.
- **Tool description budget**: no 500-char tool-description-length gate was found in this repo during this round's read (unlike `ms-graph-mcp`'s `test_tools_list_snapshot`) — the dev leg should re-confirm this before assuming the docstring additions above are free of any such constraint (see Change list note).
