**Issue A — `graph_get_user` omits the `manager` key instead of returning `manager: null` when `select` includes `"manager"` and the user has none** (retest's "Partial – 1.6", second half).

Code: `src/graph_mcp/tools/users.py:417–461` (`graph_get_user`, at `4ae1571`). When `manager` is requested, the tool sets `params["$expand"] = "manager($select=id,displayName,userPrincipalName)"` (`:450-451`) and returns Graph's response verbatim via `dump_json_capped(result)` (`:455`) — there is no code that inspects the result and injects `manager: None` if Graph omitted the key. Whether the key is present for a user with no manager is entirely up to what Microsoft Graph's `$expand` returns for an empty single-valued navigation property; this repo has never added logic either way.

This exact path was checked once, in production, by the 2026-10-16 PRD smoke test (`90170263323318`): "select ["proxyAddresses","manager"] -> id + proxyAddresses (this user has no manager, so no manager key, as expected)." At that time the omitted key was recorded as the **expected**, passing result — not a defect. The 2026-11-02 retest now asks for the opposite: "Please return manager: null in that case." No code change happened between the two tests (confirmed above); what changed is the acceptance bar itself. This is a requirement change, not a regression.

**Issue B — the reported `graph_remove_manager` response shape does not match this tool** (retest's "Fail – 1.5").

The retest reports: `graph_remove_manager` on `off.leaver1@2qmxyw` (a user with no manager) "still returns `{"status":"removed"}`." Reading `graph_remove_manager` at `src/graph_mcp/tools/users.py:745–818` (`4ae1571`): there is no code path in this function that returns a bare `{"status": "removed"}`. Every return path produces `{"user_id", "removed": <bool>, "previous_manager": <dict|null>, "reason": <str|null>}` (`:779-785` for the no-manager path, `:811-817` for the has-a-manager path) or a `GraphError` envelope (`:784`, `:794`). The no-manager path (`:779-785`) was exercised exactly as described by a test (`tests/test_tools.py::test_remove_manager_returns_no_manager_without_calling_delete`) and by round 3's own INT test (`90170263287176`/`90170263295399` lineage) and PRD smoke test, both passing.

The shape the retest reports — `{"group_id": ..., "status": "removed"}` per item — is exactly what a **different** tool, `graph_remove_group_member`, returns per group (`src/graph_mcp/tools/groups.py:335-362`, specifically `:357`: `results.append({"group_id": group_id, "status": "removed"})`). `graph_remove_manager` takes no `group_ids` argument and never produces a `group_id` key. This strongly suggests the retest's agent called `graph_remove_group_member` (removing the user from a group) rather than `graph_remove_manager` (clearing the manager relationship) — an easy mix-up on a GDAP/Ginko-migrated tenant where tool names may have been re-mapped or re-labeled during the connector migration. This is not reproducible as a code defect against the current implementation.

**Issue C — the four on-premises/audit fields are already in the default response** (retest's "Partial – 1.6", first half).

The retest reports these are "still missing from the default return": `onPremisesImmutableId`, `onPremisesSamAccountName`, `createdDateTime`, `lastPasswordChangeDateTime`. `_USER_PROFILE_SELECT` at `src/graph_mcp/tools/users.py:35-45` lists all four (`:42-43`) alongside the rest of the default profile, and `graph_get_user` uses this constant for every call with no `select` param (`:449`). This has been true since round 2's Defect 4a fix (`ccf3931`, re-confirmed unchanged by round 3) and is locked in by `tests/test_tools.py::test_get_user_default_select_includes_onprem_and_audit_fields` (`:2022-2043`), which asserts all four are present. The 2026-10-16 INT test and PRD smoke test (`90170263322451`, `90170263323318`) both explicitly confirmed these four fields present in production at this same commit lineage. Nothing has changed in this code since. The most likely explanation is that the GDAP/Ginko-migrated connector on the demo tenant had not picked up the already-released tool definitions (the release comments for rounds 1–3 each ended with "Please Refresh Tools on the connector") — not a code defect.

## Product design

### Goals / Non-goals

**Goals**:
- G1 (Issue A): `graph_get_user` returns an explicit `manager: null` — not an omitted key — when `manager` was requested (default call, or `select` including `"manager"`) and the resolved user has no manager.
- G2 (Issues B/C, regression confirmation, not a behavior change): add tests that assert `graph_remove_manager`'s no-manager response shape and `graph_get_user`'s default on-premises/audit fields, so a future retest has an automated, citable answer instead of a fresh code read.

**Non-goals**:
- Re-opening any of items 1.1–1.4, or the has-a-manager / nonexistent-user paths of `graph_remove_manager` — the retest reports these as passing, and nothing in this round touches that code.
- Guessing at what the GDAP/Ginko connector migration actually changed on the demo-tenant side (tool name mapping, connector refresh state) — that is outside this repo and outside what a design review of this code can determine. See Open questions.
- Any further field additions to `graph_get_user` beyond the single `manager: null` change — the retest does not ask for more.

### Acceptance criteria AC1..AC3

- AC1 (new, Issue A — requirement change): Given `graph_get_user` is called with no `select` (the default profile, which always `$expand`s `manager`) or with a `select` list that includes `"manager"`, and the resolved user has no manager assigned, When Graph's response does not contain a `manager` key (or contains one that is itself empty/absent), Then the tool's returned JSON contains `"manager": null` explicitly, not an omitted key. Given the same calls on a user who does have a manager, Then `manager` continues to carry the expanded `{id, displayName, userPrincipalName}` object exactly as rounds 1–3 shipped (regression guard — this round must not change the has-a-manager path).
- AC2 (regression confirmation, Issue B — not a behavior change): Given a `user_id` that resolves to a real user with no manager, When `graph_remove_manager` is called, Then it returns `{"user_id", "removed": false, "previous_manager": null, "reason": "no_manager"}` — never a bare `{"status": "removed"}` or any shape containing a `group_id` key. This re-asserts round 3's already-shipped behavior as a named, independently-citable test so the next retest's result can be checked against this tool specifically.
- AC3 (regression confirmation, Issue C — not a behavior change): Given `graph_get_user` is called with no `select`, When the tool builds its request, Then the default `$select` includes `onPremisesImmutableId`, `onPremisesSamAccountName`, `createdDateTime`, and `lastPasswordChangeDateTime` alongside the rest of the default profile. This re-asserts round 2/3's already-shipped behavior; the existing `test_get_user_default_select_includes_onprem_and_audit_fields` already covers the identical assertion — AC3 exists so this round's AC numbering names it explicitly as this round's answer to the retest's Issue C, not just a leftover from round 2.

## Tech design

### Conclusion

One targeted change in `graph_get_user` (`src/graph_mcp/tools/users.py`): after fetching the result, if `manager` was requested (default call or explicit `select` including `"manager"`) and the key is absent from Graph's response, set it to `None` before serializing. No change to `graph_remove_manager`, no new file, no new dependency, no schema/DB change. Two new regression tests (AC2, AC3) document already-correct behavior; no production code changes for those two.

### Data & API contract

**`graph_get_user`** (modified) — **additive, not breaking**: the response shape is unchanged for every existing caller that does not request `manager` on a no-manager user. The only change is that a previously-omitted `manager` key now appears with value `null` in that one specific case. A caller using `"manager" in response` to test for presence would now see `True` with a `null` value instead of `False` — this is exactly the ambiguity the retest asked to remove, and is called out explicitly for the groomer/reviewer since it is a (narrow, intentional) shape change on this one path.

**`graph_remove_manager`**: no change.

### Key flow / sequence

`graph_get_user` (round 4's addition to the tail, after round 3's `:417-461` is otherwise unchanged):

1. Caller → `graph_get_user(user_id="u1")` (default) or `graph_get_user(user_id="u1", select=[..., "manager"])`.
2. Server computes `params` exactly as rounds 1–3 built it (unchanged): default call always sets `$expand=manager(...)`; a `select` containing `"manager"` routes it to the same `$expand`.
3. Server → `GET /users/u1` with those params.
4. Server receives `result` from Graph.
5. **(new this round)** If `manager` was requested this call and `"manager" not in result`: set `result["manager"] = None`.
6. Return `dump_json_capped(result)`.

### Non-functional

- **Idempotency & concurrency**: no state change, no new Graph call — a plain dict-key check and assignment after an existing read. Calling it twice on the same no-manager user is equally `manager: null` both times.
- **Performance**: zero added Graph calls. The check runs only when `manager` was requested at all (the common offboarding call shape already requests it by default), and is an O(1) dict lookup.
- **Security**: no new auth surface — the fix only post-processes a response the tool already had permission to fetch.
- **Multi-tenant isolation**: unchanged — no isolation logic of its own, every Graph call scoped by the caller's own bearer token, same as rounds 1–3.
- **Observability**: none needed — this is a response-shape fix, not an error path.
- **Tool description budget**: `graph_get_user`'s current docstring normalizes to 425/500 chars (checked this round: `re.sub(r'\s+',' ',docstring).strip()` → 425); the proposed one-clause addition ("manager is null, not omitted, when the user has none") is well within the remaining 75-char budget `tests/test_tools.py::test_tools_list_snapshot` enforces.

Recommend the next retest: (a) confirm the exact tool name called for item 5 is `graph_remove_manager`, not `graph_remove_group_member`; (b) run "Refresh Tools" on the GDAP/Ginko connector against the demo tenant before retesting item 6's default fields; (c) re-run item 6's `select=["proxyAddresses","manager"]` case specifically to confirm the new `manager: null`.

The fix handles both "Graph omits the key" and "Graph returns a null/empty value" the same way (inject explicit `null`), so this gap does not block the fix's correctness, only its exact trigger condition in the real API.
- **Dependency**: none on another ticket or repo. Rounds 1–3's shipped fixes are untouched and are not a dependency of this round.
