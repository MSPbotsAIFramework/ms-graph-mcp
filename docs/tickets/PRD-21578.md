## Requirement understanding

One line: Add a `graph_delete_message` tool to the Microsoft Graph connector that deletes a single email from a mailbox by message id, so Ginko IT's malicious-email-removal Rewst flow can be ported to MSPbots.

The ticket comes from the Rewst → MSPbots migration gap register (`mspbots-gap-register.xlsx`, item 10): Ginko IT's Rewst flow "[ROC] M365: Remove Malicious Emails and Block Sender" has run 185 times in the last 365 days (evidence grade A) and calls `microsoft_graph.graph_api_request` with `DELETE /users/{user}/messages/{message_id}` to remove one already-identified malicious email from a mailbox. The reporter checked all 43 Microsoft Graph tools plus 51 GDAP tools against this capability and found no match — `graph_list_messages`/`graph_get_message` are read-only. The requested inputs are `user` (UPN or id) and `message_id` (obtained upstream, in Rewst's case from a search step not covered by this ticket), the requested permission is `Mail.ReadWrite` (application), and the expected result is Graph's `204 No Content`.

## Current state (every claim carries path:line, read at `master@e274955`)

- No tool in `ms-graph-mcp` deletes, moves, flags, or otherwise mutates a message. The mail tool module's own scope note says so explicitly: `src/graph_mcp/tools/mail.py:1-8` — *"these tools cover one business flow — 'what landed in this mailbox, what is it about, and does it need a reply': list/search messages, open one in full, read what an attachment says, send one. Moving, flagging, deleting, replying in place and folder management are deliberately not exposed — the read side exists to let an agent triage a mailbox and draft follow-ups, not to act as a mail client."* This is a scoping note about what had been *built so far* (three tools: send, list, get, plus the later attachment reader), not a security control enforced in code — unlike the PRD-16540 precedent this SOP warns about (role checks + disabled UI + backend 403, all three consistent), there is no runtime gate here that a new tool would have to bypass. Treated as "scope not yet extended", not "policy that forbids extension" — see Open Questions for the one piece of this note that *is* worth flagging back.
- The repo already ships three other idempotent, `destructiveHint=True` delete tools built on exactly this pattern (confirming it is an established, reviewed convention, not a one-off):
  - `graph_delete_file` (`src/graph_mcp/tools/sites.py:567-593`): `await client.delete(...)`, catches `GraphError`, treats `status_code == 404` as already-gone and still returns `{"deleted": True}`.
  - `graph_remove_managed_device` (`src/graph_mcp/tools/devices.py:52-80`): identical shape, same 404-is-success idempotency.
  - `graph_cancel_calendar_event` (`src/graph_mcp/tools/calendar.py:287+`, per README.md:185): falls back to a direct delete when there are no attendees to notify; also idempotent on a missing event id.
  None of these needed a design exception — they are the precedent this design follows.
- `GraphClient.delete(path)` already exists and is used by all three tools above: `src/graph_mcp/api_client.py:105-106`.
- The mail tools' `user_id` convention (`_USER_ID_DESC`, `mail.py:92-97`; used by `graph_list_messages` and `graph_get_message`, `mail.py:574,713`) is: omit `user_id` → operate on `/me` (the signed-in user under a delegated token); pass it → `/users/{user_id}` (required for every call under an app-only token, since app-only has no signed-in user). The new tool reuses this exact convention — the ticket's `user` parameter maps onto the existing `user_id`.
- Permission gap, confirmed by reading the scope documentation: `README.md:223` states *"`Mail.ReadWrite` is **not requested** (no tool edits, moves, or marks messages as read)"*, and the scope union code block at `README.md:202-211` does not list it. Microsoft Graph's `DELETE /users/{id}/messages/{id}` requires `Mail.ReadWrite` (delegated or application) — there is no narrower Graph permission that covers delete-only; this repo has no tool today that would let `Mail.ReadWrite` be requested as a byproduct of something else.
- Adding a new scope to this connector is a well-trodden, documented path in this exact repo, not a novel risk: `UserAuthenticationMethod.ReadWrite.All` (`graph_create_tap`, PRD-20480), `Group.ReadWrite.All` (`graph_add_group_owner`, PRD-20480), `Synchronization.ReadWrite.All` (`graph_start_cloud_sync`, PRD-20422), `Mail.Read` (PRD-19103) and `Calendars.ReadWrite` (PRD-18631) were all added the same way: ship the tool, add the scope to the README union and to the platform-side request in `auth/oauth/vendors/msgraph.py` (`MCP-Management-Service`, outside this repo — Leo Yang's team), and every already-connected tenant must re-consent once before the new tool stops returning `unauthorized`/403 (`README.md:216`). This design follows that same path for `Mail.ReadWrite`.
- Graph's semantics for this endpoint (Microsoft Learn, "Delete message"): `DELETE /users/{id}/messages/{id}` moves the message to the mailbox's **Deleted Items** folder — the same thing a user sees after pressing Delete in Outlook — it does not purge it; a separate `permanentDelete` action exists for that and is not requested by the ticket (the Rewst flow's own description just says "删除"/remove, matching the Outlook-Delete semantics, not a purge).
- Wiki: `mbp.py wiki sync` (fact base HEAD `0c1f40e`, product version `v20261030.0410`) → `wiki find "Microsoft Graph"` / `"mail"` / `"delete message"`. **Wiki does not cover this capability.** The hits that came back (`ProductDocs/15-Capabilities.md` § Connector detail view, `ProductDocs/_connector-fields.md`) are generic connector-field/OAuth-dialog pages shared by every vendor connector, not anything specific to Microsoft Graph's mail tools; `"delete message"` had zero hits. Same situation as the immediately prior ticket on this connector (PRD-21391): there is no connector *page* here to be wrong or stale, just an unbuilt tool — not filing a `_gaps.md` entry for the same reason.

## Product design

### Goals / Non-goals

Goals:
- Add one new tool, `graph_delete_message(message_id, user_id=None)`, to the Microsoft Graph connector, so an agent that has already identified a malicious (or otherwise unwanted) email via `graph_list_messages`/`graph_get_message` can remove it from the mailbox in one call — the capability Ginko IT's Rewst flow exercises 185 times/year.
- Match this repo's existing delete-tool contract exactly: idempotent (deleting an id that is already gone is success, not an error), `destructiveHint=True`, structured error envelope on failure, no partial effects.
- Keep the mail domain's existing read tools (`graph_list_messages`, `graph_get_message`, `graph_read_mail_attachment`) and `graph_send_mail` unchanged.

Non-goals (this slice):
- No move/flag/mark-as-read/reply-in-place/folder-management tools — the scope note's broader "not a mail client" boundary stands for everything except this one, specifically-requested, narrowly-scoped delete action. Adding delete does not reopen the rest of that boundary.
- No bulk delete (one `message_id` per call, same granularity as `graph_delete_file`/`graph_remove_managed_device`).
- No `permanentDelete` / hard purge. The ticket asks for the Outlook-Delete behavior Graph's plain `DELETE` already gives; a true purge is a different, higher-risk endpoint nothing in the ticket's evidence (the Rewst flow, or its 185 runs) asks for.
- No new "detect malicious email" logic. Identifying *which* message to delete stays in Rewst/the calling agent, exactly as it does today for `graph_get_message`/`graph_list_messages`.

### Acceptance criteria AC1..AC6

- **AC1** — Given a `message_id` and an explicit `user_id` (the app-only / "someone else's mailbox" case), when `graph_delete_message` is called, then the server issues `DELETE /users/{user_id}/messages/{message_id}` and returns `{"user_id": <user_id>, "message_id": <message_id>, "deleted": true}`.
- **AC2** — Given a `message_id` and no `user_id` (the delegated / "my own mailbox" case), when `graph_delete_message` is called, then the server issues `DELETE /me/messages/{message_id}` and returns `{"user_id": "me", "message_id": <message_id>, "deleted": true}` — same `user_id` convention as `graph_get_message`.
- **AC3** — Given a `message_id` that no longer exists (already deleted, or never existed), when `graph_delete_message` is called, then the response is still `{"deleted": true}`, not an error — idempotent, matching `graph_delete_file`/`graph_remove_managed_device`.
- **AC4** — Given a Graph error other than 404 (e.g. 403 when the token lacks `Mail.ReadWrite`, or a tenant that has not re-consented yet), when `graph_delete_message` is called, then the response is this repo's structured `GraphError.to_envelope()`, and the message is left untouched — no silent partial success.
- **AC5** — The tool appears in `tools/list` with exactly one required parameter (`message_id`), an optional `user_id`, and annotations `readOnlyHint=false, destructiveHint=true, idempotentHint=true` — mirrors the three existing delete tools' annotation shape.
- **AC6** — The new tool, its required `Mail.ReadWrite` scope, and its GDAP role are documented consistently: a row in the `README.md` Tools table, an entry in `docs/gdap-role-map.yaml`, and `Mail.ReadWrite` added to the scope-union code block and the "`Mail.Read`/`Mail.ReadWrite`" narrative paragraph — enforced by the existing `tests/test_gdap_role_map.py` consistency test (no new test needed, it already fails if a registered tool has no matching table/yaml row).

### Open questions

- **Does the "not a mail client" scope note (`mail.py:1-8`) need an explicit edit, or does adding one delete tool implicitly supersede it?** Not blocking — assumption made: the Tech design updates that docstring to say the mail domain now exposes exactly one narrow, scoped mutation (delete-by-id, for an already-identified message) while explicitly still not exposing move/flag/reply-in-place/folder management. This keeps the note accurate without re-litigating the original boundary, the same way `mail.py`'s own docstring already narrates each permission decision inline. If whoever owns this connector's scope intended the boundary to be stricter than "no bulk mail-client behavior", that is the one thing worth a comment back — but nothing in this ticket's evidence (a single, specific delete-by-id, already in production on Rewst) reads as crossing it.
- **GDAP role for `Mail.ReadWrite`**: every existing mail tool's GDAP role is `null`/"unknown" (`docs/gdap-role-map.yaml:106-120`) because mail access is scope-gated, not Entra-role-gated, in this connector's model. `graph_delete_message` follows the same `roles: null` pattern. Not blocking — consistent with 100% of the existing mail domain.
- **Tenant re-consent for `Mail.ReadWrite`**: per the established rollout pattern (README.md:216), already-connected tenants will see 403 on this one tool until they re-consent, and the platform-side scope request change in `MCP-Management-Service` (`auth/oauth/vendors/msgraph.py`) is outside this repository. Not blocking this design — same handoff shape as every prior new-scope tool in this connector; flagged in the Tech design's Rollout section so the dev/review legs don't have to rediscover it.

## Tech design

### Conclusion

Add one tool, `graph_delete_message`, to `src/graph_mcp/tools/mail.py`, implemented as a direct copy of the existing `graph_delete_file`/`graph_remove_managed_device` idempotent-delete pattern, reusing `GraphClient.delete()` and the mail domain's existing `user_id`/`NO_TOKEN` conventions. No new file, no new client method, no new connector, no gateway change. The only repo-wide (non-mail-module) edits are: `README.md` (tool row + scope union + scope narrative), `docs/gdap-role-map.yaml` (one entry), and `tests/test_tools.py` (`EXPECTED_TOOLS`/`_NON_READ_ONLY` + new test cases).

### Where the current implementation lives

- Tool registration: `register(mcp, client_factory)` in `src/graph_mcp/tools/mail.py:493-888` — the new tool is added as a fourth `@mcp.tool(...)` inside this same function, after `graph_read_mail_attachment` (keeps the file's existing order: send, list, get, read-attachment, [new] delete).
- Idempotent-delete pattern to copy: `src/graph_mcp/tools/sites.py:567-593` (`graph_delete_file`) and `src/graph_mcp/tools/devices.py:52-80` (`graph_remove_managed_device`).
- HTTP primitive: `GraphClient.delete(path)` → `src/graph_mcp/api_client.py:105-106`.
- `user_id` → base-path convention and its docstring: `src/graph_mcp/tools/mail.py:92-97` (`_USER_ID_DESC`), applied at `mail.py:742` (`graph_get_message`'s `base = f"/users/{user_id}" if user_id else "/me"`).
- Error envelope: `GraphError.to_envelope()`, already imported in `mail.py:51`.

### Option analysis

- **Option A (chosen): one tool, `graph_delete_message(message_id, user_id=None)`, hard `DELETE`.** Matches the ticket's exact ask, the existing idempotent-delete convention, and needs exactly the permission the ticket names (`Mail.ReadWrite`).
- **Option B (rejected): move-to-Deleted-Items via `PATCH .../move` instead of `DELETE`.** Graph's plain `DELETE` on a message *already* moves it to Deleted Items (see Current state) — a `move` call would be a redundant, more complex way to reach the same end state the ticket asks for. Not chosen: no behavioral benefit, extra code path.
- **Option C (rejected): add a `permanent` flag that calls `permanentDelete` when true.** No requirement in the ticket or the cited Rewst flow asks for a hard purge; `permanentDelete` is a materially higher-risk, harder-to-undo operation (Deleted Items itself is still recoverable in Outlook for a retention window, a purge is not). Adding an unused, higher-risk code path fails the "don't add machinery nothing asks for" bar. If a future ticket needs it, it is a one-tool addition following this same pattern — not blocked by this design.
- **Option D (rejected): fold delete into `graph_get_message` via an `action` parameter.** This repo has an explicit, written convention against mode-flag tools (`tests/test_tools.py:~115-125`, the calendar-domain comment: "a tool whose required params depend on a mode flag... reads worse to an agent"). A dedicated tool keeps `message_id`-only-required and the correct `destructiveHint` annotation, which a shared tool could not express cleanly (the read path is `readOnlyHint=true`, delete is not).

### Data & API contract

New tool, `src/graph_mcp/tools/mail.py`:

```python
@mcp.tool(
    annotations=ToolAnnotations(readOnlyHint=False, destructiveHint=True, idempotentHint=True)
)
async def graph_delete_message(
    message_id: Annotated[
        str,
        Field(description="Message id from graph_list_messages or graph_get_message — never guess it, list/open first."),
    ],
    user_id: Annotated[str | None, Field(description=_USER_ID_DESC)] = None,
) -> str:
    """Delete one email from a mailbox.

    Moves the message to the mailbox's Deleted Items folder — the same
    result as pressing Delete in Outlook — it does not purge it outright.
    Idempotent: deleting an already-deleted or nonexistent message_id
    returns success, not an error. Confirm the exact message_id (from
    graph_list_messages/graph_get_message) before calling — there is no
    undo from this tool once called, only the normal Outlook
    Deleted-Items recovery window.
    """
    client = client_factory()
    if client is None:
        return NO_TOKEN

    base = f"/users/{user_id}" if user_id else "/me"
    try:
        await client.delete(f"{base}/messages/{message_id}")
    except GraphError as e:
        if e.status_code != 404:
            return e.to_envelope()
    return dump_json_capped(
        {"user_id": user_id or "me", "message_id": message_id, "deleted": True}
    )
```

- **Request**: `DELETE {base}/messages/{message_id}` where `base` is `/users/{user_id}` or `/me`, exactly the `graph_get_message` convention.
- **Response (success)**: `{"user_id": "<id-or-me>", "message_id": "<id>", "deleted": true}`.
- **Response (Graph error, non-404)**: the repo's standard error envelope (`{"error": {"code": ..., "message": ..., "retryable": ..., ...}}` via `GraphError.to_envelope()`), same shape every other tool in this file returns.
- **No request body, no `$select`/`$filter` — a plain `DELETE` takes neither.**
- **Backward compatibility**: pure addition, no existing tool's signature, return shape, or behavior changes.

### Key flow / sequence

1. Rewst (or the Agent platform) finds the message to remove via `graph_list_messages(search=..., folder=null)` or already holds its `message_id` from an earlier step.
2. Agent calls `graph_delete_message(message_id, user_id)` — `user_id` is required under the app-only `ms-graph-app` connector (no signed-in user), optional under the delegated `ms-graph` connector.
3. Server issues `DELETE /users/{user_id}/messages/{message_id}` (or `/me/...`).
4. Graph moves the message to Deleted Items and returns `204`; `GraphClient._request` (per the existing 204-handling at `api_client.py:187`) returns an empty body, which the tool ignores and reports `deleted: true`.
5. On a repeat call with the same `message_id` (e.g. a retried Rewst step), Graph returns `404`; the tool still reports `deleted: true` — no special-casing needed by the caller.

### Non-functional

- **Idempotency / concurrency**: stateless per call, same as every tool in this server (`stateless_http=True`, noted in `offboarding.py:20`); the 404-as-success handling is what makes repeated/retried calls safe.
- **Security / least privilege**: `Mail.ReadWrite` (delegated or application, matching the ticket's "应用权限") is the minimum Graph permission for this endpoint — there is no narrower delete-only scope. Under app-only, this permission reaches **every** mailbox in the tenant, same caveat this README already documents for `Mail.Read` app-only (`README.md:223`) and `Calendars.ReadWrite` app-only (`README.md:225`) — worth the same "restrict via Exchange application access policy" recommendation, which the README edit carries forward verbatim for the new scope.
- **Multi-tenant isolation**: unaffected — this connector is single-tenant per credential, same as every existing mail tool; no cross-tenant code path is touched.
- **Logging / observability**: no new logging added beyond what `GraphClient` already does for every request; matches the rest of the mail module (`graph_send_mail` logs attachment metadata, the read tools do not log message content — this tool does not need to either, since it carries no content).
- **Irreversibility**: documented in the tool's own docstring (the only mitigation available at this layer, same convention `graph_send_mail`'s and `graph_delete_file`'s docstrings already use for their own irreversible/hard-to-reverse actions).

### Rollout & rollback

- **Rollout**: ship the tool and the scope-union/README/GDAP-yaml edits together, then publish to INT via `mcppub publish` per `mcp-track.md` §4.8 — standard path, no new-vendor registration needed (`ms-graph-mcp` is already registered). This is a platform-side follow-up outside this repo and outside this ticket's Code Repo; the design doesn't block on it, matching how the prior four scope additions shipped.
- **Rollback**: remove the tool registration (or feature-flag it out) and drop the `Mail.ReadWrite` row from the README scope union; no data migration, no state to unwind — every call this tool makes is already-committed on the Graph side (a delete), so "rollback" means "stop offering the tool", not "undo past calls" — same as every other delete tool in this repo.

### Test strategy

- **Automated, no live tenant required** (same style as every existing test in `tests/test_tools.py`): a fake `GraphClient`/`_mail_mcp` harness that records calls and can be made to raise `GraphError`, following the exact pattern of `test_remove_manager_handles_concurrent_delete_404_as_removed` (idempotent-404) and `test_get_message_*` (user_id/base-path routing).
- **Consistency gate**: the existing `tests/test_gdap_role_map.py` already fails if `EXPECTED_TOOLS`/the README table/the yaml file disagree — no new test needed for AC6, just correct entries in all three places.
- **Real-tenant verification**: like every other mutating tool in this repo (see README's "Known Gaps" entries for `graph_revoke_sessions`, `graph_remove_group_member`, etc.), this tool has not been run against a real Microsoft 365 tenant as of this design — no test mailbox/sacrificial message was available. Not a blocker per `mcp-track.md` §2.5 ("no test account is not a blocker"); the self-test leg should run it against a disposable test message on whatever tenant is available and record the result in Known Gaps, same convention the rest of this README already follows.
