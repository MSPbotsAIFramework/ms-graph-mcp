## Requirement understanding

One line: the reporter wants ms-graph-mcp's `graph_list_groups` to return `isAssignableToRole`, `onPremisesSyncEnabled` and `sync_source` for every group, the same way `graph_get_group` and `graph_list_user_groups` already do in this connector, and the same way the GDAP connector's `graph_list_groups` already does.

`graph_list_groups` (the single-tenant Microsoft Graph connector's group search/list tool) only selects `id,displayName,groupTypes,securityEnabled,mailEnabled` from Graph, so callers cannot see whether a listed group is role-assignable or AD-synced without a follow-up `graph_get_group` call per group. Two sibling tools in the same file already solved this (`graph_get_group` for PRD-21676, `graph_list_user_groups` for PRD-21676), and the GDAP connector's equivalent list tool returns the same fields (PRD-21647, PRD-21706). This ticket closes the gap for the one remaining tool. Found by Pantene Hui during QA of PRD-21676; PRD-21676 itself is accepted and unchanged.

## Product design

### Goals / Non-goals

**Goals**
- `graph_list_groups` returns `isAssignableToRole`, `onPremisesSyncEnabled` and `sync_source` for every group in its result, computed the same way `graph_get_group`/`graph_list_user_groups` already compute them.
- `isAssignableToRole` is passed through from Graph unmodified: `true`, `false`, or `null` for an ordinary group — never coerced to `false`.
- The tool's docstring documents the new fields with wording consistent with `graph_get_group`'s ("null means an ordinary group").

**Non-goals**
- `graph_list_owned_groups` (the different tool whose `$select` happens to live at the line number the ticket mis-cited) is not touched. It serves offboarding sole-owner detection, its output shape is not named in this ticket's Done-when, and changing it is a separate concern.
- No change to `graph_list_groups`'s filtering (`display_name`/`exact`), pagination contract (`max_results`/`page_token`/`has_more`/`next_page_token`), or any other existing field.
- No change to `graph_get_group` or `graph_list_user_groups` — they already have the fields this ticket asks for.
- No change to the GDAP connector (separate repo, already correct per the ticket).

### Acceptance criteria AC1..ACn

- **AC1**: Given a group that is role-assignable in Graph (`isAssignableToRole: true`), When `graph_list_groups` lists it (e.g. "test two" on INT tenant `2qmxyw`), Then that group's entry in the response has `isAssignableToRole: true`.
- **AC2**: Given an ordinary group where Graph returns `isAssignableToRole` as `false` or `null`, When `graph_list_groups` lists it, Then the entry carries that exact value unchanged — `null` must never be converted to `false`.
- **AC3**: Given any group `graph_list_groups` returns, When the same group is read with `graph_get_group`, Then `graph_list_groups`'s `sync_source` and `onPremisesSyncEnabled` for that group match `graph_get_group`'s values exactly (both derive `sync_source` as `"on-premises"` when `onPremisesSyncEnabled` is truthy, else `"cloud"`).
- **AC4**: Given the existing fields (`id`, `displayName`, `groupTypes`, `securityEnabled`, `mailEnabled`) and the existing pagination/filter contract (`max_results`, `page_token`, `has_more`, `next_page_token`, `display_name`, `exact`), When this fix is applied, Then none of that behaviour changes.
- **AC5**: Given the same group on the GDAP connector's `graph_list_groups`, When compared to this connector's `graph_list_groups` output for that group, Then `isAssignableToRole`, `onPremisesSyncEnabled` and `sync_source` match (verified on INT tenant `2qmxyw`, since the two connectors are separate codebases/repos and this cannot be unit-tested in-repo).
- **AC6**: Given the tool's description (as read via `tools/list`), When compared to `graph_get_group`'s description, Then it documents `isAssignableToRole` with the same "null means an ordinary group" semantics.

## Tech design

### Conclusion

Change the single `$select` statement in `graph_list_groups` (`src/graph_mcp/tools/groups.py:224`) to add `onPremisesSyncEnabled` and `isAssignableToRole`, then derive `sync_source` per group the same way `graph_list_user_groups` does (a loop that annotates each object before returning), and update the tool's docstring. This is a copy of an already-proven pattern used twice in the same file for the same connector — no new mechanism, no new dependency.

### Where the current implementation lives

- `src/graph_mcp/tools/groups.py:192-247` — `graph_list_groups` (the tool being changed).
- `src/graph_mcp/tools/groups.py:125-186` — `graph_list_user_groups` (the pattern to copy: multi-field `$select` + per-group `sync_source` loop + docstring wording).
- `src/graph_mcp/tools/groups.py:365-402` — `graph_get_group` (the other sibling with the same derivation, single-object form).
- `src/graph_mcp/tools/groups.py:251-325` — `graph_list_owned_groups` (out of scope; shares the *old* `$select` string by coincidence, not by relation).
- `src/graph_mcp/tools/_common.py` — `skiptoken()` helper used by the pagination contract; unaffected by this change.

### Option analysis

No real alternative: the connector already has two implementations of "add these two Graph fields to `$select`, derive `sync_source` from `onPremisesSyncEnabled`, don't coerce `isAssignableToRole`" for the same data shape (`graph_get_group`, `graph_list_user_groups`). Doing anything else in `graph_list_groups` — e.g. a different field name, a different null-handling rule, or a shared helper extracted now — would make the three tools inconsistent with each other for no benefit, and extracting a shared helper is more change than this one-line `$select` fix and one small loop justify (see Reuse & cleanup).

### Change list

- `src/graph_mcp/tools/groups.py` [modify] — in `graph_list_groups`:
  - `:224` `$select` string: add `onPremisesSyncEnabled,isAssignableToRole`, matching the multi-line format already used at `:151-155` in `graph_list_user_groups`.
  - `:238` (`groups = result.get("value", [])[:max_results]`): after slicing, loop over the sliced list and set `group["sync_source"] = "on-premises" if group.get("onPremisesSyncEnabled") else "cloud"` for each group, mirroring `:166-169`. `isAssignableToRole` needs no extra code — it is already in the response dict once added to `$select`, and Graph's `true`/`false`/`null` passes through untouched because nothing here reads or rewrites that key (same reason `graph_get_group` needs no special-case code for it).
  - `:211-216` docstring: add a line describing `isAssignableToRole` (true for role-assignable groups, null for ordinary groups — `graph_get_group`'s wording) and `sync_source` ("on-premises" for AD-synced groups, else "cloud" — `graph_list_user_groups`'s wording), keeping the existing pagination-contract sentence.
- `tests/test_tools.py` [modify] — add test(s) for the new fields on `graph_list_groups`, modeled on the existing `test_list_user_groups_returns_group_type_mail_enabled_and_sync_source` (`:1647-1673`) and the PRD-21676 `isAssignableToRole` tests (`:3832-3929`). Test strategy below has exact names.

### Reuse & cleanup

- **Reuse**: the `sync_source` derivation and the "don't coerce `isAssignableToRole`" rule are copied verbatim from `graph_get_group`/`graph_list_user_groups` in this same file — no new helper function, no new dependency. The existing `_register`/mock-client test harness in `tests/test_tools.py` (used by every other test in the file) is reused as-is.
- **New dependencies**: none.
- **API/param shape**: `graph_list_groups`'s signature (`display_name`, `exact`, `max_results`, `page_token`) is unchanged; only its output grows two fields per group item (`isAssignableToRole`, `onPremisesSyncEnabled`) plus the derived `sync_source`, consistent with the shape `graph_list_user_groups` already returns.
- **In-scope cleanup**: none found. The code this ticket touches (`:211-247`) has no dead code, no duplicate logic beyond the pattern already intentionally repeated three times in this file (which is the existing house style here — each tool is self-contained rather than sharing a field-shaping helper; not something to refactor as a side effect of this ticket).
- **Follow-ups (out of scope, for a separate ticket if wanted)**: `graph_list_owned_groups` (`:251-325`) still uses the old three-field `$select` for its internal full-group enumeration; its output (`owned_groups`) does not currently carry `isAssignableToRole`/`sync_source` either. Not requested by this ticket's Done-when, and its purpose (offboarding sole-owner detection) doesn't obviously need those fields — flagging only because it shares the stale select string the ticket's line citation pointed at.

### Data & API contract

- No HTTP-facing API changes — this is one MCP tool's Graph query and response shape.
- Graph request: `GET /groups` via `client.get("/groups", params=params)` (`:237`). `params["$select"]` changes from
  `"id,displayName,groupTypes,securityEnabled,mailEnabled"`
  to
  `"id,displayName,groupTypes,securityEnabled,mailEnabled,onPremisesSyncEnabled,isAssignableToRole"`.
  All other params (`$top`, `$skiptoken`, `$filter`) are unchanged.
- Tool response shape, before:
  ```json
  {"count": 1, "groups": [{"id": "g1", "displayName": "test two", "groupTypes": [], "securityEnabled": true, "mailEnabled": false}], "has_more": false, "next_page_token": null}
  ```
  after:
  ```json
  {"count": 1, "groups": [{"id": "g1", "displayName": "test two", "groupTypes": [], "securityEnabled": true, "mailEnabled": false, "onPremisesSyncEnabled": null, "isAssignableToRole": true, "sync_source": "cloud"}], "has_more": false, "next_page_token": null}
  ```
  (`sync_source` here is `"cloud"` because `onPremisesSyncEnabled` is falsy/null in this example — same rule as `graph_get_group`/`graph_list_user_groups`.)
- Backward compatibility: purely additive — three new keys per group object. No existing key is removed, renamed, or changes meaning. Callers that only read the old five fields are unaffected.
- No DB, no migration, no new error codes — `GraphError` handling at `:236/:247` is untouched.

### Key flow / sequence

1. Caller invokes `graph_list_groups` (optionally with `display_name`, `exact`, `max_results`, `page_token`).
2. Tool builds `params` with the expanded `$select` and calls `GET /groups`.
3. Graph returns a page of group objects, each already including `onPremisesSyncEnabled` and `isAssignableToRole` (because they're in `$select`), but not `sync_source` (Graph has no such field — it's this connector's own label).
4. Tool slices to `max_results`, then for each group sets `sync_source` from `onPremisesSyncEnabled`, exactly like step 3 of `graph_list_user_groups` (`:166-169`) and the single-object version in `graph_get_group` (`:398-400`).
5. Tool returns `{count, groups, has_more, next_page_token}` as before, with the enriched `groups`.

No sequence diagram needed — single external call, no branching beyond what already exists.

### Non-functional

- **Idempotency & concurrency**: unaffected. `graph_list_groups` is a read-only, annotated `idempotentHint=True` tool (`:192`); this change adds fields to a GET response, no new state.
- **Performance**: negligible. Two more fields in one existing `$select` does not add a Graph round trip (contrast with `graph_list_owned_groups`'s N+1 pattern, which this ticket does not touch). No change to `_MAX_GROUP_LIST_PAGES`, `_GRAPH_TOP_MAX`, or `_HARD_CAP_MAX_RESULTS`.
- **Security**: no new data exposure beyond what `graph_get_group` and `graph_list_user_groups` already return for the same groups under the same `Group.Read.All` permission (README.md:158) — this ticket does not widen what callers of the connector can see, it only makes one tool consistent with two others that already expose these fields.
- **Multi-tenant isolation**: not applicable — this is a single-tenant connector; all calls are already scoped to the one configured tenant via `client_factory()` (`:218-220`), unchanged by this ticket.
- **Observability**: no new logging needed; errors still surface via `GraphError.to_envelope()` (`:247`), unchanged.

### Rollout & rollback

- Single repo (`MSPbotsAIFramework/ms-graph-mcp`), single tool, additive response fields. No feature flag needed — per `references/mcp-track.md` 1.2, new fields a caller doesn't look for are simply ignored, so this is safe to deploy standalone.
- Release order: no dependency on any other repo or ticket (`release order: any` — there is nothing on the other side of a release-order dependency here: this is a single-repo, single-tool fix).
- Rollback: revert the one commit on `master`; the three new fields disappear and the tool returns exactly its prior shape. No data migration, nothing to undo externally.
