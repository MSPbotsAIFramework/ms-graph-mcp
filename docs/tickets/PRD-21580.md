## Requirement understanding

One line: Add a tool to the Microsoft Graph MCP connector that resolves a conditional-access named location id to its details (display name, IP ranges or countries, trusted flag), matching the Rewst `microsoft_graph.graph_api_request` call (`GET /identity/conditionalAccess/namedLocations/{id}`) used by Ginko IT's "Look Up M365 GUIDs" flow, so that flow can be migrated off Rewst.

This is item 12 of the Rewst → MSPbots migration gap register (`mspbots-gap-register.xlsx`). The gap is a missing tool, not a missing connector: `ms-graph-mcp` already exists and already handles users/groups/licenses/mail/sites/devices/domains/calendar/offboarding, but has no tool over `identity/conditionalAccess/namedLocations`. Without it, a flow that needs to turn a conditional-access policy's location id into a human-readable name (IP range or country list) has no equivalent on the Agent platform.

## Product design

### Goals / Non-goals

Goals:
- Add one new read-only tool, `graph_list_named_locations`, to `ms-graph-mcp` that:
  - given a `location_id`, returns that one named location's details;
  - given no `location_id`, returns all named locations in the tenant (the gap register's "可加列表版" / "optionally add the list variant" — see Open question Q2).
- Keep the tool's input/output, error shape, and required permission documented consistently in README's Tools table, `docs/gdap-role-map.yaml`, and the MCP `tools/list` response — the same three places every other tool in this connector is documented, and the place the connector's own consistency test (`test_gdap_role_map.py`) checks.
- Cover both named-location types Graph defines: `#microsoft.graph.ipNamedLocation` (IP ranges, `isTrusted`) and `#microsoft.graph.countryNamedLocation` (country/region list).

Non-goals:
- Not building any Conditional Access *policy* tools (create/update/delete a CA policy, list policies, etc.) — the gap register item is specifically about resolving a location id to a name, not managing CA policies. If a future ticket needs CA policy tools, that is new scope, not this one.
- Not building a `graph_create_named_location` / `graph_update_named_location` / `graph_delete_named_location` — the ticket is read-only ("读取条件访问的命名位置"); no write capability is requested.
- No changes to any other Graph domain already covered (users/groups/licenses/mail/sites/devices/domains/calendar/offboarding) and no changes to `gdap_roles.py`'s own serving mechanism beyond the one new YAML row it will serve.

### Acceptance criteria AC1..ACn

- AC1: Given a valid `X-Ms-Graph-Token` and a `location_id` for an existing IP named location, when `graph_list_named_locations` is called with that `location_id`, then the result includes `id`, `displayName`, `@odata.type` (`#microsoft.graph.ipNamedLocation`), `ipRanges`, and `isTrusted`, plus a normalized `location_type: "ip"` field.
- AC2: Given a valid token and a `location_id` for an existing country named location, when the tool is called with that `location_id`, then the result includes `id`, `displayName`, `@odata.type` (`#microsoft.graph.countryNamedLocation`), `countriesAndRegions`, and a normalized `location_type: "country"` field (no `isTrusted` — that field does not exist on this type).
- AC3: Given a valid token and no `location_id`, when the tool is called, then the result is the tenant's named locations (bounded the same way every other list tool in this connector bounds results — default/hard-cap pattern, AC4), each shaped as in AC1/AC2.
- AC4: Given more named locations exist than the connector's per-call cap, when the tool is called without `location_id`, then the result is capped and callable again to see the rest, consistent with how `graph_list_users` / `graph_list_group_members` already paginate (no silent truncation without a `has_more`-style signal).
- AC5: Given a `location_id` that does not exist (or was deleted), when the tool is called, then the result is a structured `not_found` error envelope (`{"error": {"code": "not_found", ...}}`), not a raw exception or an empty success payload that looks like "found nothing."
- AC6: Given no `X-Ms-Graph-Token` header on the request, when the tool is called, then the result is the standard `NO_TOKEN` envelope — identical behavior to every other tool in this connector, no special-casing.
- AC7: Given a token whose tenant has not granted `Policy.Read.All` (or an equivalent covering role), when the tool is called, then Graph's 403 is surfaced as the connector's standard `unauthorized` envelope (via the existing `GraphError` → `e.to_envelope()` path), not a stack trace.
- AC8: The new tool has exactly one row in `README.md`'s Tools table and exactly one entry in `docs/gdap-role-map.yaml`, with matching role values, so the repo's own `tests/test_gdap_role_map.py` (which enforces this for every registered tool) passes without modification to that test.

### Open questions

- [不阻塞 / not blocking — already assumed] Q1: What is the least-privileged Entra ID role for `Policy.Read.All` over `identity/conditionalAccess/namedLocations`? Assumed **Security Reader**, following Microsoft's published least-privileged-role guidance for this permission and the same sourcing convention every other row in `docs/gdap-role-map.yaml` already uses (e.g. `Domain.Read.All` → Directory Readers, `Group.Read.All` → Directory Readers). If this turns out to be wrong, only the README/yaml metadata row needs correcting — no tool code, contract, or test other than the role string changes. Does not block implementation.
- [不阻塞 / not blocking — already assumed] Q2: Should `graph_list_named_locations` support the unfiltered list call (the gap register's parenthetical "可加列表版"), or only the single-id lookup the Rewst flow actually calls? Assumed **yes, `location_id` is optional**: when given, behaves as a get-by-id (matching the Rewst call exactly); when omitted, lists all locations (the same shape, bounded like every other list tool). This is a strict superset of the literally-requested capability, needs no extra Graph permission (the same `Policy.Read.All` scope covers both the collection and item GET), and keeps the tool's "list" name accurate instead of it secretly being a "get." Does not block implementation; if product disagrees, dropping the no-id branch is a smaller change than adding it later.

## Tech design

### Conclusion

Add one new tools module, `src/graph_mcp/tools/conditional_access.py`, exposing `graph_list_named_locations(location_id: str | None = None)`. It is a pure read: one Graph GET (by id when given, the collection endpoint when not), reusing the exact `client_factory()` / `NO_TOKEN` / `GraphError.to_envelope()` / `dump_json_capped()` pattern every other tool in this repo already uses — no new abstractions, no new dependencies, no new error-handling path. The only other required changes are additive: one import + one `register()` call in `server.py`, one README table row, and one `docs/gdap-role-map.yaml` entry.

### Data & API contract

Request (MCP tool call):
```json
{
  "name": "graph_list_named_locations",
  "arguments": { "location_id": "7fb67f7f-99a2-45a0-ba35-0dc1b6ced0f6" }
}
```
or, with no arguments, to list all:
```json
{ "name": "graph_list_named_locations", "arguments": {} }
```

Response — single IP location (AC1):
```json
{
  "id": "7fb67f7f-99a2-45a0-ba35-0dc1b6ced0f6",
  "displayName": "Corporate network",
  "@odata.type": "#microsoft.graph.ipNamedLocation",
  "location_type": "ip",
  "isTrusted": true,
  "ipRanges": [{ "@odata.type": "#microsoft.graph.iPv4CidrRange", "cidrAddress": "203.0.113.0/24" }]
}
```

Response — single country location (AC2):
```json
{
  "id": "a1b2c3d4-...",
  "displayName": "Blocked countries",
  "@odata.type": "#microsoft.graph.countryNamedLocation",
  "location_type": "country",
  "countriesAndRegions": ["CU", "IR", "KP"],
  "includeUnknownCountriesAndRegions": false
}
```

Response — list, no `location_id` (AC3/AC4), same shape as `graph_list_domains`'s envelope:
```json
{ "count": 2, "named_locations": [ /* objects shaped as above */ ], "has_more": false }
```

Errors (reusing the connector's existing envelope, no new codes):
```json
{ "error": { "code": "not_found", "message": "Graph API error 404: Resource '...' does not exist", "retryable": false } }
```
- `not_found` (404) — unknown/deleted `location_id` (AC5).
- `unauthorized` (401/403) — missing or insufficient-scope token (AC6/AC7); 401 is the `NO_TOKEN` short-circuit before any Graph call, 403 is Graph's own response surfaced via `GraphError`.
- `invalid_argument` (400/422) — malformed `location_id` (not a GUID) — Graph itself returns 400 for this; no extra validation needed in the tool (consistent with `graph_get_group`, which does not pre-validate `group_id` either).

DB: none — this connector is stateless (SOP "runtime model" — no persistence, no cross-request state; `api_client.py:16-19`'s shared `httpx.AsyncClient` carries no credentials).

Backward compatibility: pure addition. No existing tool, parameter, or response shape changes. No client of this connector can be broken by this change — it is a new capability under a new name.

### Key flow / sequence

1. Agent platform → `ms-graph-mcp` `/mcp`: `tools/call graph_list_named_locations` with `X-Ms-Graph-Token` header and (optionally) `location_id`.
2. `GatewayTokenMiddleware` (`server.py:28-60`) extracts the token into the per-request contextvar; 401 short-circuit if missing.
3. `conditional_access.register()`'s tool body calls `client_factory()` → `GraphClient(token, ...)`.
4. Tool calls `client.get(path, params=...)` — `path` is `/identity/conditionalAccess/namedLocations/{location_id}` or `/identity/conditionalAccess/namedLocations` depending on the argument.
5. `GraphClient.get()` (`api_client.py`) issues the HTTPS request to `graph.microsoft.com`, retries on 429/5xx, raises `GraphError` on a terminal failure.
6. Tool derives `location_type` from `@odata.type`, returns `dump_json_capped(result)` on success or `e.to_envelope()` on `GraphError`.
7. Response flows back through FastMCP to the Agent platform exactly like every other tool's response — no new transport-level behavior.

### Non-functional

- Idempotency & concurrency: pure GET, naturally idempotent; no shared mutable state introduced (the shared `httpx.AsyncClient` carries no credentials per `api_client.py:16-19`'s existing comment, and the per-request contextvar token isolation in `server.py` is unchanged by this ticket).
- Performance: one Graph call per invocation (by-id branch) or one bounded-page call (no-id branch, capped at the same 50/200 convention as every other list tool) — no N+1, no new hot path.
- Security: no new scope-handling code — reuses the existing per-request Header-only token model (SOP's "runtime model" three rules: credentials only from request headers, never persisted, never logged, no cross-request state). The new tool requires `Policy.Read.All`; tenants that have not granted it get Graph's 403, surfaced as the standard `unauthorized` envelope (AC7) — the same "returns 403 until the tenant re-consents" situation already documented for several existing tools (e.g. `graph_create_tap`, `graph_add_group_owner` in the current README), not a new category of problem for this connector.
- Multi-tenant isolation: unaffected — every call is scoped by the caller's own bearer token, same as all 43 existing tools; no tenant id is ever accepted as a parameter.
- Observability: no new logging/metrics needed beyond what `GraphClient`'s existing error classification already provides; a failed call surfaces its `GraphError` status code and message in the structured envelope, consistent with every other tool.

### Risks & dependencies

- Risk: the GDAP role assumption (Q1, Security Reader) could be wrong. Mitigation: it is metadata-only — wrong role name does not change the tool's behavior or contract, just needs a one-line fix in two files if corrected later.
- Risk: Graph's `/identity/conditionalAccess/namedLocations` collection endpoint's real-world pagination behavior (does it return `@odata.nextLink` the same way `/groups/{id}/members` does) is assumed, not verified against a live tenant, because no test tenant was available during design. Mitigation: the no-id branch degrades gracefully even if this assumption is wrong — worst case, `has_more` is always `false` and a tenant with more than the cap's worth of named locations needs a second mechanism later (unlikely in practice; named locations per tenant are typically single digits to low tens, not hundreds).
- Dependency: none on any other open ticket. `ms-graph-mcp`'s `master` at `e274955` (the tip used for this design, already including PRD-21391's `graph_list_user_roles` merge) is a stable base with no pending conflicting work visible in the branch list at design time.
