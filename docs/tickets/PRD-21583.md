## Requirement understanding

One line: Add a Microsoft Graph MCP tool that deletes one of a user's registered MFA authentication methods (Authenticator app / phone / email / FIDO2 / software OATH / Windows Hello for Business), identified by user_id + method_type + method_id, so the existing Rewst "Reset Microsoft MFA" flows can be migrated onto the Agent platform.

This comes from the Rewst → MSPbots migration gap register (item 15/53). Two live Rewst flows — `[ROC] M365: Reset Microsoft MFA` (Ginko IT, EMD Networking Services) and `[GinkoIT] HaloPSA- Update Ticket Reset MFA` (Ginko IT) — call Microsoft Graph's `DELETE /users/{id}/authentication/{methodType}/{methodId}` as the delete half of an MFA-reset runbook, after first reading the method id. `ms-graph-mcp` already exposes `graph_list_auth_methods` (read-only) and `graph_create_tap` (issue a one-time sign-in code), but has no tool to delete a method, so this half of the reset flow cannot be done through the Agent platform today. Success is: an agent can take a `method_id` obtained from `graph_list_auth_methods` and delete that exact method, getting back a clear, idempotent result.

## Product design

This connector has no end-user UI; "user-visible behaviour" here is the tool's observable contract to the calling agent/workflow (the same audience `graph_list_auth_methods`/`graph_create_tap` already serve).

### Goals / Non-goals

Goals:
- Add `graph_delete_auth_method(user_id, method_type, method_id)` to `ms-graph-mcp` so an agent can delete one specific MFA method after identifying it via `graph_list_auth_methods`.
- Match this repo's existing idempotent-delete contract: deleting an already-gone method is a success, not an error.

Non-goals:
- Not a "reset/delete all MFA methods for a user" composite. Both cited Rewst flows delete one named method per step; batch deletion isn't asked for and would be a separate design (bigger blast radius per call).
- Not adding a new OAuth scope or a new re-consent rollout — the needed scope (`UserAuthenticationMethod.ReadWrite.All`) is already requested for `graph_create_tap`.
- Not adding a "does the user have another MFA method left" lockout check — neither cited Rewst flow does this check (the ticket's own Rewst call example has no pre-check step). See Open Questions.

### Acceptance criteria AC1..ACn

- AC1: Given a user has a registered MFA method of a supported type and its `method_id` is known (from `graph_list_auth_methods`), When `graph_delete_auth_method` is called with `user_id`, `method_type`, `method_id`, Then Graph returns 204 and the tool reports `{"user_id": ..., "method_type": ..., "method_id": ..., "deleted": true}`.
- AC2: Given the `method_id` no longer exists for that user (already deleted, or a stale id), When the tool is called, Then Graph returns 404 and the tool still reports `deleted: true` — idempotent, the same convention as `graph_remove_managed_device`/`graph_remove_manager` — not an error.
- AC3: Given `method_type` is not one of `microsoftAuthenticatorMethods | phoneMethods | emailMethods | fido2Methods | softwareOathMethods | windowsHelloForBusinessMethods`, When the tool is called, Then the MCP layer rejects the call before any Graph request is made (enum/schema validation).
- AC4: Given the caller's tenant hasn't re-consented since `UserAuthenticationMethod.ReadWrite.All` was added (the same pre-existing condition already documented for `graph_create_tap`), When the tool is called, Then Graph returns 403 and the tool returns the standard `unauthorized` error envelope — no new rollout step introduced by this ticket.
- AC5: Given the token is scoped to tenant A, When `user_id` belongs to a different tenant, Then Graph rejects/404s the cross-tenant lookup server-side (the connector holds no tenant state of its own) — the same isolation model as every other tool in this connector.
- AC6: Given a missing or invalid `X-Ms-Graph-Token` header, When the tool is called, Then it returns the connector's standard `not_configured`/401 envelope, same as every other tool.

### Open questions

- [不阻塞] Should the tool refuse to delete a user's *last remaining* MFA method (lockout risk)? Neither cited Rewst flow performs this check, and both call this as one step inside a larger "reset MFA" runbook rather than a standalone action. Not implementing a pre-check for v1; recorded as a Known Gap in the README, in the same style as this connector's other documented limitations (e.g. `graph_list_user_roles`'s PIM-eligible-roles gap, `README.md:277`). If product wants this changed, say so in a comment and move the ticket back to `5b - ready for groom`.

## Tech design

### Conclusion

Add one new tool, `graph_delete_auth_method`, to `src/graph_mcp/tools/users.py` (same file and `register()` closure as `graph_list_auth_methods`), following the exact idempotent-DELETE shape already used three times in this repo. No new scope, no new OAuth rollout, no new file, no new dependency — the pattern, the HTTP client, and the scope all already exist.

### Where the current implementation lives

- `src/graph_mcp/tools/users.py:819-833` `graph_list_auth_methods` — the upstream lookup this new tool pairs with; same file, same `register()` function, same `client_factory`.
- `src/graph_mcp/tools/users.py:745-813` `graph_remove_manager` — the idempotent-delete pattern to copy: read-then-delete isn't needed here (no replacement object), but the `try/except GraphError: if status_code != 404: return envelope` shape is.
- `src/graph_mcp/tools/devices.py:56-80` `graph_remove_managed_device` — closest structural twin: a pure delete-by-id tool (no read step at all), `ToolAnnotations(readOnlyHint=False, destructiveHint=True, idempotentHint=True)` — the annotation shape this new tool should reuse.
- `src/graph_mcp/api_client.py:105` `GraphClient.delete(path) -> Any`; `:55-63` `GraphError`/`to_envelope()`; `:36-43` `_STATUS_TO_CODE` (404→`not_found`, 403→`unauthorized`, 400/422→`invalid_argument`, 429→`rate_limited`).
- `src/graph_mcp/tools/_common.py:5-7` `NO_TOKEN` envelope, reused unchanged.
- `README.md:138-225` tool table + scope-union block — needs one new row; no new scope line (scope already listed at `README.md:206`).
- `docs/gdap-role-map.yaml:45-52` — needs a sibling entry for the new tool, next to `graph_list_auth_methods`/`graph_create_tap`.
- `tests/test_tools.py:16-70` `EXPECTED_TOOLS` dict + `_NON_READ_ONLY` set, `:94` onward `test_tools_list_snapshot` running tally comment — all three need updating, the same way every prior tool addition in this repo's history has (e.g. PRD-21391's `graph_list_user_roles`).

### Option analysis

No real alternative: this is a single, narrowly-scoped Graph endpoint (`DELETE /users/{id}/authentication/{methodType}/{methodId}`) mapping to exactly one new tool, following a pattern this repo already uses three times. The only real choice is *shape*:

| Option | Shape | Decision |
|---|---|---|
| One tool, three required params (`user_id`, `method_type`, `method_id`) | mirrors Graph's own path 1:1; `method_type` as a `Literal` enum lets the MCP schema reject bad values before any network call (AC3) | **chosen** |
| Six separate tools, one per method type | same endpoint, same params, only the path segment differs | rejected — exactly the "mode flag" shape this repo's own `test_tools_list_snapshot` comments reject for every prior tool (see its calendar/mail notes) |
| Delete-all-methods composite | one call removes every method | rejected — not asked for (Non-goals); silently escalates the blast radius of a single call |

### Data & API contract

- MCP tool: `graph_delete_auth_method(user_id: str, method_type: Literal[microsoftAuthenticatorMethods|phoneMethods|emailMethods|fido2Methods|softwareOathMethods|windowsHelloForBusinessMethods], method_id: str) -> str` (JSON string, like every tool in this repo).
- Upstream call: `DELETE https://graph.microsoft.com/v1.0/users/{user_id}/authentication/{method_type}/{method_id}`, `Authorization: Bearer <token forwarded from X-Ms-Graph-Token>` (handled by the existing `GraphClient`, no new code). Graph returns `204 No Content` on success (the ticket's own "返回字段" section confirms this and matches Microsoft's documented contract for this endpoint).
- Tool response (both the 204 and the idempotent-404 case): `{"user_id": "<echoed>", "method_type": "<echoed>", "method_id": "<echoed>", "deleted": true}`.
- Error envelope (any other status): `error_envelope(code, message, retryable)` via `GraphError.to_envelope()` — `403`→`unauthorized`, `400`/`422`→`invalid_argument`, `429`→`rate_limited`, `5xx`→`upstream_error`. No new error codes introduced.
- Backward compatibility: purely additive — new tool, new README row, new yaml entry, new test entries. No existing tool's signature, return shape, or requested scope changes.
- DB: none — this connector is stateless (no persistence layer exists in this repo).

### Key flow / sequence

1. Agent calls `graph_list_auth_methods(user_id)` (existing tool) → gets back each registered method's `id` and Graph's `@odata.type` (e.g. `#microsoft.graph.phoneAuthenticationMethod`).
2. Agent maps the target method's `@odata.type` to the corresponding `method_type` path segment — this mapping is the caller's responsibility today, same as it is for every other multi-type Graph resource this connector exposes; no server-side translation is added or requested.
3. Agent calls `graph_delete_auth_method(user_id, method_type, method_id)`.
4. `GraphClient.delete` issues the Graph `DELETE` with the forwarded per-request token — no stored credentials, no state shared across calls (`api_client.py:16-18`).
5. `204` or `404` → tool returns `deleted: true`. Any other status → the standard structured error envelope, same as every other tool in this connector.

### Non-functional

- Idempotency/concurrency: delete is naturally idempotent at the Graph layer (a second call 404s); the tool additionally normalizes 404 to success, matching the convention already documented for `graph_remove_managed_device`/`graph_remove_manager`. No local state to race on — the server holds no credentials or session state (`api_client.py:16-18`), identical to every other tool.
- Performance: one Graph call, no pagination, no loop. Timeout/retry behavior is inherited unchanged from `GraphClient` (`_TIMEOUT`, retries on `{429,500,502,503,504}`, `_MAX_RETRIES=3`).
- Security: the Graph access token is read only from the per-request `X-Ms-Graph-Token` header, never stored, never logged — same as every tool in this repo (the SOP's header-only-credentials / no-persistence / request-level-isolation rules). This is a destructive, non-reversible action from the tenant's point of view (a deleted MFA method must be re-registered by the user), so it is annotated `destructiveHint=True` — no new risk category versus `graph_remove_managed_device`, which is equally destructive and already ships.
- Multi-tenant isolation: identical to every other tool — the access token determines the tenant scope on Microsoft's side; this server is stateless per request and never caches or mixes tokens across calls (`api_client.py:16-18`, unchanged by this ticket).
- Observability: no new logging beyond what `GraphClient`/`GraphError` already produce (error envelopes carry the Graph status code and message). Consistent with every other tool — this repo does not log tool-call-level audit trails today, and adding that is out of scope here.
