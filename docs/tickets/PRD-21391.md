# PRD-21391 · [Feature] Read user admin roles in Graph and GDAP

## Requirement understanding

One line: Don wants a read-only tool that looks up a Microsoft 365 user's administrator roles (active now, PIM-eligible roles later) in both the Microsoft Graph connector and the Microsoft 365 GDAP multi-tenant connector, so an offboarding agent can check before resetting a password or blocking sign-in.

Don (reporter) needs an offboarding agent to confirm a departing user is not an administrator — active or PIM-eligible — before it resets the password or blocks sign-in, and also wants this for access reviews. No such lookup exists today; `graph_list_user_groups` only returns group memberships, not directory roles. He explicitly confirmed (Interview Log A1) that active-role detection alone is enough for the first deployment to PRECICOM; eligible (PIM) roles can follow in a later ticket. The capability must exist in both connectors used today: the single-tenant Microsoft Graph connector and the multi-tenant GDAP connector (which needs a `customer_tenant_id` to pick the customer). The ticket's own "Existing Capability Check" and "Open Questions" sections say the reporter could not verify wiki coverage or endpoint feasibility themselves and ask engineering to do so — both are done below (Current state, wiki check).

## Current state

- No tool in either connector reads a user's Entra ID directory role assignments. `graph_list_user_groups` (`src/graph_mcp/tools/groups.py:126-182`) lists **group** memberships only, via `GET /users/{user_id}/memberOf/microsoft.graph.group` (the OData type-cast segment at `groups.py:166`); it deliberately excludes the polymorphic `directoryRole` and `administrativeUnit` members of `/memberOf` (`groups.py:157-162` comment).
- `graph_list_gdap_roles` (`README.md:185`, added by PRD-21193) and gdap-mcp's `gdap_list_tool_roles` (`gdap-mcp/README.md:103`) serve the **static** per-tool GDAP role requirement map (`docs/gdap-role-map.yaml`) — "which Entra role does a human need to call tool X" — not a per-**user** role lookup. This is a different capability from what PRD-21391 asks for; verified by reading both repos' `docs/gdap-role-map.yaml` and `app/gdap_roles.py` — neither touches a user id.
- `gdap-mcp/app/snapshot.py:187,226` and `app/pim.py` read `/roleManagement/directory/roleDefinitions` and `/policies/roleManagementPolicyAssignments`, but only to drive the MSP's own PIM-for-groups elevation flow (`pim_activate`/`gdap_pim_status`), not to report a **client-tenant user's** admin roles. Confirmed by grep: no occurrence of `roleAssignment`/`transitiveMemberOf`/`directoryRole` tied to a `user_id` parameter in either repo (`ms-graph-mcp/src`, `gdap-mcp/app`).
- The GDAP connector's tool-porting mechanism already exists and is documented: ms-graph-mcp tool bodies are copied into `gdap-mcp/app/graph_tools/`, then `gdap-mcp/app/graph_tools/registry.py:33-53` (`TOOLS` frozenset) opts a copied tool in, and `registry.py:91-121` (`_wrap`) auto-prepends a required `customer_tenant_id` parameter and routes the call through `toolrun.run` (guard → scope check → customer token → 403 mapping → audit). This is documented end to end in `gdap-mcp/app/graph_tools/__init__.py:1-33` ("To resync").
- Both repos' `docs/gdap-role-map.yaml` is enforced by a test (`tests/test_gdap_role_map.py` in each repo) that fails if a registered tool has no matching row — confirmed by reading both test files; any new tool needs a row in both yaml files.
- Permission scopes currently requested by the platform for this connector (`ms-graph-mcp/README.md:201-224`) do **not** include `Directory.Read.All` or `RoleManagement.Read.Directory` ("`Directory.Read.All` is **not requested** (no tool needs to read the whole directory)", `README.md:214`). `graph_list_user_groups`'s `/memberOf` family of calls already works today under the requested `GroupMember.Read.All` / `User.Read.All` scopes (Microsoft Graph's documented permissions for `GET /users/{id}/memberOf` include `User.Read.All`, `Directory.Read.All`, *or* `GroupMember.Read.All` — any one suffices).

"Microsoft Graph" only matches generic platform connector-field pages (`ProductDocs/11-SOP-Agents.md`, `_field-index.md`, `15-Capabilities.md`) unrelated to this capability; "GDAP" and "admin role" have zero hits. **Wiki does not cover this capability** — consistent with the reporter's own note that wiki retrieval was unavailable to them. ## Product design

### Goals / Non-goals

Goals:
- Add one new read-only tool, `graph_list_user_roles(user_id)`, to the Microsoft Graph connector (`ms-graph-mcp`), returning the Entra ID directory roles the given user is currently an active member of.
- Make the same tool available in the GDAP connector (`gdap-mcp`), where it additionally takes `customer_tenant_id` (the standard GDAP parameter every ported tool gets, per `registry.py:55-58`) to select which MSP customer tenant to look at.
- Each returned role carries a name, a classification, and a scope, per the ticket's Success Criteria.
- The lookup never writes to the directory (AC4).

Non-goals (this slice, per the reporter's explicit confirmation that active-role detection alone is sufficient for the first PRECICOM deployment — Minimal Viable Slice / Interview Log A1):
- PIM-**eligible** role detection. Tracked as a follow-up; see Open Questions.
- Administrative-Unit-scoped role assignments (roles granted over a subset of the directory rather than tenant-wide). See Open Questions — this is a real gap in this slice's coverage, not an oversight to silently accept.
- Any write/elevation action. This tool only reads; `pim_activate` (already in gdap-mcp) is the existing, separate elevation path and is untouched by this ticket.

### Acceptance criteria AC1..AC7

- **AC1** — Given a known Global Administrator's `user_id`, when `graph_list_user_roles` is called (in either connector), then the response's `roles` list includes an entry whose `display_name` is `"Global Administrator"`. *(ticket Success Criteria #1, Acceptance criteria #1)*
- **AC2** — Every entry in `roles` has `display_name`, `classification` (`"active"` for every entry in this slice — see Non-goals), and `scope` (`"directory"` for every entry in this slice — see Open Questions on AU scope). *(ticket Acceptance criteria #2)*
- **AC3** — The tool is registered and callable in both `ms-graph-mcp` (signature `graph_list_user_roles(user_id)`) and `gdap-mcp` (signature `graph_list_user_roles(customer_tenant_id, user_id)`, the `customer_tenant_id` added automatically by the existing wrapper). *(ticket Acceptance criteria #3)*
- **AC4** — The tool issues only HTTP GET calls to Microsoft Graph; calling it never changes a user's account, group membership, or role assignment (verified by code review: the tool body contains no PATCH/POST/DELETE call, and by `fake_microsoft.py` recording zero mutating calls during the AC1/AC6/AC7 test runs). *(ticket Acceptance criteria #4)*
- **AC5** — Given a user with no admin role assignment, when `graph_list_user_roles` is called, then the response is `{"user_id": ..., "count": 0, "roles": []}`, not an error (mirrors the existing `graph_list_auth_methods`/`graph_list_user_groups` empty-result contract).
- **AC6** — Given a `user_id` that does not exist in the tenant, when `graph_list_user_roles` is called, then the response is the same structured 404 error envelope every other user-scoped tool in this repo returns (`GraphError.to_envelope()`), not an unhandled exception.
- **AC7 (deferred, not implemented this slice)** — Given a user who is PIM-eligible (but not currently active) for an administrator role, looking up that user returns an entry with `classification: "eligible"` for that role. *(ticket Acceptance criteria #5)* Tracked as a non-blocking Open Question / follow-up ticket; see below. Listed here, not silently dropped, because it was an explicit ticket acceptance criterion.

### Open questions

- **Eligible/PIM role detection (AC7) is out of scope for this slice** — not blocking. The reporter explicitly confirmed active-role detection alone is sufficient to deploy to PRECICOM (Interview Log A1, Minimal Viable Slice). Recommend a follow-up ticket once this slice ships; it will need `/roleManagement/directory/roleEligibilitySchedules` (or `/roleManagement/directory/roleEligibilityScheduleInstances` for currently-eligible-not-yet-activated), which needs the new scope `RoleManagement.Read.Directory` and, per this repo's documented rollout pattern for every previous new-scope tool (Mail.Read/PRD-19103, Calendars.ReadWrite/PRD-18631, Synchronization.ReadWrite.All/PRD-20422 — see `README.md:216-220`), a re-consent by every already-connected tenant before it stops returning `unauthorized`.
- **Administrative-Unit-scoped role assignments are not covered by this slice** — not blocking, but a real, documented limitation, not an oversight. `GET /users/{id}/memberOf/microsoft.graph.directoryRole` (the endpoint this design uses, see Tech design) only returns tenant-wide directory role membership; a role assigned to a user over a specific Administrative Unit (e.g. "User Administrator for AU X") does not appear there and would need `/roleManagement/directory/roleAssignments?$filter=principalId eq '{id}'&$expand=directoryScopeId` instead (the reporter's second suggested endpoint). Assumption made: AU-scoped admin delegation is uncommon enough in the MSP/offboarding use case that this gap does not block the PRECICOM deployment; if PRECICOM or another tenant relies on AU-scoped admin roles, offboarding could still fail to flag the departing user as an admin. Flagging for product/engineering awareness rather than guessing an answer — same reasoning the reporter used for the active/eligible split.
- **Exact minimal Graph permission for `/memberOf/microsoft.graph.directoryRole` is unverified against a real tenant** — not blocking, consistent with how nearly every other endpoint in this repo's README is marked ("has not yet been tested on real tenant", e.g. `README.md:260-274`). The design's assumption (stated in Tech design) is that it needs no new scope beyond what `graph_list_user_groups` already uses successfully in production; this should be confirmed on a real tenant during dev/self-test, same as every other tool in this file's "Known Limitations" section.

## Tech design

### Conclusion

Add one new read-only tool, `graph_list_user_roles`, to both connectors, reusing the already-granted Graph permission scopes and the existing GDAP tool-porting mechanism. No new repo, no new Entra scope, no gateway change, no database change.

### Where the current implementation lives

- `ms-graph-mcp/src/graph_mcp/tools/users.py` — user-scoped tools; `graph_list_auth_methods` (`users.py:818-836`) is the closest existing analog: single user-scoped GET, no pagination, returns `{user_id, count, <list>}`, errors via `except GraphError as e: return e.to_envelope()`.
- `ms-graph-mcp/src/graph_mcp/tools/groups.py:126-182` (`graph_list_user_groups`) — closest analog for *which endpoint family to use*: it already reads `/users/{id}/memberOf/<cast>` and explicitly documents (comment at `groups.py:157-162`) that `/memberOf` is polymorphic and the OData type-cast segment (`/microsoft.graph.group`) makes Graph itself filter the result server-side.
- `gdap-mcp/app/graph_tools/` — where ms-graph-mcp tool bodies are copied verbatim (per `__init__.py:1-33`); `gdap-mcp/app/graph_tools/registry.py:33-53` (`TOOLS`) is the opt-in list, `registry.py:55-58` (`CUSTOMER_PARAM`) and `registry.py:91-121` (`_wrap`) are the generic wrapper that every copied tool gets for free — no per-tool GDAP plumbing needed beyond adding the name to `TOOLS` and the yaml row.
- Both repos' `docs/gdap-role-map.yaml` (ms-graph-mcp: `docs/gdap-role-map.yaml:1-4` header, row example at `:62-65`; gdap-mcp: header + row example at `:84-87`) and the consistency test `tests/test_gdap_role_map.py` in each repo.

### Option analysis

- **Chosen: `GET /users/{user_id}/memberOf/microsoft.graph.directoryRole`.** Same call shape as the proven `graph_list_user_groups` (`groups.py:166`), just a different OData type-cast segment. Reuses scopes already granted for `graph_list_user_groups` (`GroupMember.Read.All`/`User.Read.All` cover `/memberOf` per Microsoft's documented permissions for that endpoint) — no new Entra scope, no tenant re-consent rollout. Returns `displayName` directly on each `directoryRole` object, so no extra lookup is needed to turn a role template id into a human-readable name.
- **Rejected for this slice: `/roleManagement/directory/roleAssignments?$filter=principalId eq '{id}'` + `/roleManagement/directory/roleEligibilitySchedules`** (the reporter's suggested endpoints). Two reasons: (1) needs the new scope `RoleManagement.Read.Directory`, which — per this repo's own documented rollout cost for every previous new-scope addition (`README.md:216-220`) — means every already-connected tenant must re-authorize before the tool works, a multi-week-class rollout for an MVP the reporter said only needs active roles; (2) `roleAssignments` returns raw `roleDefinitionId`/`principalId` GUIDs, requiring extra calls to resolve a human-readable role name — more code and more Graph round-trips to reproduce what `directoryRole.displayName` already gives for free. This option is not thrown away: it becomes necessary anyway for the deferred eligible-role follow-up (Open Questions), since eligibility has no `/memberOf` equivalent.
- **Rejected: a new standalone tool/repo outside the two existing connectors.** The ticket asks for the capability inside the Microsoft Graph and GDAP connectors specifically (so the offboarding agent uses the same connector it already uses for `graph_update_user`/`graph_revoke_sessions`); both connectors already exist and already expose directory-management tools, so this is a "modify existing tool table" change (`references/mcp-track.md` §2.1, row 1), not a new-vendor build.

### Data & API contract

Request (both connectors; GDAP adds `customer_tenant_id`, prepended automatically by `registry.py:91-121`):

```
graph_list_user_roles(user_id: str)                                  # ms-graph-mcp
graph_list_user_roles(customer_tenant_id: str, user_id: str)         # gdap-mcp
```

`user_id`: object id (GUID) or `userPrincipalName`, same contract as every other user-scoped tool in both repos (e.g. `graph_get_user`, `graph_list_user_groups`).

Response (JSON, both connectors — identical shape, `dump_json_capped`):

```json
{
  "user_id": "alice@contoso.com",
  "count": 1,
  "roles": [
    {
      "id": "6a5b2c3d-...",
      "display_name": "Global Administrator",
      "role_template_id": "62e90394-69f5-4237-9190-012177145e10",
      "classification": "active",
      "scope": "directory"
    }
  ]
}
```

Empty case: `{"user_id": "...", "count": 0, "roles": []}` (AC5). Error case: the standard envelope from `error_envelope(code, message, retryable)` (e.g. `{"error": "not_found", "message": "...", "retryable": false}`), same shape every other tool's 404 produces (AC6).

Upstream Graph call: `GET https://graph.microsoft.com/v1.0/users/{user_id}/memberOf/microsoft.graph.directoryRole`. No request body, no write. `scope`/`classification` are computed client-side (not from Graph) for this slice, since every row this slice returns is, by construction, a tenant-wide active assignment — see Open Questions for what changes if/when AU-scoped or eligible roles are added.

Backward compatibility: purely additive (new tool, new yaml rows, new README rows); no existing tool's request or response shape changes.

### Key flow / sequence

1. Agent calls `graph_list_user_roles(user_id=...)` (ms-graph-mcp) or `graph_list_user_roles(customer_tenant_id=..., user_id=...)` (gdap-mcp).
2. (GDAP only) `registry.py`'s wrapper (`_wrap`, `registry.py:91-109`) routes the call through `toolrun.run`: scope/role check → customer token for `customer_tenant_id` → invoke the tool body → map 401/403 → audit row.
3. Tool body calls `GET /users/{user_id}/memberOf/microsoft.graph.directoryRole` using the per-request Graph token.
4. Each returned `directoryRole` object is mapped to `{id, display_name, role_template_id, classification: "active", scope: "directory"}`; the list (possibly empty) is wrapped in `{user_id, count, roles}` and returned as text (`dump_json_capped`).
5. On a Graph error (e.g. user not found → 404), `GraphError.to_envelope()` returns the same structured error shape as every other tool.

### Non-functional

- **Idempotency/concurrency**: pure read, no state; safe to call concurrently and repeatedly (`idempotentHint=True`, matching `graph_list_auth_methods`/`graph_list_user_groups`).
- **Performance**: single Graph call, no pagination (an admin typically holds a handful of directory roles; Graph does not page `/memberOf` for a realistic role count). No load/SLA target beyond what every other single-GET tool in this file already implicitly meets — this is a lookup, not a bulk listing.
- **Security / multi-tenant isolation**: in gdap-mcp, `customer_tenant_id` goes through the same `toolrun.run` customer-token/scope-check path as every other ported tool (`registry.py:97-105`) — no new isolation surface. In ms-graph-mcp, the token is per-request from the caller (gateway mode) as for every other tool; the server itself holds no credentials. No new credential storage, no new Header.
- **Observability**: covered for free by the existing audit path (`toolrun.py`, gdap-mcp) and the platform's existing per-tool-call logging — no new logging code needed, this is a GET like any other.
- **Least privilege**: deliberately reuses an already-granted scope instead of requesting a new one (see Option analysis) — this is itself the non-functional win of this design over the reporter's suggested endpoints.

### Rollout & rollback

- No new Entra scope, so no tenant re-consent rollout is needed (contrast with Mail.Read/Calendars.ReadWrite/Synchronization.ReadWrite.All, which all needed a re-auth wave per `README.md:216-220`). The tool should work on every already-connected tenant the moment the new version deploys.
- Rollback is a plain revert: remove the tool registration (and yaml row) in both repos; no data migration, no schema, no irreversible side effect to undo (the tool never writes).
- Release order: no cross-repo dependency to sequence — `graph_list_user_roles` in ms-graph-mcp and gdap-mcp are independent tool additions to independent services; publishing one before the other causes no breakage (`release order: any`, per `references/mcp-track.md` §1.2).

### Test strategy

- Unit tests (both repos, no network): `graph_list_user_roles` returns the right shape for AC1 (role present), AC5 (empty list), AC6 (404 → structured error), and issues only GET (AC4) — verified against a fake Graph/`fake_microsoft.py` HTTP layer, same style as the existing tests for `graph_list_user_groups`/`graph_list_auth_methods`.
- Role-map consistency: existing `tests/test_gdap_role_map.py` in both repos fails automatically if the new tool is registered without a matching yaml row, or vice versa — no new test code needed for this guarantee, just the two yaml rows.
- gdap-mcp integration: `tests/test_flows.py` call-through test exercising the full wrapped path (`customer_tenant_id` → `toolrun.run` → tool body → fake Graph), following the `graph_list_auth_methods` pattern at `test_flows.py:338-432`.
- Real-tenant verification (per repo convention, e.g. `README.md:260-274`): AC1/AC5/AC6 should be re-run against a real tenant with a known Global Administrator and a known non-admin user before this is trusted in production, same caveat this repo attaches to nearly every new endpoint. Not a blocker for merging — a missing real test account does not block this track (`references/mcp-track.md` §3, "Completion criteria").
- Regression: existing `graph_list_user_groups`/`graph_list_auth_methods` tests are untouched by this change (additive only) — self-test should still show them green.

### Effort & breakdown

- ms-graph-mcp: ~0.5 day (one tool function + yaml row + README row + test coverage).
- gdap-mcp: ~0.5 day (copy tool body + registry entry + yaml row + fake-route + flow test + two README count fixes).
- No sub-ticket split recommended — both halves are small and tightly coupled (same tool, same contract); splitting them would just add handoff overhead for no parallelism benefit (one dev does both in the same tick per `references/mcp-track.md` §3.2, one dev-leg pass per MCP repo).

### Risks & dependencies

- **Risk**: the exact minimal Graph scope for `/memberOf/microsoft.graph.directoryRole` is assumed, not yet verified on a real tenant (Open Questions) — if wrong, the tool would need a new scope and inherit the same re-consent rollout cost this design was chosen specifically to avoid. Mitigation: verify during dev self-test against a real or sandbox tenant before merge, consistent with this repo's existing practice for new endpoints.
- **Risk**: AU-scoped role assignments are invisible to this slice (Open Questions) — if PRECICOM or another tenant relies on them, a departing AU-scoped admin could be missed by the offboarding guard. Not blocking per the reporter's explicit MVP scoping, but worth flagging to the reporter once this ships.
- **Dependency**: none on another in-flight ticket. PRD-21193 (GDAP role mapping) is already merged into both repos' default branches and is read-only context for this design (it is *not* reused code, since it answers a different question — see Current state).
