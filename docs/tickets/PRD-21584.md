## Requirement understanding

One line: Add a graph_create_invitation tool to the Microsoft Graph connector so an agent can invite an external email address into the tenant as an Entra ID B2B guest user and get back the guest's directory id, closing gap item 16 of the Rewst-to-MSPbots migration register.

This ticket is item 16 of `mspbots-gap-register.xlsx` (Rewst account Ginko IT). Rewst's `[Ginko] Guest Invitation - Add Group` flow (18 runs in the last 365 days, evidence grade A) calls `microsoft_graph.create_invitation` (`POST https://graph.microsoft.com/v1.0/invitations`) to invite an external email address as a guest — supplying `invitedUserEmailAddress`, `inviteRedirectUrl` (Ginko uses `https://ginko.com.au/`), `sendInvitationMessage`, and `invitedUserDisplayName` — then publishes the result as `invite_result` and immediately calls `add_group_member` with the invited user's id. The requester checked all 43 Microsoft Graph tools plus the 51 GDAP tools in this connector and found no tool that creates an invitation, so the ask is a straight gap-fill: one new tool, no change to any existing tool.

## Product design

### Goals / Non-goals

**Goals:**
- Add one new MCP tool, `graph_create_invitation`, that lets an agent workflow (replacing Rewst's `[Ginko] Guest Invitation - Add Group` flow, and any future consumer) invite an external email address into the tenant as an Entra ID B2B guest user, optionally send the invitation email, customize the invited user's display name and the invitation email's language/body/CC list, and get back the information needed to immediately add that guest to a group with the existing `graph_assign_groups` tool — matching Rewst's own two-step `invite_result` → `add_group_member` flow with no extra lookup in between.
- Keep the tool's shape, error handling, and documentation consistent with every other tool in this connector, in particular the existing `graph_create_user` "build body from params → curated response" pattern, so an agent that already knows how to call `graph_create_user` needs no new mental model for this one.

**Non-goals:**
- Not supporting **resetting the redemption status of an already-invited guest** (the `invitedUser.id` + `resetRedemption: true` variant of the same Graph endpoint). Neither the ticket nor the Rewst flow it replaces asks for this — Rewst's flow only ever creates new invitations. A reset-redemption capability is a different, unasked-for operation that happens to share an HTTP endpoint; it can be added as a follow-up tool (or an optional parameter) if a future ticket asks for it.
- Not adding a tool to look up or list pending/redeemed invitations. The ticket's flow is write-only (invite, then add to group); reading invitation status, if ever needed, is a separate ask.
- Not deduplicating or special-casing "this email is already a pending/redeemed guest" — Graph itself decides what happens when `invitedUserEmailAddress` already corresponds to an existing guest (see AC8); this tool passes the request through and returns whatever Graph returns, the same contract every other write tool in this connector already has.
- Not verifying `User.Invite.All` / the `Guest Inviter` role assumption against a real tenant during design — no test tenant is available to this leg; the dev leg's self-test runs against the repo's existing fake-client test harness, same as every other tool here (`mcp-track.md` §3, "缺厂商测试账号不算阻塞").

### Acceptance criteria

- **AC1 (happy path, required fields only):** Given a valid `X-Ms-Graph-Token` with `User.Invite.All`, when `graph_create_invitation` is called with only `invited_user_email_address` and `invite_redirect_url`, then the tool issues `POST /invitations` with those two fields (plus the `sendInvitationMessage` default from AC2) and returns a JSON object containing the invited guest's directory id, the invitation's `inviteRedeemUrl`, and its `status`, sourced from Graph's `201` response.
- **AC2 (send_invitation_message default and override):** `send_invitation_message` defaults to `true` (Graph emails the invitation) when omitted, matching Rewst's own flow default; passing `send_invitation_message=false` is forwarded as `sendInvitationMessage: false` so no email is sent — an explicit, callable opt-out, not a hard-coded value.
- **AC3 (invited_user_display_name):** Given `invited_user_display_name` is supplied, it is forwarded as `invitedUserDisplayName` and the created guest user is given that display name (Graph's own behavior — this tool does not re-derive or validate it).
- **AC4 (invitation email customization):** Given any of `message_language`, `customized_message_body`, or `cc_recipients` are supplied, they are forwarded inside Graph's `invitedUserMessageInfo` object (`messageLanguage`, `customizedMessageBody`, `ccRecipients`) so the Graph-sent invitation email can be localized, carry custom text, and copy additional recipients; omitting all three omits `invitedUserMessageInfo` entirely rather than sending an empty object.
- **AC5 (required-field enforcement):** Given either `invited_user_email_address` or `invite_redirect_url` is missing, the call is rejected before any Graph request is made — these are the tool's only two non-default parameters, enforced the same way every other required parameter in this connector already is (FastMCP/pydantic schema validation, exercised here via `EXPECTED_TOOLS["graph_create_invitation"]`).
- **AC6 (upstream Graph error):** If Graph returns an error (400 — malformed email or redirect URL; 403 — token lacks `User.Invite.All`, or B2B invitations are disabled on the tenant; 429 — rate limited; 5xx — upstream failure), the tool surfaces it as this connector's standard structured error envelope (`{"error": {"code", "message", "retryable"}}` via `GraphError.to_envelope()`), with the same code/retryable mapping every other tool already gets from `api_client._classify` — no new error-mapping logic needed or wanted.
- **AC7 (composable with graph_assign_groups — the ticket's actual end-to-end ask):** The id this tool returns for the invited guest is the same kind of plain directory-object-id string `graph_assign_groups`'s `user_id` parameter expects (`groups.py:32-36`) — an agent can pass this tool's output id directly into `graph_assign_groups` with no intermediate lookup, exactly reproducing Rewst's own `invite_result` → `add_group_member` chain.
- **AC8 (Graph decides duplicates, not this tool):** Given `invited_user_email_address` already corresponds to an existing guest user (pending or already redeemed), this tool does not special-case, detect, or block that condition — it passes the request through and returns whatever Graph's response contains (a fresh invitation, an error, or Graph's own existing-user handling), consistent with every other write tool in this connector not re-implementing Graph's own business rules.
- **AC9 (permission/multi-tenant anchor, hits the backend):** Given the caller's token lacks `User.Invite.All` (or the signed-in user lacks a role permitted to invite guests), Graph returns `403` and the tool surfaces it as `unauthorized` via the real `POST /invitations` call path — this connector has no UI, so there is no menu/gating layer to be fooled by; the only gate is this backend call itself.

### Open questions

- **Q1 — exact GDAP role (not blocking, decided with a flagged assumption).** Microsoft's docs list three least-privileged Entra roles for inviting guests: `Guest Inviter`, `Directory Writers`, `User Administrator`. This repo's convention (e.g. `graph_check_user_exists` → `Directory Readers` only, not also `Global Reader`) is to record the single narrowest-fitting role, not enumerate every role that happens to also qualify. **Decision for this ticket:** record `Guest Inviter` — the role Microsoft purpose-built for exactly this operation — and note in the yaml that `Directory Writers`/`User Administrator` also qualify per Graph's docs if an MSP's GDAP relationship doesn't carry `Guest Inviter` specifically. This does not block implementation: the tool's actual runtime gate is Graph's own `User.Invite.All` permission check on the bearer token, not this connector's documentation file (same reasoning PRD-21581's Q1 used for its own GDAP-role choice).
- **Q2 — `v1.0` vs `beta` endpoint (not blocking, decided).** Rewst's own flow calls `v1.0` already (unlike PRD-21581's source flow, which happened to call `beta`) — Microsoft Learn confirms `POST /invitations` is GA in `v1.0` with the exact same request/response shape. **Decision:** use `v1.0`, matching both Rewst's own call and every other tool in this connector.
- **Q3 — resetRedemption (not blocking, out of scope, see Non-goals).** Flagged here rather than silently dropped: if a future ticket needs to resend an invitation to an already-invited guest, it would add `invited_user.id` + `reset_redemption` as two more optional parameters to this same tool (same Graph endpoint, same shape) rather than a new tool.

### Option analysis

**Where does the new tool live — a new `invitations.py` module, `users.py`, or `groups.py`?**

- Considered: `users.py`, since an invitation creates an Entra user object (`userType: Guest`) and the module already has the closest-shaped precedent (`graph_create_user`).
- Considered: `groups.py`, since the ticket's own end-to-end use case is "invite, then add to a group" — but the invitation itself has nothing to do with groups; chaining to `graph_assign_groups` is the caller's job (AC7), not this tool's.
- Chosen: a new `invitations.py` module. Reasoning — this repo's own module boundary is "one Graph resource family per file" (`domains.py` → `/domains`, `gdap_roles.py` → the static role map, `licenses.py` → `/subscribedSkus` + license assignment), and `/invitations` is Graph's own distinct resource family, conceptually and operationally different from `/users`: it doesn't take a `user_id` (there is no existing user to act on — the whole point is that the user doesn't exist yet), its response shape is its own (`inviteRedeemUrl`, `status`, a nested `invitedUser` sub-object) rather than a user profile, and bolting it onto an already-965-line `users.py` would make that file's name less precise for no benefit (mirrors PRD-21581's identical reasoning for spinning `policies.py` out of `domains.py`/`users.py` rather than appending to either).
- Not chosen: a one-off function appended to `users.py` with a comment explaining the mismatch — rejected for the same reason PRD-21581 rejected it: it sets a precedent that "small tools get appended to whatever file already exists" instead of being named for the Graph resource they read/write.

**Flatten `invitedUserMessageInfo` into scalar parameters, or accept a raw nested object?**

- Chosen: flatten into `message_language: str | None`, `customized_message_body: str | None`, `cc_recipients: list[str] | None` (plain email-address strings), assembled into Graph's `{"messageLanguage", "customizedMessageBody", "ccRecipients": [{"emailAddress": {"address": ...}}, ...]}` shape only if at least one is supplied. This matches the existing convention of exposing agent-friendly scalar/list parameters instead of raw Graph JSON shapes — `calendar.py`'s `attendees`/`optional_attendees` (`calendar.py:209-213`) take plain email-address lists and build Graph's nested `attendees` array internally; no tool in this connector currently asks the caller to hand-assemble a nested Graph object.
- Not chosen: a single `invited_user_message_info: dict | None` parameter accepting Graph's raw nested shape — rejected because every other tool in this connector hides Graph's own object nesting behind named scalar/list parameters (the whole point of exposing MCP tools instead of a raw Graph proxy), and a raw-dict parameter would be the only one of its kind, making the schema both harder for an agent to use correctly and inconsistent with the rest of the Tools table's styling.

**Response shape: curated fields, or raw passthrough of Graph's `201` body?**

- Chosen: curated response — `invited_user_id` (from `invitedUser.id`), `invited_user_email_address`, `invite_redeem_url`, `status`. Matches `graph_create_user`/`graph_create_tap`'s convention of picking named fields into a snake_case dict rather than passing Graph's raw camelCase response straight through, and gives exactly the one field (`invited_user_id`) the ticket's own downstream step (`add_group_member`) needs, without the caller's agent having to know to reach into a nested `invitedUser` object itself.
- Not chosen: raw passthrough of Graph's response (`id`, `invitedUser: {id, userPrincipalName}`, `invitedUserDisplayName`, `invitedUserType`, `invitedUserEmailAddress`, `sendInvitationMessage`, `resetRedemption`, `inviteRedirectUrl`, `status`, `invitedUserMessageInfo: {...}`) — rejected because it echoes the caller's own input back at it (noise) and makes the one field that matters for chaining (`invitedUser.id`) one nesting level deeper than every other tool's curated id fields in this connector.

**Error response** (same shape as every other tool):
```json
{"error":{"code":"unauthorized","message":"...","retryable":false}}
```

**Backward compatibility:** purely additive — a new tool, no change to any existing tool's request or response shape, no schema migration (this connector has no database).

### Key flow / sequence

1. Agent client sends `tools/call` for `graph_create_invitation` with `X-Ms-Graph-Token: <token>` on the `/mcp` request.
2. `GatewayTokenMiddleware` (unchanged) validates the header is present, stores the token in the per-request `contextvars.ContextVar`, forwards the request.
3. FastMCP dispatches to `invitations.py`'s registered tool function.
4. The tool calls `client_factory()` → `get_client_from_context(settings)` → a fresh `GraphClient(token, settings.graph_base_url)` scoped to this request/task only (no change to this mechanism).
5. The tool builds the request body from its parameters (conditionally assembling `invitedUserMessageInfo`), then `GraphClient.post("/invitations", body)` → Graph API → `201 Created` with the invitation object, or a `4xx`/`5xx` that the client turns into a `GraphError`.
6. Tool returns the curated `dump_json_capped({...})` on success, or `e.to_envelope()` on `GraphError`.
7. (Caller's own next step, not part of this tool) The agent calls `graph_assign_groups(user_id=<invited_user_id from step 6>, group_ids=[...])` to reproduce Rewst's `add_group_member` step.

No new sequence, no new state, no persistence — this is the same "build body → `client.post` → curate response" flow `graph_create_user`/`graph_create_tap` already follow.

### Non-functional

- **Idempotency / concurrency:** `readOnlyHint=False, idempotentHint=False` — a `POST` that creates a new resource; calling it again with the same email may create a second invitation or hit Graph's own existing-guest handling (AC8), not something this tool should claim is safe to retry blindly. No state shared across calls.
- **Performance:** single Graph API call, no pagination; response is small (a handful of scalar fields plus one small nested object) — well under `dump_json_capped`'s 20,000-char cap.
- **Security:** credentials are never read from anywhere but the per-request `X-Ms-Graph-Token` header (unchanged mechanism); the tool never logs the token (inherited from `GraphClient`); no email-format validation beyond what Graph itself performs (a malformed `invitedUserEmailAddress`/`inviteRedirectUrl` surfaces as Graph's own `400` → `invalid_argument`, the same contract every other tool in this connector has — no tool here re-implements Graph's own request validation). `cc_recipients` entries are forwarded as-is to Graph; this tool does not send any email itself — Graph does, if `send_invitation_message` is true.
- **Multi-tenant isolation:** relies entirely on the existing `GatewayTokenMiddleware` / `_gateway_token_var` contextvar mechanism (`server.py:15-18,27-44`), already the isolation boundary for all 45 existing tools; no new mechanism needed.
- **Observability:** no new logging added; errors surface through the existing structured `GraphError.to_envelope()` path, consistent with every other tool.

### Rollout & rollback

- **Rollout:** merge to `master` (this repo's default branch — no `release`/`int` concept per `mcp-track.md`), then publish to INT via `mbp.py mcppub publish --repo MSPbotsAIFramework/ms-graph-mcp` (review leg, per `mcp-track.md` §4.8). Purely additive — no coordination needed with any other repo, no feature flag, `release order: any` (this ticket touches exactly one MCP repo and no platform repo).
