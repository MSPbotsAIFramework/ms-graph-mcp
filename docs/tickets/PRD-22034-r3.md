## Requirement understanding

One line: Add three read-only tools to the ms-graph connector -- graph_list_teams, graph_list_channels, graph_get_channel -- so any SOP agent can discover a Microsoft Teams team and channel (with paging, a membership-type filter, and an explicit empty email value instead of a failure), with a clear error when the tenant has not consented to the needed Graph scope, before any send/preview capability is added.

Unchanged from `PRD-22034.md` -- this round is a bug-fix/clarification rework found during INT QA against a real tenant, not a scope change to what the feature does. See that file for the full requirement context.

## Product design addendum

### Acceptance criteria addendum

- **AC12** (DW4): Given a 403 from Microsoft Graph where the caller's own access token already carries the Graph permission the called tool needs (consent already granted -- e.g. the call fails because the target resource belongs to a different tenant, or for any other access-denied reason unrelated to consent), When that tool is called, Then the response is Graph's normal `unauthorized` error (today's generic 403 handling, `error.code == "unauthorized"`), not `missing_scope` -- a permission the token already carries is never reported as missing. This does not relax AC8: when the token does **not** carry the permission (or it cannot be determined whether it does), the `missing_scope` error still applies.

### Open questions addendum

- **[not blocking]** Telling "missing consent" and "access denied for another reason" apart from Graph's 403 alone is not reliable -- QA's own repro shows Graph returns the same generic `Authorization_RequestDenied` message for both. The fix (Tech design D2) reads the caller's own access-token claims (`scp`/`roles`) instead of trusting Graph's error text. If a future Graph response shape makes this unnecessary (e.g. Graph starts returning a distinct error code for cross-tenant denial), simplifying D2 is a contained follow-up, not a redesign.

## Tech design addendum

### D2: a 403 is only `missing_scope` when the caller's own token actually lacks the permission (FIND1, AC12)

- **Problem**: `missing_scope_error()` (`src/graph_mcp/tools/_common.py:11-27`), used by all three tools' three call sites (`src/graph_mcp/tools/teams.py:178,211,252,285`), turns every `status_code == 403` into a `missing_scope` envelope unconditionally. On a real tenant this is wrong whenever the 403 has a different cause -- QA's repro: reading a team belonging to another tenant from `2q` returns `missing_scope` naming `Channel.ReadBasic.All`, even though `2q`'s admin has already consented to it (proven by other channel calls in the same QA session succeeding). Graph's own 403 body does not distinguish the two cases (`Authorization_RequestDenied` / "Insufficient privileges" is the generic message either way), so the fix cannot be "read the message more carefully."
- **Fix**: before converting a 403 to `missing_scope`, check whether the caller's own bearer token already carries `scope`. The token is already available (`GraphClient` is constructed with it, `src/graph_mcp/api_client.py:74-76`); it is a standard Azure AD access token (JWT) whose claims this connector can read without verifying the signature -- Graph itself already validated the token before this connector ever saw it; this connector only needs to know what it was granted, not re-authenticate it.
  - **Delegated tokens** (`ms-graph` connector) carry granted scopes space-separated in the `scp` claim.
  - **App-only / client-credentials tokens** (`ms-graph-app` connector) carry them as a list of strings in the `roles` claim.
  - Add to `src/graph_mcp/api_client.py` (after `__init__`, `:74-76`): a read-only `token` property on `GraphClient` returning `self._token`, so `_common.py` can read it without reaching into a private attribute.
  - Add to `src/graph_mcp/tools/_common.py` (next to `missing_scope_error`): two small helpers -- `_decode_jwt_claims(token: str) -> dict | None` (splits on `.`, base64url-decodes the middle segment with padding fixed up, `json.loads`s it; returns `None` for anything that is not a well-formed 3-part JWT or does not parse to a JSON object -- no new dependency, no signature check) and `_granted_scopes(token: str) -> set[str] | None` (returns the `scp` string split on whitespace, or the `roles` list filtered to strings, or `None` if neither claim is present or the token could not be decoded).
  - Change `missing_scope_error(e: GraphError, scope: str) -> str` to `missing_scope_error(e: GraphError, scope: str, client: GraphClient) -> str`: on a 403, call `_granted_scopes(client.token)`; if it returns a set that **contains** `scope`, return `e.to_envelope()` (today's generic `unauthorized` envelope, Graph's own message -- this literally is "access denied," reusing the existing code path rather than inventing a new error code); otherwise (set without `scope`, or `None` meaning "could not tell") return the `missing_scope` envelope exactly as today. **`None` must default to `missing_scope`, not to "assume granted"** -- that preserves AC8's existing guarantee for every token this heuristic cannot read (opaque token, decode failure), so the fix only narrows the cases that were wrong, it never produces a new false negative.
  - Update the three call sites in `teams.py` (`:178,211,252,285`) from `missing_scope_error(e, "Team.ReadBasic.All")` / `missing_scope_error(e, "Channel.ReadBasic.All")` to the same calls with `, client` appended -- `client` is already in scope at each call site (bound at the top of each tool function).
- **Why this layer, not Graph's response**: Option considered and rejected -- parsing Graph's `error.code` (e.g. `Authorization_RequestDenied`) more finely. Rejected because QA's own evidence shows Graph returns the *same* code/message for both cases on this tenant; there is nothing in the response body to branch on. Reading the token's own claims is the only signal available that is actually different between "never granted" and "granted but denied for another reason."
- **Does not change**: the shape of the `missing_scope` envelope itself (unchanged from AC8/round 1); AC1-AC11; no new Graph call (claims are read from the token already in hand, no extra round-trip); no new third-party dependency (a 3-line base64url+JSON decode, not a JWT library -- this connector only ever reads, never verifies or mints, a token).

### D3: `graph_list_channels` / `graph_get_channel` need `Prefer: include-unknown-enum-members`, and the "no filter" doc line is wrong (FIND2, regression against AC5/AC6)

- **Problem**: Microsoft Graph's `channel.membershipType` is an evolvable (extensible) enum; by Graph convention, a value added after a client's API version was authored (`shared` is one such value) is returned as the sentinel `unknownFutureValue` unless the request carries `Prefer: include-unknown-enum-members`. Neither `graph_list_channels` (`src/graph_mcp/tools/teams.py:250`) nor `graph_get_channel` (`:280-283`) sends this header today, so QA's real tenant correctly reproduces `membershipType: "unknownFutureValue"` for a shared channel through both tools (`membership_type="shared"` filter result, and `graph_get_channel` on a shared channel) -- this violates AC5 ("every returned channel has that exact `membershipType`") and the implicit field-fidelity of AC6/AC7's response shape for `graph_get_channel`.
- **Fix**: add `extra_headers={"Prefer": "include-unknown-enum-members"}` to both Graph `GET` calls (`GraphClient.get()` already accepts `extra_headers`, used elsewhere in this repo, e.g. `src/graph_mcp/tools/users.py`'s advanced-query header -- this is the same mechanism, not a new one). This only changes how an extensible enum value serializes in the response; it does not change filtering, pagination, or any other field.
- **Separately, a documentation bug** (same root cause QA flagged, but a different kind of fix): `graph_list_channels`'s `membership_type` parameter description (`src/graph_mcp/tools/teams.py:229-232`) currently reads "Omit for Graph's default (standard channels only -- private/shared channels only appear when explicitly filtered)." QA confirms this is not true against a real tenant -- omitting the filter returns channels of every type the caller can see. This line was the original design's own unverified assumption (flagged as such in `PRD-22034.md`'s Open Questions, "whether `GET /teams/{id}/channels` returns only `membershipType: standard` channels unless `$filter=...` is passed... this environment cannot call Graph to confirm live"), now confirmed wrong. Fix: correct the description to "Return only channels of this type. Omit to return channels of every type (standard, private and shared) the caller can see." No AC requires a specific default-filtering behavior (AC4/AC5 only constrain the *filtered* case), so this is a docstring-only correction, not a behavior change -- no new test case needed for the wording itself, it is covered by the Self-test's own review of the tool's registered description text.
- **Does not change**: AC4 (no filter returns the known test channel); AC9 (own-tenant-only); the response shape; no new scope (the two scopes this ticket uses, `Team.ReadBasic.All`/`Channel.ReadBasic.All`, are unchanged -- `Prefer` is a request header, not a permission).

### Reuse & cleanup addendum

- **Reuse**: `GraphClient.get()`'s existing `extra_headers` parameter (already used by other tools, e.g. the advanced-query header in `users.py`) -- D3 needs no new plumbing. `e.to_envelope()` is reused as-is for the "access denied" case (D2) instead of inventing a new error code, keeping one error-code vocabulary across the whole connector.
- **New dependencies**: none. D2's claims read is a ~10-line base64url+JSON decode, not a JWT library -- this connector never needs to verify a signature (Graph already did), so adding a dependency (e.g. PyJWT) for a decode-only need would be the wrong tradeoff (KISS/YAGNI) for the one place in the repo that needs it.
- **In-scope cleanup**: the `membership_type` parameter description fix (D3) is the only "clean up what's wrong" item this round touches; it is inside the one function this round already modifies, not a separate pass over the module.
- **Follow-ups (out of scope, for a separate ticket, not this one)**: `visibility` returning `null` on the `user_id` branch of `graph_list_teams` (QA's "minor, not counted" note) -- no AC covers `visibility` fidelity for that branch, and QA explicitly excluded it from this round's fail count; worth a line in README's Known Gaps if a future ticket touches this area, not a fix forced into this round.

### Test strategy addendum

- **Unit (fake `GraphClient`, `tests/test_tools.py`)**:
  - D2, scope already granted: a fake client whose GET raises `GraphError(403, ...)` and whose `token` is a synthetic (unsigned, three-part) JWT with `scp` containing the tool's required scope (delegated case) -- asserts the envelope is `error.code == "unauthorized"`, not `missing_scope`. A second parametrized case does the same with `roles` (app-only case) instead of `scp`.
  - D2 regression, scope not determinable: the same 403 fake client with a token that is empty / not a well-formed JWT -- asserts the envelope is still `error.code == "missing_scope"`, naming the scope (this is the existing AC8 guarantee; it must keep passing exactly as today, since `None` must default to "missing", not "granted").
  - D3: a fake client (the existing `_CapturingClient`, already records `extra_headers` per call, `tests/test_tools.py:299-349`) -- asserts `graph_list_channels` and `graph_get_channel` each send `extra_headers={"Prefer": "include-unknown-enum-members"}`.
  - The existing `_ForbiddenGetClient` (`:5397-5402`) gets a `token: str = ""` constructor parameter (default empty, so the three existing AC8 tests -- TC-TEAMS-009/010/011 -- keep passing unchanged: an empty string is not a well-formed JWT, so `_granted_scopes` returns `None`, and the existing "missing_scope" assertions hold with no edit to those three tests).
- **Manual, against a real Microsoft 365 test tenant on INT (cannot be unit-tested, needs real data)**: AC12 end-to-end (a token whose consent already covers the scope still gets `missing_scope` turned off for a genuine cross-tenant/other-cause 403 -- this is exactly QA's own repro, re-verified once the fix ships); AC5/AC6's `membershipType` fidelity for a shared channel through both `graph_list_channels` and `graph_get_channel` (confirm `"shared"`, not `"unknownFutureValue"`).
- **Regression面**: no existing tool outside `teams.py` is touched; `missing_scope_error`'s new `client` parameter is a signature change local to this one function and its three call sites (all three already pass `client` to other calls in the same function, so no new variable needs introducing at any call site); `GraphClient.token` is additive (a new property, no existing attribute renamed or removed). TC-TEAMS-001..016 are re-run in full per rework discipline; none of their fakes construct a 403, except the three AC8 ones, covered above.
